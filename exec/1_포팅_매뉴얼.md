## 1. 전체 구성

```text
공공 API 9종 → 수집기(Python) → Kafka ─┬→ Spark Streaming → Redis(최신값)
                                         └→ Archiver → Parquet → HDFS(이력)

안드로이드 앱 / 웹 → nginx(HTTPS) → Spring Boot 백엔드 → MySQL / Redis
                                         ├→ ML 서빙(FastAPI, LightGBM)
                                         ├→ 카카오 길찾기·SSAFY GMS
                                         └→ Firebase(푸시 알림)
```

| 서버 | 주소 | 맡은 일 |
|---|---|---|
| 서버1 (데이터) | `j15e202a.p.ssafy.io` (사설 `172.26.15.35`) | Kafka, 수집기 9개, Spark(마스터·워커 2·스트리밍 앱 2), HDFS 네임노드·데이터노드1, 아카이버, 모니터링 수집기 |
| 서버2 (서비스) | `j15e202.p.ssafy.io` (사설 `172.26.6.220`) | nginx·웹, 백엔드, MySQL, Redis, ML 서빙, HDFS 데이터노드2·세컨더리 네임노드, Prometheus·Grafana, GitLab 러너 |

- 인터넷에 열린 포트는 **서버2의 80·443뿐**이다. MySQL·Redis·Kafka는 두 서버 사이에서만 통한다.
- 모든 구성요소는 Docker Compose(`infra/docker-compose.yml`)로 띄운다. 서버마다 덮어쓰는 파일이 하나씩 있다(`docker-compose.server1.yml`, `docker-compose.server2.yml`).

저장소 폴더:

| 폴더 | 내용 |
|---|---|
| `backend/` | Spring Boot 사용자·일정·추천 API (Maven) |
| `client/` | Flutter 안드로이드·웹 공통 앱 |
| `collector/` | 공공 API 수집 → Kafka 발행 (Python) |
| `archiver/` | Kafka 원본 → Parquet → HDFS (Python) |
| `sparkjobs/` | PySpark 스트리밍·배치 |
| `ml-serving/` | 버스 구간 소요시간 예측 서버 (FastAPI) |
| `infra/` | Compose, nginx, Kafka·Spark·HDFS 설정, 모니터링, 배포 스크립트 |
| `docs/` | 아키텍처, 데이터 계약, 장애 절차서(`docs/runbooks/`) |
| `notification/` | 비어 있음(설명 파일만). 알림은 백엔드가 직접 보낸다. CI가 폴더 존재를 검사하므로 지우지 않는다. |

### 2-7. 웹 서버 설정 (nginx)

설정 파일은 `infra/nginx/templates/default.conf.template` 하나다. 컨테이너가 뜰 때 `PUBLIC_DOMAIN`, `SERVER1_PRIVATE_IP` 값을 채워 넣는다.

| 포트·경로 | 동작 |
|---|---|
| 80 `/.well-known/acme-challenge/` | 인증서 갱신용 파일 응답 |
| 80 `/healthz` | 200 |
| 80 `/internal/` | 서버1 사설 IP만 허용 → 백엔드. 본문 20MB, 시간 제한 300초 |
| 80 그 밖 | `https://{PUBLIC_DOMAIN}`으로 301 이동 |
| 443 | HTTP/2, TLS 1.2·1.3, 인증서 `/etc/letsencrypt/live/{PUBLIC_DOMAIN}/`, gzip, 보안 헤더(nosniff, SAMEORIGIN, Referrer-Policy) |
| 443 `/api/` | `http://backend:8080`으로 전달(`/api` 접두사 유지). 도커 DNS를 10초마다 다시 찾아 백엔드를 새로 만들어도 502가 나지 않는다 |
| 443 `/internal/` | 80과 같은 규칙 |
| 443 `/` | 웹 정적 파일 `/usr/share/nginx/html` (= 서버2 `infra/nginx/web/`), 없는 경로는 `index.html` |

## 3. 빌드 방법

> 서버 배포는 서버가 직접 이미지를 빌드하므로, 사람이 손으로 빌드할 것은 **안드로이드 APK와 웹 파일**뿐이다. 아래 3-1, 3-3은 로컬 확인용이다.

### 3-1. 백엔드

```bash
# 테스트 (CI와 같은 명령, Java 17 필요)
cd backend && ./mvnw -B test

# 실행 파일만 만들기
cd backend && ./mvnw -B package -DskipTests      # → backend/target/*.jar

# 로컬 실행 (개발 프로파일 + 개발용 MySQL·Redis)
docker compose -f backend/docker-compose.dev.yml up -d
cd backend && SPRING_PROFILES_ACTIVE=dev ./mvnw spring-boot:run
```

- 운영 이미지(`backend/Dockerfile`, 빌드 위치는 저장소 루트):
  1. `maven:3.9.9-eclipse-temurin-17`에서 `mvn dependency:go-offline` → `mvn package -DskipTests`
  2. 실행은 `eclipse-temurin:17-jre-jammy`, 사용자 `ddubi`, `java $JAVA_OPTS -jar app.jar`
- `backend/transit-master/subway/`가 jar 안 `transit/`으로 들어가므로 빌드할 때 이 폴더가 있어야 한다(저장소에 있음).
- 프로파일을 안 주면 **운영(`prod`)** 으로 뜬다. 운영 프로파일은 `JWT_SECRET`이 비어 있으면 기동을 거부한다.

### 3-2. 앱 — 안드로이드 릴리스 APK

릴리스 APK는 **서명 스크립트로만** 만든다(윈도 PowerShell).

1. 준비물 (Git에 없음)
   - `client/.env` : `client/.env.example`을 복사해 키를 채운다(4-3절)
   - `client/android/app/google-services.json` : Firebase 콘솔에서 받는다
   - 릴리스 키스토어 `%USERPROFILE%\.android\keystores\ddubi-release.jks` (별칭 `ddubi`)와 비밀번호
2. 실행

   ```powershell
   cd client
   flutter pub get
   powershell -ExecutionPolicy Bypass -File tool\build_release_apk.ps1
   # 선택 인자: -KeystorePath <jks> -EnvironmentFile <.env> -ApiBaseUrl https://j15e202.p.ssafy.io/api/v1
   ```

   - 스크립트가 키스토어 비밀번호를 **입력받는다**(화면에 안 보임). 끝나면 임시 환경변수를 지운다.
   - 내부에서 실행하는 명령: `flutter build apk --release --dart-define-from-file=.env --dart-define=API_BASE_URL=<주소>`
3. 결과: `client/build/app/outputs/flutter-apk/app-release.apk`

- 카카오·구글 로그인이 되려면 이 키스토어의 **키 해시(카카오)와 SHA-1(구글)** 을 각 콘솔에 등록해야 한다.
- 서명 설명: `client/android/RELEASE_SIGNING.md`.

### 3-3. 앱 — 웹

```bash
cd client
flutter pub get
flutter build web --release \
  --dart-define=API_BASE_URL=https://j15e202.p.ssafy.io/api/v1 \
  --dart-define=KAKAO_JAVASCRIPT_KEY=<카카오 JavaScript 키>
# 결과: client/build/web/  →  서버2 infra/nginx/web/ 에 올린다 (5-5절)
```

- 로컬 개발 실행: `flutter run -d chrome --web-port=3001 --dart-define-from-file=.env`
- 웹은 소셜 로그인과 푸시가 안 된다(안드로이드 전용). 이메일 로그인으로 쓴다.

### 3-4. 수집기·아카이버·Spark·ML 서빙 이미지

서버의 `docker compose ... up -d --build`가 알아서 빌드한다. 손으로 빌드하려면 저장소 루트에서:

```bash
docker build -f collector/Dockerfile -t ddubi/collector:0.1.0 .
docker build -f archiver/Dockerfile  -t ddubi/archiver:0.1.0 .
docker build -f infra/spark/Dockerfile --build-arg SPARK_IMAGE=apache/spark:3.5.3-python3 -t ddubi/spark:0.1.0 .
docker build -f ml-serving/Dockerfile -t ddubi/ml-serving:0.1.0 ml-serving
```

- Spark 잡 코드는 이미지에 넣지 않고 `sparkjobs/`를 붙여서 `sh submit.sh streaming/<잡>.py`로 돌린다. 배치: `docker compose --profile batch --profile spark run --rm spark-batch sh submit.sh batch/<잡>.py`

## 5. 처음부터 배포하기

새 서버 두 대에 처음 올리는 순서다. 이미 돌고 있는 서버는 6절만 보면 된다.

### 5-1. 두 서버 공통 준비

```bash
# 1) 도커·compose, 방화벽 저장 도구 설치 (Ubuntu 24.04)
sudo apt-get update && sudo apt-get install -y ca-certificates curl git python3 iptables-persistent
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker ubuntu        # 다시 로그인

# 2) 소스 받기 (Deploy Token 을 넣은 HTTPS 주소를 쓴다. GitLab SSH 포트가 막혀 있다)
cd ~ && git clone -b develop https://<토큰이름>:<토큰>@lab.ssafy.com/s15-bigdata-dist-sub1/S15P21E202.git
cd ~/S15P21E202/infra

# 3) 환경 파일 만들기 → 4절 표대로 채운다
cp .env.example .env && chmod 600 .env
```

- 방화벽: 도커는 ufw를 우회하므로 스크립트로 막는다.

  ```bash
  sudo sh scripts/firewall.sh 172.26.6.220           # 서버1 에서 (상대 = 서버2)
  sudo sh scripts/firewall.sh 172.26.15.35 --web     # 서버2 에서 (80·443 공개)
  sudo netfilter-persistent save                     # 재부팅 뒤에도 유지
  ```

- 서버 접속용 키는 SSAFY가 준 pem 파일(`J15E202T.pem`)이다.

### 5-2. 서버1 기동 (데이터)

```bash
cd ~/S15P21E202/infra
C="docker compose -f docker-compose.yml -f docker-compose.server1.yml"

$C --profile core up -d                    # 1) Kafka
sh scripts/create-topics.sh                # 2) 토픽 5개 만들기 (처음 한 번. 브로커 자동 생성이 꺼져 있다)
$C --profile hdfs up -d                    # 3) HDFS 네임노드(첫 실행 때 자동 포맷)·데이터노드1
$C --profile core --profile collect --profile spark --profile archive --profile hdfs --profile exporters up -d --build
bash scripts/post-deploy.sh server1        # 4) Kafka·HDFS·컨테이너 상태 확인
```

- 수집기는 키가 비어 있으면 "키 없음"으로 재시작을 반복한다. 4-2절 키를 먼저 채운다.
- Spark는 첫 실행 때 Kafka 커넥터를 인터넷(Maven Central)에서 받는다.
- 서버1 메모리가 빠듯하므로 스왑 4GB를 만들어 둔다(`/swapfile`, swappiness 10).

### 5-3. 서버2 기동 (서비스)

```bash
cd ~/S15P21E202/infra
C="docker compose -f docker-compose.yml -f docker-compose.server2.yml"

mkdir -p nginx/web                          # 1) 웹 폴더를 먼저 만든다 (없으면 / 가 403)
$C --profile data up -d                     # 2) MySQL·Redis
#    (선택) DB 덤프 복원 → 3_DB_덤프/README.md
```

- 백엔드가 처음 뜰 때 Flyway가 V1~V15 스키마를 만든다. 테이블을 손으로 만들 필요가 없다.

### 5-4. HTTPS 인증서 첫 발급 (서버2, 한 번만)

## 6. 평소 배포 (CI 버튼)

1. 기능 브랜치 → 파트 `dev` → 파트 `main` → `develop` 순서로 병합한다.
2. GitLab → 빌드 → 파이프라인에서 **`develop` 파이프라인**을 연다.
3. `deploy-server1`, `deploy-server2` 버튼을 누른다(수동). 바뀐 쪽만 눌러도 된다.

배포 잡이 하는 일:

| 순서 | 서버1 | 서버2 |
|---|---|---|
| 1 | — | CI 변수로 `infra/.env.backend` 생성(권한 600) |
| 2 | `pre-deploy.sh develop` : 서버에서 고친 추적 파일은 `git stash`와 `~/deploy-backup/<시각>/`에 보관 → `git pull --ff-only` | 같음 |
| 3 | `compose up -d --build` (프로필 core, collect, spark, archive, hdfs, exporters) | `compose up -d --build` (프로필 data, serving, hdfs2, monitoring, road-feature) |
| 4 | `post-deploy.sh server1` : Kafka 정상, HDFS 안전 모드 해제, 재시작 반복 컨테이너 확인 | `post-deploy.sh server2` : nginx 설정 검사·reload, Prometheus·Grafana 다시 읽기, 백엔드 정상, `https://도메인/api/health`가 401이면 정상 |

- 배포는 **그 순간의 `develop` 최신**을 받는다. 옛 파이프라인의 버튼을 눌러도 옛 버전으로 돌아가지 않는다.
- 되돌리기는 `develop`에 되돌리기 커밋(`git revert`)을 병합한 뒤 다시 배포한다. 자세한 절차: `docs/runbooks/deploy-rollback.md`.

| `infra/.env` (서버마다), `client/.env` | 4절 표대로 작성 |
| `client/android/app/google-services.json` | Firebase 콘솔 |
| 릴리스 키스토어 `ddubi-release.jks`와 비밀번호 | 팀 보관 (잃으면 같은 앱으로 업데이트 불가) |

### 7-3. 교통 기준 자료 (Git에 있음)
- `backend/transit-master/`의 버스·지하철 마스터와 대응표를 수집기·Spark·백엔드가 읽기 전용으로 붙여 쓴다.
- 대응표 지문(SHA-256)이 compose 기본값과 다르면 **버스 수집기 2개와 Spark 실시간 앱이 기동을 거부**한다. 대응표를 새로 만들면 지문도 함께 바꾼다.
- `.gitattributes`에 `backend/transit-master/**/*.csv binary`가 있다. 지하철 시각표 원본 CSV의 줄바꿈이 바뀌면 지문 검사에 걸려 시각표 생성이 거부되기 때문이다. **서버에서 이 CSV를 다른 편집기로 열어 저장하지 않는다.**

### 7-4. Flyway (DB 스키마)
- 적용된 마이그레이션 파일(V1~V15)은 **고치지 않는다.** 바꿀 것이 있으면 V16부터 새로 추가한다.
- Hibernate는 `ddl-auto: validate`라 스키마를 검사만 한다.
- 코드를 옛 버전으로 되돌려도 DB의 새 표·이력은 지우지 않는다(옛 코드가 새 이력을 모르면 기동을 거부할 수 있어, 되돌리기는 새 커밋으로 한다).

### 7-5. ML 모델 묶음 (서버2)
- Git에 없다. 운영 서버는 `/home/ubuntu/ddubi-models/<버전>/`에 두고 `ML_BUNDLE_DIR`로 가리킨다.
- 설치:
  ```bash
  sha256sum -c SHA256SUMS.txt
  python3 ml-serving/tools/install_bundle.py --archive <묶음.zip> --model <selected_model.joblib> --destination ~/ddubi-models/<새 폴더>
  # .env 의 ML_BUNDLE_DIR 변경 후
  docker compose -f docker-compose.yml -f docker-compose.server2.yml up -d --no-deps --force-recreate ml-serving
  ```
- 참고 데이터에는 지원 날짜 범위가 있다(현재 묶음 2026-09-17~10-10). 기간이 지나면 새 묶음으로 바꾼다. 절차서: `docs/runbooks/ml-bundle-swap.md`.
- 묶음이 없어도 배포는 된다. ML 서빙만 준비 안 됨 상태가 되고, 백엔드는 카카오 시간으로 대신 계산한다.

### 7-6. 버스 과거 참고자료 (서버2)
- DB의 `bus_reference_row`(약 1천만 행, 8GB)는 **덤프에 넣지 않았다.** 필요하면 업로드 도구로 다시 채운다.
  1. `DDUBI_BUS_REFERENCE_FALLBACK_ENABLED=false`로 백엔드를 띄운다.
  2. `python3 infra/scripts/transfer-bus-reference.py <자료 폴더>` 로 파일 전체 검증
  3. `sudo python3 infra/scripts/upload-bus-reference-local.py <자료 폴더> <체크포인트 파일>` 로 적재 (중단되면 같은 명령으로 이어서)
  4. 적재 수가 10,020,903행 / 10,021묶음과 같으면 `DDUBI_BUS_REFERENCE_DATA_VERSION=bus-ref-3e2b388cdbb2beefd3a7b75e`, 기대 수량을 넣고 `FALLBACK_ENABLED=true`
- 자료 폴더는 서버2 `/home/ubuntu/ddubi-stage3-20260917/stage3-bus-export-full/`에 있다. 절차 문서: `docs/transit-stage3-deployment.md`, `docs/contracts/bus-reference-staging.md`.
- 참고자료가 없으면 ML이 실패한 버스 구간은 카카오 시간으로 계산한다(서비스는 된다).

### 7-7. 서버·운영 주의
- **재부팅은 서버2 먼저, 서버1 나중.** 두 대를 동시에 끄지 않는다. 04:10(DB 백업)과 09:30·17:00(브리핑)을 피한다. 절차서: `docs/runbooks/server-reboot.md`.
- 모든 컨테이너가 `restart: unless-stopped`이고 도커 `live-restore`가 켜져 있어, 서버가 켜지면 자동으로 다시 뜬다.
- `kafka-ui`는 기본 배포에서 뺐다(메모리 약 500MB). 필요할 때만 `--profile kafka-ui up -d kafka-ui`.
- `spark-split` 프로필(옛 방식 Spark 앱 4개)은 되돌리기용이다. `spark-streaming-light`와 **동시에 켜지 않는다**(같은 체크포인트).
- 관리 화면은 외부에서 막혀 있으니 SSH 터널로 연다.
  ```bash
  ssh -i J15E202T.pem -L 3000:localhost:3000 ubuntu@j15e202.p.ssafy.io     # Grafana → http://localhost:3000
  ssh -i J15E202T.pem -L 9870:localhost:9870 ubuntu@j15e202a.p.ssafy.io    # HDFS 화면
  ```
- 장애별 절차서는 `docs/runbooks/`에 있다(백엔드 502, HDFS 데이터노드·네임노드, Kafka 재시작, Spark 중단, 인증서 갱신, 모델 교체 등).
