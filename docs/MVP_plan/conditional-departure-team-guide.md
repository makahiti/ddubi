# 조건부 출발시간 추천 — 팀 작업 안내

## 2026-09-17 BE 계약 정정

사용자가 지정한 [카카오맵 공식 도보 문서](https://developers.kakao.com/docs/ko/kakaomap/rest-api#walking)를 기준으로 `GET https://dapi.kakao.com/v2/routing/walk`를 사용한다. 이전 제휴 API·service·priority·default_speed 설명은 이 정정으로 대체한다. REST API 키와 `start_x/start_y/end_x/end_y`, WGS84, `route_mode=SHORTEST`를 사용하며 운영 기본값은 OFF다.

- `durationSource`: `KAKAO_WALKING_API`, `PUBLIC_TRANSIT_STEP`, `PROVIDER_TOTAL_FALLBACK`, `ML_PREVIEW`, `TIMETABLE`. 최종 계산에 사용된 출처를 표시한다.
- `endpointEvidence`: nullable 객체. `verified`, `source`, `masterVersion`, `mappingVersion`, `policyVersion`, `distanceMeters`, `coordinateType`, `judgment`, `reason`을 보존한다. HTTP 실패와 좌표 검증 실패는 구분한다.
- `legRole`: `ACCESS_WALK`, `TRANSFER_WALK`, `EGRESS_WALK`, `RIDE`. 승하차 없는 WALK는 표시상 `ACCESS_WALK`로 정규화하고 `WALK_NO_TRANSIT_ENDPOINT`로 별도 API 호출을 생략한다.
- provider 전체시간 fallback에서는 개별 `segments[].durationSeconds=null`이다. 전체 `durationSeconds`를 구간별로 중복 배분하지 않는다.
- `causes`: `eventId`, `source`, `segmentIds`, `effect`, `confirmed`를 최종 BE 계약으로 유지한다. `effect=BLOCKED|POTENTIAL_IMPACT`이며 `confirmed`는 실제 영향 검증 결과다. FE !147 최신 파서는 이 필드들의 호환 읽기를 지원한다. 확인되지 않은 설명·사건 revision은 만들어 넣지 않는다.

기계 계약과 비어 있지 않은 도보·사건 예제는 `docs/contracts/schedule-evaluation-v2.schema.json`, `docs/contracts/examples/conditional-departure/details/`를 따른다. 상세 검증·DT 소비 조건은 `docs/contracts/conditional-departure-be-runtime.md`에 기록한다.

## 이번에 무엇을 바꾸나요?

지금은 사용자가 입력한 일정 시작시각과 경로의 전체 소요시간을 이용해 출발시각을 단순하게 보여 주는 부분이 있습니다.

이번 작업에서는 사용자가 입력한 출발 계획을 먼저 존중합니다.

예를 들어 사용자가 다음과 같이 입력했다고 가정합니다.

- 출발 계획: 오전 8시 30분
- 일정 시작: 오전 9시

서버는 오전 8시 30분에 출발했을 때의 예상 도착시각을 먼저 계산합니다.

- 오전 8시 59분 도착 예상: 기존 오전 8시 30분 출발을 유지합니다.
- 오전 9시 도착 예상: 일정 10분 전인 오전 8시 50분 도착을 목표로 더 이른 출발시각을 찾습니다.
- 오전 8시 50분까지 도착하기 어려우나 오전 9시 전 도착 가능: “10분 여유는 어렵지만 일정 전 도착 가능”으로 안내합니다.
- 지금 출발해도 오전 9시 이후 도착: 지각 예상으로 안내합니다.

핵심은 앱에서 출발시각을 임의로 계산하지 않고, 서버가 실제 경로·배차·환승·현재 데이터를 이용해 판단하는 것입니다.

최신 설계에서는 출발지에서 첫 버스·지하철을 타는 곳까지와 마지막 하차 지점에서 목적지까지의 도보도 보강합니다. 이 두 구간은 카카오모빌리티의 제휴용 도보 길찾기를 사용합니다. 버스와 지하철 사이의 환승 도보는 기존 대중교통 경로 정보를 유지합니다.

제휴 권한이 없거나 승·하차 좌표를 확실히 확인할 수 없으면 기존 대중교통 도보시간을 사용합니다. 별도 도보시간을 기존 시간에 무조건 더하지 않아야 같은 시간이 두 번 계산되지 않습니다.

## 용어는 이것만 알면 됩니다

| 용어 | 뜻 |
|---|---|
| P | 사용자가 현재 계획한 출발시각 |
| D | 일정 시작시각 |
| T | 일정 시작 10분 전 시각 |
| ETA | 예상 도착시각 |
| PREVIEW | 아직 실제 운영 추천으로 승인되지 않은 검증용 결과 |
| 접근 도보 | 출발지에서 첫 버스·지하철 승차지까지 |
| 환승 도보 | 버스·지하철 사이를 갈아타기 위한 이동 |
| 이탈 도보 | 마지막 하차지에서 최종 목적지까지 |

판단 규칙은 하나입니다.

> P에 출발해서 D보다 일찍 도착하면 그대로 유지하고, D와 같거나 늦게 도착할 때만 T까지 도착할 수 있는 더 이른 출발을 찾습니다.

## 누가 무엇을 맡나요?

### FE 담당

사용자가 보는 Flutter 앱을 맡습니다.

주요 작업:

- 일정 등록·수정 화면에서 출발시각과 일정 시작시각을 정확히 입력받기
- 서버가 계산한 출발시각과 예상 도착시각 표시하기
- 정상 도착, 조기 출발 필요, 10분 여유 부족, 지각 예상, 정보 부족을 서로 다르게 표시하기
- 검증용 결과에는 “검증용” 표시하기
- 검증용 결과를 사용자가 실제 일정에 적용하지 못하게 하기
- 앱에서 `일정 시작시각 - 전체 소요시간`으로 출발시각을 계산하던 로직 제거하기
- 오래된 알림이나 오래된 추천을 적용하지 못하게 하기
- 접근·환승·이탈 도보와 서버가 사용한 도보시간·fallback 상태 표시하기

FE 담당이 만들지 않는 것:

- 출발시간 추천 계산
- 데이터가 부족할 때 임의의 ETA 생성
- 첫 번째 경로라는 이유만으로 “추천 경로” 이름 붙이기
- 직선거리나 고정 보행속도로 도보시간 다시 계산하기

FE가 먼저 받아야 하는 것:

- BE/ML의 응답 예제
- 결과 상태 목록
- 오류 응답 예제
- 검증용 결과와 운영 가능 결과의 차이
- 접근·환승·이탈 도보와 도보 API 적용·fallback 예제

### BE/ML 담당

출발시각 계산, 일정 재평가, API와 모델 연결을 맡습니다.

주요 작업:

- 사용자가 입력한 P와 D 저장·검증하기
- P에서 출발했을 때 모든 경로의 ETA 계산하기
- 필요할 때만 T를 목표로 더 이른 출발시각 탐색하기
- 출발시각이 바뀌면 버스·지하철·환승을 처음부터 다시 계산하기
- FE가 사용할 통일된 응답 형식 제공하기
- 일정 수정 중이거나 오래된 계산 결과는 저장·적용되지 않게 하기
- 사용자가 추천을 직접 수락했을 때만 일정의 출발 계획 변경하기
- ML을 사용할 수 없는 경우 경로 API 값으로 안전하게 돌아가기
- 첫 승차·마지막 하차 좌표를 검증한 뒤 접근·이탈 도보 API 호출하기
- 접근·이탈 도보는 별도 도보 결과로 교체하고 환승 도보는 기존 값 유지하기
- 제휴 권한·호출 제한·장애가 있어도 기존 대중교통 도보시간으로 돌아가기
- 기존 도보시간과 별도 도보시간이 두 번 더해지지 않게 하기
- 검증되지 않은 ML 결과는 PREVIEW로 표시하고 수락 차단하기
- 알림 실패 재시도와 중복 방지를 안전하게 처리하기

BE/ML 담당이 만들지 않는 것:

- 원천 교통 API 수집기
- 근거가 없는 버스·지하철·도로 매핑
- 앱 화면에서 사용할 임의 문구나 시간 계산

BE/ML이 먼저 받아야 하는 것:

- DT의 버스·지하철·도로·날씨 데이터 예제
- 데이터가 생성된 시각과 유효시간
- 매핑 성공·실패 상태
- 데이터와 마스터 버전
- 정류장·역 좌표와 해당 좌표가 정류장, 승강장, 출입구, 역 중심 중 무엇인지에 대한 정보

### DT 담당

교통 원천 데이터를 모으고, 서버와 모델이 사용할 수 있는 형태로 정리하는 작업을 맡습니다.

주요 작업:

- 버스 도착·위치 데이터 수집 및 정규화
- 지하철 도착·위치·운행 알림과 시간표 데이터 정리
- 도로 사고·통제 데이터 정리
- 날씨와 구간별 기준 이동시간 데이터 생성
- 노선·정류장·역·도로를 내부 구간과 안전하게 연결하기
- 공식 정류장·역 좌표의 출처·버전·좌표 의미 정리하기
- 데이터가 언제 생성됐고 언제까지 유효한지 함께 제공하기
- 정상적인 빈 응답, 일부 실패, 전체 실패를 구분하기
- 실제 운행 기록과 예측값을 구분하기
- BE/ML이 바로 읽을 수 있는 예제 데이터와 스키마 제공하기

DT 담당이 만들지 않는 것:

- 사용자에게 보여 줄 최종 추천 문구
- 일정 DB 수정
- 데이터가 없을 때 정상이라고 판단하는 로직
- 이름이 비슷하다는 이유만으로 노선·역·도로를 강제 연결하는 작업
- 카카오 도보 API 호출이나 도보시간 계산

DT가 먼저 받아야 하는 것:

- BE/ML이 실제로 필요한 데이터 필드 목록
- 필요한 노선·역·도로 범위
- 실시간 데이터가 없을 때 허용할 fallback 방식
- 도보 endpoint 검증에 필요한 공식 좌표 범위

## 세 담당자가 먼저 맞춰야 할 것

각자 코드를 많이 작성하기 전에 아래 세 가지부터 합의해야 합니다.

### 1. 서버 응답 예제

BE/ML이 다음 상황의 JSON 예제를 먼저 제공합니다.

- 현재 출발 유지
- 더 일찍 출발 필요
- 10분 여유 확보 불가
- 지각 예상
- 데이터 부족
- 탐색 미완료
- 계산 중·실패·종료

FE는 이 예제로 화면을 만들고, 실제 서버 응답이 같은 형태인지 확인합니다.

### 2. 교통 데이터 예제

DT가 다음 데이터를 키와 개인정보 없이 제공합니다.

- 정상 데이터
- 정상적인 빈 데이터
- 오래된 데이터
- 일부만 받은 데이터
- 호출 실패 데이터
- 매핑 성공·실패 데이터
- 정류장·역 좌표와 좌표 의미가 다른 데이터

BE/ML은 이 예제를 읽는 테스트를 먼저 만듭니다.

### 3. 상태 이름

다음 상태 이름은 세 담당자가 동일하게 사용합니다.

| 상태 | 사용자에게 전달할 의미 |
|---|---|
| KEEP_DEPARTURE | 현재 출발 계획 유지 가능 |
| ADVANCE_DEPARTURE | 더 일찍 출발하면 10분 전 도착 가능 |
| DEPART_NOW | 계획한 출발시각이 지났으므로 지금 가능한 경로 확인 필요 |
| MARGIN_UNAVAILABLE | 10분 여유는 어렵지만 일정 전 도착 가능 |
| LATE_EXPECTED | 일정 시작 이후 도착 예상 |
| DATA_INSUFFICIENT | 판단에 필요한 데이터 부족 |
| ROUTE_UNAVAILABLE | 사용할 수 있는 경로를 찾지 못함 |
| SEARCH_INCOMPLETE | 제한 시간 안에 탐색을 끝내지 못함 |

상태 이름을 바꾸려면 FE, BE/ML, DT 문서를 모두 같이 수정합니다.

## 작업 순서

### 1단계 — 계약 맞추기

- BE/ML: 서버 응답 예제와 상태 목록 제공
- DT: 교통 데이터 예제와 필드 설명 제공
- FE: 모든 응답 상태를 화면에서 표시 가능한지 확인

이 단계가 끝나기 전에 각자 다른 필드 이름을 만들지 않습니다.

### 2단계 — 가장 작은 기능 연결

- BE/ML: P에서 ETA를 계산하고 유지 여부 판단
- FE: 유지·조기 출발·지각 상태 표시
- DT: 기존 데이터로 필요한 입력 제공
- BE/ML: 검증된 승·하차 좌표에서만 접근·이탈 도보 보강

이때는 실제 알림이나 자동 적용까지 한 번에 열지 않습니다.

### 3단계 — 10분 전 도착 탐색

- BE/ML: T를 목표로 이전 출발시각 탐색
- FE: 제안 출발시각과 예상 도착시각 표시
- DT: 출발시각 변화에 따른 버스·지하철 입력이 올바른지 검증
- FE: 접근·환승·이탈 도보와 fallback 상태 표시

### 4단계 — 실시간 변화와 재평가

- 사고·통제·지연 발생 시 관련 일정 다시 계산
- 오래된 결과가 적용되지 않는지 확인
- 데이터 부족과 실제 지각을 구분

### 5단계 — 알림과 운영 활성화

- 알림 중복 방지와 실패 재시도 검증
- PREVIEW 표시와 수락 차단 확인
- 모델과 데이터 품질이 승인된 범위만 실제 추천으로 활성화

## 연동할 때 꼭 확인할 화면과 결과

| 상황 | 기대 결과 |
|---|---|
| 09:00 일정, ETA 08:59:59 | 기존 출발 유지 |
| ETA 09:00:00 | 08:50 도착을 위한 조기 출발 탐색 |
| ETA가 정확히 08:50 | 조기 출발 성공 |
| 08:50은 불가능하지만 08:59 도착 가능 | 10분 여유 부족, 지각 아님 |
| 지금 출발해도 09:05 도착 | 지각 예상 |
| ETA 확인 불가 | 정보 부족 |
| 계산 제한시간 초과 | 탐색 미완료 |
| 일정 수정 중 이전 계산 완료 | 이전 결과 폐기 |
| 오래된 교통 데이터 | 실시간 반영으로 표시하지 않음 |
| PREVIEW 결과 | 화면 표시 가능, 일정 적용 불가 |
| 출발지→첫 승차지 | 접근 도보로 분류하고 올바른 방향으로 도보 조회 |
| 마지막 하차지→목적지 | 이탈 도보로 분류하고 올바른 방향으로 도보 조회 |
| 버스→도보→지하철 | 가운데 도보는 환승 도보로 유지 |
| 승·하차 좌표가 서로 맞지 않음 | 별도 도보 조회 생략, 기존 도보시간 사용 |
| 도보 API 권한 없음·호출 제한·장애 | 전체 경로 실패가 아니라 기존 도보시간으로 fallback |
| 기존 도보와 별도 도보가 모두 있음 | 같은 구간 시간을 한 번만 계산 |

## 작업 완료 보고에 포함할 내용

각 담당자는 “코드 작성 완료”만 보고하지 않고 다음을 함께 전달합니다.

### FE

- 상태별 화면 캡처
- 사용한 서버 응답 예제
- 앱 테스트 결과
- 아직 표시하지 못하는 상태나 필드

### BE/ML

- API 요청·응답 예제
- 정책 경계 테스트 결과
- 모델 사용·fallback·PREVIEW 조건
- 도보 API 적용 범위·좌표 검증·중복 방지·fallback 결과
- DB 변경 내용
- 오래된 결과와 중복 알림 방지 테스트 결과

### DT

- source별 정상·빈 응답·실패 예제
- 필드와 단위 설명
- 매핑 성공률과 실패 이유
- 정류장·역 좌표의 출처·버전·좌표 의미와 누락 현황
- 데이터 생성시각·유효시간·버전
- 수집 성공·부분 실패·실패 건수

## 최종 완료 기준

다음 조건을 모두 만족해야 전체 연동 완료입니다.

- 앱과 서버가 동일한 P, D, ETA와 결과 상태를 표시합니다.
- 앱이 출발시각을 자체 계산하지 않습니다.
- 출발시각을 바꾸면 전체 경로와 환승이 다시 계산됩니다.
- 오래된 계산 결과를 저장하거나 수락할 수 없습니다.
- 데이터가 부족한 상황을 지각이나 정상으로 잘못 표시하지 않습니다.
- 검증용 ML 결과를 실제 일정에 적용할 수 없습니다.
- 수집 데이터의 시각·버전·매핑 상태를 서버가 확인할 수 있습니다.
- 접근·이탈 도보는 검증된 좌표에서만 적용되고 환승 도보와 중복 계산되지 않습니다.
- 제휴 도보 기능을 사용할 수 없어도 기존 대중교통 경로가 유지됩니다.
- PM 로컬 통합 환경에서 같은 예제로 FE, BE/ML, DT 결과가 일치합니다.
