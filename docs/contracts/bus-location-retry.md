# 버스 위치 수집 실패 후 재시도

## 문제와 원인

사용자 보고: 06:19 bus_location 호출 실패 후 다음 시도가 14:19로 밀림.
저장소에서 확인한 구조:

1. API 호출 전에 SQLite cycles에 다음 시각(+8시간)을 선점하므로 실패해도 cooldown이 유지된다.
2. BusLocationError를 일반 RuntimeError로 바꿔 main의 HTTP 예외 재시도 대상에서 빠진다.
3. 노선 하나 실패 시 전체 노선 조회가 중단된다. 먼저 읽은 일부 노선도 이 사이클에서는 발행되지 않는다.
4. 기존 어댑터는 예외 종류만 남겨 HTTP 상태·원천 코드·실패 노선을 진단하기 어렵다.

이는 **실패 후 장시간 복구하지 못하는 이유**다. 최초 API 호출 실패의 직접 원인(네트워크, 인증, 서버, 한도)은
운영 로그/응답이 없어 확정하지 못했다. 이번 변경은 안전한 노선·HTTP 상태·원천 코드·통신 예외 종류를 보존한다.
인증키가 포함된 URL, HTTP 예외 원문이나 원천 응답의 메시지를 로그에 넣지 않는다.

## 변경 후 동작

```text
06:19 정기 조회 → 타임아웃/연결 실패/HTTP 408 또는 5xx
       ↓
실패 처리 완료 후 5분 뒤 재시도 예약
       ↓
재시도 성공: 새 관측 발행 / 재시도 실패: 추가 재시도 없음
       ↓
원래 정기 조회 시각(예: 14:19)에 다시 조회
```

시각은 예시이고 5분은 실제 실패 처리 시각 기준이다. 재시도가 오래 걸려 다음 정기 시각을 넘기면
기존 선점 규칙으로 다음 정기 사이클을 처리한다. 횟수는 **정기 사이클당 최대 한 번**이며 bus_location만 적용한다.
bus_arrival과 다른 소스의 기존 주기는 유지한다. run_once 수동 점검은 지연 재시도를 예약하지 않는다.
단독 JSON CLI는 즉시 조회 도구이므로 5분 재시도는 장기 실행 Collector에서만 동작한다.

인증·호출 한도 응답, HTTP 401/403/429, JSON/계약/설정 오류는 이번 정책의 지연 재시도 대상이 아니다.
판별되지 않은 원천 오류를 일시적 장애로 추측하지 않는다.

## 재시도와 예산

cycle_retries 테이블에 예약 시각과 사용 여부를 저장한다. 정상 주기 deadline은 유지한다.
동시 프로세스가 재시도를 선점해도 한 프로세스만 실행한다. 재시작 뒤 예약 시각 전이면 남은 시간만 기다린다.
실제 재시도 선점 후 프로세스가 죽으면 같은 사이클에서 다시 재시도하지 않는다. 이는 호출 폭주 방어를 우선한 선택이다.

예약 전에 전체 노선 재조회 비용이 최근 24시간 잔여 예산 안에 들어가는지 확인한다.
재시도 시작 때도 확인하며, 다른 수집기와 경쟁해 예산이 줄면 각 HTTP 직전의 기존 SQLite 한도 검사가 차단한다.
실패 요청도 호출로 차감하고 환불하지 않는다. 기존 API_DAILY_LIMIT(예제 900)은 올리지 않았다.

README의 약 600회는 기본 노선 100개×하루 3사이클×위치·도착 두 종류의 **정상 호출량 추정치**다.
실제 허용 한도는 운영 API_DAILY_LIMIT과 제공자 제한이며 같은 인증키를 사용하는 다른 소스·리다이렉트도 포함한다.
실제 한도가 600이고 여유가 없으면 재시도를 실행하지 않는다.

이번 재시도는 실패 노선 하나만 이어 받는 방식이 아니라 **전체 위치 사이클 재조회**다.
노선 100개라면 재시도에 최대 100개 원 요청 및 발생한 리다이렉트 비용이 추가될 수 있다.
부분 성공 발행·실패 노선만 복구하는 최적화는 이번에 변경하지 않았다.

## 오래된 Redis 값에 대한 주의

기존 위치 최신 기록은 TTL 86,400초로 보존될 수 있지만 Spark가 부여하는 validUntil/freshnessSeconds는 120초다.
키가 존재한다는 것만으로 현재 유효한 위치라고 판단해서는 안 된다. validUntil이 지난 값은 stale/unknown 또는 fallback으로 처리해야 한다.
이번 변경은 TTL과 기존 유효기간을 늘리거나 실패 때 옛 값의 시각을 갱신하지 않는다.
실제 서비스/대시보드가 오래된 위치를 현재값으로 표시하는지는 운영 소비 경로를 별도로 확인해야 한다.

## 검증과 적용

`python -m unittest discover -s collector/tests -p test_bus_retry.py -v`

지연 재시도 6개 테스트: 5분 대기, 재시작 복구, 정상 deadline 유지, 한 번 제한, 예산 부족·요청 차감,
동시 선점, 실제 HTTP fixture 실패→성공, 재실패, 오류 분류·키 미노출을 검증했다.
기존 버스 위치·도착 및 지하철 회귀 테스트도 실행했다. 버스 16개 + 지하철 26개 총 42개 통과.
전체 bus 패턴 실행에는 별도 crosswalk 테스트의 pytest 미설치로 import 실패가 있어 전체 테스트 통과라고 보고하지 않는다.
main 장기 실행 및 운영 Kafka/API 재현은 아직 수행하지 못했다.

새 환경변수는 필요 없다. 수정 코드 배포 후 서버1 infra 디렉터리에서 Collector 이미지를 다시 빌드하고 재생성한다.

```sh
docker compose -f docker-compose.yml -f docker-compose.server1.yml --profile collect up -d --build --force-recreate collector-bus-location
docker logs collector-bus-location --since 1h 2>&1 | grep -E 'cycle|retry|노선=|HTTP'
```

기존 호출 예산 DB·Kafka·원본을 삭제하지 않는다. 새 테이블은 CREATE TABLE IF NOT EXISTS로 생성한다.
예약 실패 또는 비대상 오류는 원인을 포함한 cycle failed로 기록하며 정기 시각에 다시 시도한다.
현재는 로컬 구현·검증 완료이며 운영 배포·실제 API 장애 원인 확정은 미완료다.
