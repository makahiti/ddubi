## 1. 교통수단 선호 — 세 곳이 서로 다릅니다 🔴

| 위치 | 선택지 | 방식 |
| --- | --- | --- |
| 일정 등록 (`screens.dart:616`) | 지하철 우선 / 버스+지하철 / 버스 우선 | 단일 선택 |
| 마이페이지 (`screens.dart:2357`) | 버스 / 지하철 / 도보 / 택시 | 단일 선택 (`int selected`) |
| **DB·API** | `BUS`·`SUBWAY` × `PREFER`·`AVOID` | **다중 행** |

> 참고: 마이페이지가 체크박스처럼 보이지만 코드는 `selected = i` 라 실제로는 하나만
> 선택됩니다. 다중 선택 의도였다면 그것도 버그입니다.

### 백엔드 의견

**도보·택시는 빼는 것을 제안합니다.**

- **도보**는 선호 대상이 아닙니다. 모든 대중교통 경로가 도보로 시작해 도보로 끝나므로,
  "도보 선호"를 골라도 추천 로직이 반영할 것이 없습니다.
- **택시**는 서비스 범위 밖입니다. 실시간 구간 상태도 기준선(baseline)도 대중교통만
  수집합니다. 택시를 넣으면 추천 근거가 없는 선택지가 생깁니다.

**일정별 교통수단 선호는 화면에서 빼는 것을 제안합니다.**

`schedule` 테이블에 저장할 컬럼이 없습니다. 넣으려면 ERD·마이그레이션 변경이 필요한데,
"출근은 지하철, 약속은 버스"를 매번 고르게 하는 것이 사용자에게 값어치가 있는지
의문입니다. 사용자 설정 한 번이면 충분해 보입니다.

**필요하다고 판단되면 말씀 주세요.** 컬럼 추가는 가능하고, 다만 ERD·마이그레이션·
Notion ERD_master 를 함께 고쳐야 합니다.

### 제안하는 최종 형태 (마이페이지 한 곳)

```
교통수단 선호
  버스     [ 선호 | 상관없음 | 회피 ]
  지하철   [ 선호 | 상관없음 | 회피 ]
```

"상관없음" = 해당 수단의 행을 보내지 않음. 현재 API 가 그대로 받습니다.

```json
PATCH /users/me
{ "transportPrefs": [
    { "mode": "SUBWAY", "preference": "PREFER" },
    { "mode": "BUS",    "preference": "AVOID"  }
] }
```

현재 일정 등록 화면의 3지선다도 이 두 행으로 정확히 표현됩니다.

| 화면 선택 | 보낼 값 |
| --- | --- |
| 지하철 우선 | `SUBWAY:PREFER` |
| 버스 + 지하철 | (행 없음 — 둘 다 상관없음) |
| 버스 우선 | `BUS:PREFER` |

**결정 필요**: ① 도보·택시 제외 여부 ② 일정별 선호 유지 여부

## ✅ 1번 결론 (2026-09-08, ML 연동안 확정)

**교통수단 선호는 서비스에서 쓰지 않습니다.** 위에서 제안했던 "도보·택시 제외 / 마이페이지
한 곳" 안은 더 이상 유효하지 않습니다.

ML 연동안 §7 에서 후보 비교 순서가 이렇게 확정됐고, 선호·회피 가중치가 빠졌습니다.

```
탑승 가능 → 약속시간 내 도착 가능 → 지연 위험 → 예상시간 → 과도한 환승·도보 → 데이터 신뢰도
```

### 프론트가 할 일

- **마이페이지의 교통수단 선호 UI 를 빼 주세요** (`screens.dart:2357` 부근)
- **일정 등록의 3지선다도 빼 주세요** (`screens.dart:616` 부근)
- `PATCH /users/me` 의 `transportPrefs` 는 **보내지 않아도 됩니다**

### 백엔드는 지우지 않습니다

`user_transport_pref` 테이블과 `transportPrefs` API 는 **그대로 둡니다.** 다만 추천이
읽지 않습니다.

지우지 않는 이유: 이미 동작하고 프론트가 붙어 있어서, 데모를 앞두고 걷어내면 회귀 위험만
생깁니다. 값을 보내도 저장될 뿐 추천 결과는 달라지지 않습니다. 정책이 되살아나면 그대로
쓸 수 있습니다.

> 함께 바뀐 것: **일정 중요도(`importance`)도 추천 여유시간을 바꾸지 않습니다.**
> 예전에는 `NORMAL=p50 / HIGH=p80 / CRITICAL=p95` 로 출발 시각이 달라졌는데,
> 지금은 모두 같은 안전 여유를 쓰고 중요도는 **감시·재계산·알림 빈도**에만 씁니다.
> 필드는 그대로이니 **프론트 변경은 없습니다.**
## 2. `importance` 타입이 다릅니다 🟡

| | 값 |
| --- | --- |
| 프론트 | `int` — `0`(일반) / `1`(중요) / `2`(절대 지각 불가) |
| API | `String` — `"NORMAL"` / `"HIGH"` / `"CRITICAL"` |

숫자를 그대로 보내면 `400 INVALID_REQUEST` 입니다.

**백엔드는 문자열을 유지하겠습니다.** 이 값이 추천 백분위를 결정하는데
(`NORMAL=p50 / HIGH=p80 / CRITICAL=p95`), 숫자로 두면 로그와 DB 에서 `2` 가 무엇인지
읽히지 않습니다. 나중에 등급을 추가할 때 숫자 순서에 갇히지도 않습니다.

**프론트에서 변환 부탁드립니다.**

```dart
const _importance = ['NORMAL', 'HIGH', 'CRITICAL'];
// 전송: _importance[importance]
// 수신: _importance.indexOf(json['importance'])
```

## 3. 좌표가 없습니다 🔴

프론트 모델(`models.dart:19-20`)은 출발지·목적지가 **문자열 하나**입니다.

```dart
final String place, departurePlace;   // "잠실야구장"
```

API 는 **이름 + 좌표**를 요구합니다. 좌표 없이는 경로 탐색 자체가 불가능합니다.

```json
POST /schedules
{
  "origin":      { "name": "강남역", "lat": 37.4979526, "lng": 127.0276241 },
  "destination": { "name": "잠실야구장", "lat": 37.5121, "lng": 127.0719 },
  "arriveBy": "2026-09-10T19:00:00"
}
```

### 좌표를 얻는 방법 — 이미 API 가 있습니다

`PLACE-001 GET /places/search?query=잠실야구장` 이 카카오 장소 검색을 프록시합니다.
서울 밖 결과는 애초에 오지 않습니다.

```json
{ "content": [
    { "providerPlaceId": "18577297", "name": "잠실야구장",
      "address": "서울 송파구 올림픽로 25", "lat": 37.5121, "lng": 127.0719 }
] }
```

**등록 화면의 "도착지 검색" 입력칸을 자유 입력이 아니라 검색 → 선택 방식으로**
바꿔 주셔야 합니다. 선택한 항목의 `name/lat/lng` 를 그대로 실어 보내면 됩니다.

즐겨찾기(`PLACE-002~006`)도 구현돼 있어 "집·회사" 를 저장해두고 고르는 흐름도 가능합니다.

> 서울 밖 좌표는 `422 OUT_OF_SERVICE_AREA` 로 거절합니다. 검색 API 를 거치면
> 자연히 서울 안 좌표만 오므로 이 오류를 볼 일이 없습니다.

## 4. 화면에 없는 필드 · 화면이 못 쓰는 필드 🟡

### 4-1. `considerLastTrip`(막차 고려) 입력이 없습니다

API 가 받는 선택 필드인데 UI 가 없습니다(코드 전체 검색 결과 `막차`·`lastTrip` 없음).
막차 위험 경고(F-12)의 대상 여부를 정하는 값입니다.

- **쓸 것이면** 등록·수정 화면에 토글 하나를 넣어 주세요.
- **안 쓸 것이면** 알려 주세요. 명세서와 ERD 에서 정리하겠습니다.

안 보내면 `false` 로 저장되므로 지금 당장 요청이 실패하지는 않습니다.

### 4-2. 일정 수정 화면이 없습니다 — 있게 되면 `updatedAt` 이 필요합니다

라우터에 수정 경로가 없고 `updatedAt` 을 보관하는 코드도 없습니다.
`SCH-004 PATCH /schedules/{id}` 는 **`updatedAt` 이 필수**입니다.

```json
PATCH /schedules/12
{ "title": "변경된 제목", "updatedAt": "2026-09-03T09:14:22.123456" }
```

조회 응답의 `updatedAt` 을 그대로 되돌려 보내야 합니다. 그 사이 다른 기기가 수정했으면
`409 INVALID_STATE` 가 납니다 — **두 기기에서 동시에 고칠 때 한쪽 수정이 조용히
사라지는 것을 막는 장치**입니다. 사용자에게는 "새로 고침 후 다시 시도" 를 안내해 주세요.

즉 **일정 조회 응답을 화면에 들고 있을 때 `updatedAt` 을 버리지 말아 주세요.**

## 참고 — 잘 맞는 것

반복 일정은 손댈 것이 없습니다.

| 프론트 | API |
| --- | --- |
| `startDate` | `startDate` ✅ |
| `untilDate` | `endDate` ✅ |
| `weekdays: Set<int>` | `rrule: "FREQ=WEEKLY;BYDAY=MO,TU,..."` (변환만) |

요일 변환 표 (`DateTime.monday == 1`):

```dart
const _byday = ['MO','TU','WE','TH','FR','SA','SU'];
final rrule = 'FREQ=WEEKLY;BYDAY=${weekdays.map((d) => _byday[d-1]).join(",")}';
```

**주간 반복만 지원합니다.** 격주(`INTERVAL=2`)나 월간(`FREQ=MONTHLY`)을 보내면 400 입니다.
필요해지면 말씀 주세요.

반복 생성 응답으로 `generatedScheduleCount`(즉시 만들어진 인스턴스 수)와
`nextOccurrenceAt` 이 옵니다. "14일치 일정이 등록되었습니다" 같은 안내에 쓰시면 됩니다.

## 요청

1번(교통수단)만 **기획 결정**이 필요하고 나머지 셋은 프론트 구현 사항입니다.

등록이 아예 안 되므로 거기가 먼저입니다.
