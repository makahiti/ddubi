# segment_id 계약 — 분산·수집팀 협의 안건

작성: 백엔드(서비스) 손정민 · 관련: 안건 B-1, Jira S15P21E202-21, `kakao-public-transit-route.md`

---

## 0. 왜 이 문서가 필요한가

카카오 대중교통 API 연동은 끝났지만 **`segment_id`가 전부 `null`** 이다.
`UnresolvedSegmentIdResolver`가 항상 빈 값을 반환한다.

그 결과 아래가 **동작하지 않는다**:

- **F-05 영향 일정 역조회** — 구간 지연 → 영향받는 일정 찾기
- **실시간 재평가** — Redis `segment:status:{segmentId}` 조회 대상이 없음
- **baseline 폴백** — `baseline_serving.segment_id` 매칭 불가

즉 **뚜비의 분산 파이프라인이 서비스에 연결되지 않은 상태**다. Phase 3 전체가 여기서 막힌다.

## 1. 역할 경계 (먼저 합의)

| 담당 | 범위 |
| --- | --- |
| **분산·수집팀** | `segment_id` **채번 규칙 확정**, 정류장·노선 마스터 적재, Spark 계산 단위 결정, Redis 값 스키마 |
| **백엔드(서비스)** | 확정된 규칙대로 카카오 응답을 조립해 `route_segment`에 저장, 역조회 쿼리, 추천 계산, 프론트 서빙 |

**핵심**: "`segment_id`가 무엇이냐"는 분산팀이 정한다. 백엔드는 그 규칙을 구현하는 쪽이다.
백엔드가 임의로 정하면 Spark·수집기와 어긋나 파이프라인이 성립하지 않는다.

## 2. 문제의 구조

```
카카오 응답     "66"(마을) · "판교역서편" · "국가기록원"     ← 이름만, ID 없음
공공데이터      노선ID · 정류장ID · 역코드                    ← 수집기가 쓰는 것
                              ↑
                    이 사이를 잇는 규칙이 없다
```

카카오 실제 응답에서 확인된 사실:

| 항목 | 제공 |
| --- | --- |
| 정류장/역 이름 | O |
| 정류장 좌표 | **X** |
| 정류장 ID | **X** |
| 노선 이름·종류 | O (`66` / `마을`) |
| 노선 ID | **X** |
| 경로 폴리라인 | O (정류장 좌표 아님) |
| 노선이 복수로 오는 경우 | 있음 — `"332외 2대"` |

## 3. 백엔드 제안 (검토 대상)

서울 한정 서비스이므로 서울시 공개 마스터로 매칭이 가능하다고 본다.

### 3.1 형식

```
버스     BUS:{출발정류장ID}:{도착정류장ID}
지하철   SUB:{호선}:{출발역코드}:{도착역코드}
도보     NULL
```

예: `BUS:23001:23002` (15자) · `SUB:2:0221:0222` (15자) — `VARCHAR(50)` 여유 충분.

### 3.2 버스는 노선을 빼자

카카오가 `"332외 2대"`처럼 노선을 하나로 특정하지 않는 경우가 있다.
**같은 정류장 구간을 달리는 버스는 같은 도로를 달리므로** 노선별로 나눌 실익이 적다.

- `"332외 2대"` 문제가 자동 해결
- `route_segment.segment_id` 컬럼 1개 제약 유지 → **ERD 변경 불필요**
- Spark 계산 대상 축소 (노선×구간 → 구간)
- 여러 노선의 실측이 한 구간에 모여 표본 증가

지하철은 노선이 곧 물리 선로이므로 호선을 유지한다.

### 3.3 구간 단위는 인접 쌍

승하차 조합을 다 계산하면 노선당 약 5천 조합 × 600노선 ≈ 300만.
인접 쌍이면 100 × 600 = 6만. **인접 단위가 사실상 유일한 선택.**

### 3.4 매칭 방법

```
1) 노선명 + 종류로 후보 노선 조회
2) 그 후보 중 출발·도착 정류장명을 모두 경유하고 순서가 맞는 노선 선택
3) 해당 노선의 정류장 목록에서 정류장ID 확보
```

"66번 버스"는 여럿일 수 있어도 **"판교역서편 다음에 국가기록원을 지나는 66번"은 하나**다.
노선 컨텍스트가 동명 정류장 모호성을 제거한다.

### 3.5 필요한 마스터 (전부 공개 데이터)

| 데이터 | 출처 |
| --- | --- |
| 버스정류소 위치정보 (정류소ID, ARS번호, 이름, 좌표) | 서울 열린데이터광장 OA-15067 |
| 버스 노선 정보 / 노선별 경유 정류소 순서 | 서울 열린데이터광장 OA-1095 |
| 역사마스터 (역코드, 호선, 역명) · 1~8호선 좌표 | 서울 열린데이터광장 OA-21232 / 공공데이터포털 |

정적 데이터라 1회 적재 후 주기 갱신이면 충분하다.

## 4. 결정이 필요한 안건

### D-1. 버스 정류장 ID 종류 **[최우선]**

| 후보 | 예시 | 비고 |
| --- | --- | --- |
| ARS번호 | `23001` | 5자리, 서울시 버스도착 API가 `arsId`로 받음 |
| 정류소ID(NODE_ID) | `100000001` | 시스템 고유키, 더 안정적 |

**결정 기준**: 수집기가 Kafka 이벤트에 싣는 키와 **같아야 한다.**
→ 수집 담당이 답변하면 끝나는 안건.

### D-2. 지하철 역코드 종류 **[최우선]**

역코드(`0222`) vs 역외부코드/역번호(`222`).
**결정 기준**: 실시간 지하철 도착 API가 받는 값.

### D-3. Spark 계산 단위 = 정류장 구간(노선 무관)?

3.2의 전제. 분산팀이 "노선별로 나눠야 한다"고 판단하면 형식이 바뀌고
`route_segment.segment_id` 컬럼 1개로 복수 노선을 담을 수 없어 **ERD 변경 안건**이 된다.

### D-4. 마스터 테이블 소유·적재 주체

정류장·노선·역사 마스터 3~4개 테이블이 **현재 ERD에 없다.** 신규 안건.
공공 API를 이미 호출하는 **수집 담당**이 자연스럽다고 본다.

### D-5. 카카오 이름 → 공공 ID 매칭 구현 주체

3.4의 매칭 로직을 누가 구현하나.

- 백엔드가 구현: 마스터 테이블 읽기 권한 필요
- 분산팀이 매핑 API/테이블 제공: 백엔드는 조회만

백엔드 선호: **분산팀이 매핑을 제공**하고 백엔드는 `SegmentIdResolver` 구현체로 조회만 하는 쪽.
채번 규칙과 매칭이 같은 팀에 있어야 어긋나지 않는다.

### D-6. 매칭 실패 시 동작

100% 매칭은 불가능하다(신설 정류장, 표기 차이).

백엔드 제안: `segment_id = null` → 해당 구간은 실시간·baseline 없이 카카오 기본값 사용
→ `recommendation.confidence` 하향 (도메인 규칙 8 폴백과 연결).
후보의 몇 % 이상 실패 시 후보를 버릴지도 정해야 한다.

### D-7. 버스 경유 정류장

카카오 지하철 응답은 경유역을 준다(`판교 → 성남 → 이매`).
**버스도 경유 정류장을 주는지 실제 응답 확인 필요.**
안 주면 마스터의 노선별 정류소 순서로 승차~하차 사이를 채워야 한다.

### D-8. 단위 — 초 vs 분

현재 혼용 상태다.

| 대상 | 단위 |
| --- | --- |
| 카카오 응답 · 내부 모델 | 초 / m |
| `baseline_serving.p50/p80/p95` | **초** |
| `route.base_duration_min`, `route_segment.base_duration_min` | **분** |

재평가 엔진이 이 둘을 섞어 계산하므로 오차가 누적된다.

**백엔드 제안**: DB도 초로 통일 (`base_duration_min` → `base_duration_sec`).
`recommendation.duration_min`·`buffer_min`은 사용자 표시값이므로 분 유지, 반올림은 최종 1회만.
→ ERD 2컬럼 변경. 지금은 데이터가 0건이라 비용이 가장 낮다.

### D-9. 서울 외 좌표

서울 한정 서비스이므로 출발·도착이 서울 밖이면 `422 OUT_OF_SERVICE_AREA`로 거부.
(`ErrorCode`에 이미 존재, `/places/search`도 같은 정책)
경계 판정 기준(행정구역 코드 / 좌표 범위)을 정해야 한다.

## 5. 백엔드가 이미 준비해둔 것

결정만 나면 바로 붙는다.

- `route_segment.segment_id VARCHAR(50)` + `IX_RSEG_SEGMENT` 인덱스
- `SegmentIdResolver` 인터페이스 — 구현체만 교체하면 됨
- F-05 역조회 쿼리 경로 (`segment_id → route_segment → route.is_selected → schedule.status`)
- `ErrorCode.OUT_OF_SERVICE_AREA`, `ROUTE_PROVIDER_UNAVAILABLE`
- Redis 키 계약 `segment:status:{segmentId}` (`docs/contracts/redis-keys.yaml`)

## 6. 우선순위 제안

**지하철 먼저.**

| | 지하철 | 버스 |
| --- | --- | --- |
| 노선 수 | ~20 | ~600 |
| 역명 유일성 | 높음 | 낮음 |
| 카카오가 경유 지점 제공 | O | 확인 필요 |
| 노선 복수 문제 | 없음 | 있음 |

지하철만으로도 **"2호선 지연 → 영향 일정 재계산 → 알림"** 시연이 성립한다.
분산 파이프라인의 가치를 보여주는 데 충분하고, 버스는 여유가 생기면 붙인다.

## 7. 최소 합의 사항

시간이 없으면 이 두 줄만 정해도 백엔드는 진행할 수 있다.

> 수집기가 Kafka 이벤트에 싣는 **버스 정류장 키**와 **지하철 역 키**가 각각 무엇인가.
> 그 값을 `BUS:{A}:{B}` / `SUB:{호선}:{A}:{B}` 형식으로 조립해 쓰는 데 동의하는가.

나머지(마스터 적재, 이름 매칭 구현)는 구현 문제이며 계약이 정해진 뒤 병행할 수 있다.

## 8. 결정 기한

Phase 2(장소·일정) 종료 전까지. Phase 3(경로·추천)이 전부 이 계약 위에 올라간다.
