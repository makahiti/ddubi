## 1. 전체 계산의 목적과 현재 범위

카카오가 출발지·목적지에 대한 대중교통 경로 후보를 만든다. DDUBI는 후보의 노선·승하차지와 순서를 유지하면서 각 구성요소의 시간을 재평가한다. 새로운 전체 교통망 최단경로를 직접 탐색하는 작업이 아니다.

| 구성요소 | 결정한 계산 방향 | 왜 이 방식인가 | 기준 코드의 상태 |
|---|---|---|---|
| 접근·이탈 도보 | 카카오 도보시간을 기초로 횡단보도 신호 계획 여유를 별도 표시 | 실제 보행 경로를 확보하고, 첫 승차지 도착과 마지막 하차 후 이동을 구분하기 위해 | 일반 WALK는 제공자 시간을 유지. 도보 API 별도 연결·P90 보정은 미반영 |
| 버스 탑승 | 매핑된 인접 정류장 구간의 ML 예측 합 | 같은 노선도 구간·시간대별 소요시간이 다르기 때문 | 검증용 HTTP 예측·step 단위 교체 구현 |
| 지하철 탑승 | 같은 운행의 하차역 도착−승차역 출발 | 중간 정차와 해당 운행 패턴을 반영하기 위해 | 시간표·실시간 보조 계산 구현. 별도 9월 인덱스 자료와 런타임 형식은 다름 |
| 환승 이동 | 카카오의 해당 환승 walking 시간 유지 | 경로 제공자가 지정한 환승 동선 시간을 유지하기 위해 | WALK 시간 유지. 이전 로컬의 별도 환승 보정은 이번 기준 코드·MR에 포함하지 않음 |
| 버스 승차대기 | 초기 정책은 `0.6 × 배차간격` | 먼 미래 일정에 현재 ETA를 재사용하기 어렵고, 검증된 장기 이력이 부족하기 때문 | **정책만 결정. 현재 BusWaitingService는 실시간 ETA 사용** |
| 지하철 승차대기 | 승강장 도착 이후 이용 가능한 기준 운행까지의 시간 차이 | 앞선 도보·환승·탑승시간을 반영해야 하기 때문 | 시간표/유효한 실시간 도착으로 계산, 전체 반영에는 시간 분해 검증 필요 |
| 첫차·막차 | 승차 위치·운행일 기준으로 판단 | 노선 기점 시각과 중간 승차지 시각이 다르기 때문 | 일부 시간표 후보 배제는 있으나 전체 서비스의 운행 가능 판정은 후속 과제 |

위 표의 선택 이유가 실제 예측 정확도 향상을 측정했다는 뜻은 아니다. 버스 ML은 시간대별 구간 **평균 소요시간**을 예측하며 개별 차량의 실측시간이나 분위수 예측이 아니다. 도보 P90도 사용자의 실제 대기시간 P90과 구분한다.

기존 [ML 데이터 결정](ml-data-decision.md), [실시간 대기 계약](transit-waiting.md), [지하철 계약](subway-timing.md)은 현재 구현의 참고 근거다. 이 문서의 새 정책은 해당 실행 계약을 이미 변경했다는 뜻이 아니다. 특히 기존 실시간 대기 계약의 가상 배차 생성 금지와 새로운 사전 통계 대기를 한 실행 경로로 혼합하지 않는다.

## 2. 공통 입력·시간·ID 규칙

| 기호 | 의미 |
|---|---|
| \(t_0\) | 사용자의 출발 예정시각 |
| \(a\) | 계산 기준시각 `asOf`. 이 시각까지 확보한 정보만 사용 |
| \(t_i\) | 경로 구성요소 i의 진입 예정시각 |
| \(C_i(t_i)\) | 그 시각의 구성요소 소요시간, 초 |
| \(D\) | 일정의 도착 희망시각 |
| \(H\) | 적용할 노선의 배차간격. 분/초 단위를 명시 |
| \(W\) | 승차지 도착부터 탑승까지의 대기시간 |

정보 기준시각은 사용자 출발시각과 다르다. 예를 들어 API가 07:59에 만든 예측에서 남은 180초라면 도착예정은 08:02다. 08:00에 조회했다고 08:03으로 밀지 않는다. ETA는 Estimated Time of Arrival, 도착예정시각을 뜻한다.

내부 canonical `segmentId`, 제공자 노선/정류장 ID, 카카오 ID, 정류장 ARS 번호를 구분한다. 문자열 ID의 선행 0을 보존한다. 노선·방향·정류장 순번·반복 방문·마스터 버전을 확인하고, 미매핑 상태에서 이름을 이어 붙인 임의 ID를 만들지 않는다.

전체 진행은 다음 순서로 계산한다.

\[
t_{i+1}=t_i+C_i(t_i),\qquad T_{route}(t_0)=t_n-t_0
\]

따라서 지하철 뒤 버스로 환승할 때 버스 정류장 도착시각은 출발시각에 **앞선 도보·대기·탑승·환승 전부**를 더한 값이다. 모든 구간에 사용자 출발시각의 시간대를 일괄 넣지 않는다.

## 3. 도보시간과 횡단보도 신호 계획 여유

### 3.1 카카오 도보 경로를 선택한 이유

대중교통 전체시간에서 탑승·환승 시간을 빼 남은 시간을 얻더라도 출발지→승차지와 하차지→목적지의 비중은 확정할 수 없다. 첫 승차지 도착시각을 계산하려면 접근 도보를 따로 알아야 한다. 카카오 도보 응답은 경로점·거리·step 시간·횡단보도 안내를 제공하는 입력 후보다. [카카오 도보 REST 문서](https://developers.kakao.com/docs/ko/kakaomap/rest-api#walking)

현재 기준 코드의 [RouteEvidenceAssembler](../../backend/src/main/java/com/ssafy/ddubi/domain/recommendation/evaluation/RouteEvidenceAssembler.java)는 WALK의 `durationSeconds`를 유지한다. 별도 도보 API 호출과 횡단보도 보정은 구현 완료 항목이 아니다. 거리/1.2m/s를 일반 도보의 확정 계산식으로 추가하지 않는다.

### 3.2 길이 기반 경험식을 만든 과정

모든 경로의 횡단보도를 신호 시설·시간대별 신호표에 완전히 대응하는 자료를 확보하지 못했다. 반면 공개 시설 자료에는 횡단보도 연장과 적색신호시간이 함께 있어, 길이로 긴 신호 1회에 대한 계획 여유를 추정하는 실험을 했다. 길이만으로 실제 적색시간이 결정된다는 전제는 아니다.

원천은 [전국횡단보도표준데이터](https://www.data.go.kr/data/15028201/standard.do)의 2026-09-14 확보분이다. 원본 50,000행→신호등 존재·길이/녹색/적색 양수 6,416행→길이 100m/적색 600초 초과 제외 6,410행→동일 시설 중복 제거 6,299행→수도권 4,644행을 사용했다. 이 경계는 분석용 필터이며 법정 상한이 아니다. 확보분은 전국 전수나 무작위 표본이 아니다.

적색시간 \(R_i\), 길이 \(L_i\), 오차 \(e_i=R_i-(b_0+b_1L_i)\)에 대해 다음 P90 손실을 최소화했다.

\[
\mathcal L_{0.9}=\frac1n\sum_i\max(0.9e_i,-0.1e_i)
\]

기울기 −10~10초/m를 0.05 간격으로 탐색하고, 각 기울기에서 절편을 `Q90(R−b1×L)`로 구했다. 최선 기울기의 ±0.05를 0.0005 간격으로 재탐색했다. NumPy 기본 선형 보간 분위수와 유한 격자를 사용한 수치적 근사다.

\[
\widehat R_{90}(L)=116.91249+1.259L\quad[초]
\]
\[
B(L)=10\left\lceil\frac{\widehat R_{90}(L)}{10}\right\rceil
\]

계수는 독립 분석 결과이며 논문이나 정부 신호 설정식에서 복사한 값이 아니다. 10초 올림은 별도 시험 정책이다. 신호 1개 예시에서 길이 38m이면 164.75449초→계획 여유 170초다. 카카오 도보 452초에 더한 계획은 622초(10분 22초)다. 다른 길이도 대입할 수 있지만 관측 범위 밖 외삽이나 모든 시설의 정확성을 보장하지 않는다.

\[
T_{walk,plan}=T_{Kakao,walk}+B(L)\quad\text{(신호 1개 시험 정책)}
\]

적색 지속시간 전체는 보행자가 실제로 기다리는 잔여 적색시간과 다르다. `횡단보도 이용` 안내만으로 신호등 존재를 확정할 수도 없다. 카카오가 이미 포함한 가산분·복수 신호의 연동·계단·경사·승강장 접근 범위는 검증하지 못했다. 따라서 622초를 실측 ETA로 표시하거나 여러 B의 합을 전체 경로 P90이라고 표시하지 않는다. 복수 횡단보도 집계 정책도 미확정이다.

독립 기록의 지역 제외 검증에서는 8개 지역을 하나씩 제외해 4,644개 평가 예측을 만들었다. 평균식의 표본 내 R²는 0.1577로 길이만으로 설명되는 정도는 제한적이다. 이번 MR은 원본·분석 코드 전체를 수록하거나 이 실험을 재실행하지 않았으며, 서버에 계수를 적용하지 않는다.

## 4. 버스 탑승시간: 인접 구간 ML과 step 단위 fallback

현재 구현 경계는 [MlRoutePreview](../../backend/src/main/java/com/ssafy/ddubi/domain/recommendation/evaluation/MlRoutePreview.java)→[BusPreviewClient](../../backend/src/main/java/com/ssafy/ddubi/domain/recommendation/evaluation/BusPreviewClient.java)→[Python predictor](../../ml-serving/predictor.py)다. 모델·입출력 상세는 [버스 예측 HTTP 계약](ml-serving-http.md)을 따른다.

HTTP 입력은 `provider_namespace=SEOUL_BUS`, 제공자 노선 ID, 양 끝 정류장 ID, 출발 정류장 순번, 진입 예정 날짜, 시간대다. 차량 ID는 이 요청의 ML 입력이 아니다. 날씨·승하차·과거 이력 등은 모델 bundle의 참조 자료와 입력 명세에 따라 붙인다. 향후 수집 표에 열이 있다고 현재 실시간 입력이 연결된 것으로 표현하지 않는다.

1. 경로 BUS step의 인접 edge 전부가 같은 노선·방향으로 이어지는지 확인한다.
2. 첫 edge 진입시각은 적용 가능한 승차대기가 있으면 그 이후의 탑승시각이다.
3. 진입시각을 KST 날짜·hour slot으로 바꿔 예측한다. Python은 bundle의 학습 당시 특성 순서·인코더·결측 처리로 행렬을 만든다.
4. 현재 계약에 기록된 v12 LightGBM은 여러 결정트리의 학습 결과를 합산하는 모델이다. 서비스는 모델 출력에 `max(0, predict)`를 적용하고 응답 검증 후 Backend가 초 단위로 올림한다. 특정 트리 수·가중치를 문서에 새 상수로 정하지 않는다.
5. 앞 edge의 예측 초를 다음 진입시각에 더한다. 모든 edge 성공 시에만 BUS step 시간을 교체한다.

\[
\widehat y_k=\max(0,f_{bundle}(x_k)),\quad
s_k=\lceil\widehat y_k\rceil,\quad
t_{k+1}=t_k+s_k,\quad
T_{bus,ride}=\sum_{k=1}^{m}s_k
\]

예를 들어 120.2초·89.1초라는 합성 예측은 121+90=211초다. 두 번째 edge 입력 시각도 121초 뒤가 된다. 모델이 실패한 edge를 0초로 놓고 합산하지 않는다.

한 edge라도 미지원·응답 불일치·예산 초과이면 해당 BUS step 전체를 원래 API 시간으로 복귀한다. 부분 예측 합과 전체 API 시간을 함께 더하지 않는다. 대기를 적용할 수 있다고 가정했던 경우라도 BUS 이동 계산이 실패하면 그 대기도 미적용 처리한다. 현재 대기 제외가 검증된 설정에서는 결측 WAIT를 남겨 전체 ETA를 정보 부족으로 처리한다.

현재 PREVIEW 호출 예산은 평가당 서로 다른 입력 캐시 64개와 20초 실행 기한이며, HTTP timeout은 설정으로 최대 5초다. 이 값은 서버 호출 제한으로 안전 여유시간이 아니다. 모델 서비스의 참조 지원 날짜·ID vocab·응답 `production_ready` 등을 확인해야 하며, 모델 이름이 같다고 지원 범위가 무제한인 것은 아니다.

## 5. 지하철 탑승·대기: 시간표 차이와 실시간 보조

### 5.1 9월 서울 시간표를 사용한 독립 설계

사용자 결정은 서울 범위의 카카오 경로 지하철 구간을 시간표로 재평가하는 것이다. 원천은 [서울교통공사 열차운행시각표](https://www.data.go.kr/data/15098251/fileData.do)의 로컬 2026-09-01 CSV이며 CP949, 423,107행이다. 확인한 파일 SHA-256은 `ab5e46fc39ab14e51d27cbbda7ec21fc5ee2a69d2ceb10095dc88b9a84434021`이다. 파일명·공식 기준일과 로컬 바이트를 대조한 것이며 이번 MR에서 다시 다운로드하지 않았다.

시각 `h:m:q`를 초로 바꾸는 \(s=3600h+60m+q\)는 비교·차이를 한 단위로 계산하기 위한 변환이다. 24/25시는 영업일을 유지한 다음날 시각으로 처리해야 한다. 날짜 유형·호선·방향·열차코드로 같은 운행을 묶고 정차 순서·시각 역전·서울 주소·마스터 인접 순서를 검증했다.

\[
T_{subway,ride}=A_{j,to}-D_{j,from}
\]

\(A_{j,to}\)는 같은 열차 j의 하차역 도착시각, \(D_{j,from}\)은 승차역 출발시각이다. 서울역 05:20:30 출발→종각 05:25:00 도착이면 270초다. 시간표 한 행의 열차 기점·종점을 사용자의 승하차역으로 오인하지 않는다. 중간 정차시간은 이 차이에 포함된다.

CSV는 원본 보존용으로 두고 독립 폴더에서 `stations`, `trips`, `departureIndex` 압축 JSON을 만들었다. 역·운행유형별 정렬 인덱스로 출발 후보를 찾는 시작 비용은 O(log N)이며 이후 목적역 정차 확인 비용은 별도다. 보존 서울 정차 318,157행, 인덱스 306,017항목, 채택 운행키 11,105개다. 운행키 수는 DAY/SAT/END 합계로 하루 운행 수가 아니다.

**이 독립 JSON과 현재 [SubwayTimetable](../../backend/src/main/java/com/ssafy/ddubi/domain/recommendation/evaluation/SubwayTimetable.java)의 운행일별 입력 형식은 같지 않다.** 새 인덱스 로더가 Backend에 이미 들어갔다고 표현하지 않는다. 원본 전처리·주소·마스터·15개 관련 테스트의 결과는 독립 검증 기록이며 이번 문서 MR의 실행 테스트가 아니다.

### 5.2 현재 Backend 알고리즘

[SubwayTimingService](../../backend/src/main/java/com/ssafy/ddubi/domain/recommendation/evaluation/SubwayTimingService.java)는 EXACT 매핑·마스터 버전·시간표 공개일/유효기간과 같은 노선의 정차열을 확인한다. 현재 코드는 인덱스 파일을 이진 탐색하는 방식이 아니라 `data.trips()`를 순회해 일치 운행을 찾는다.

시간표만 쓸 때 승강장 도착 예정시각을 U라 하면 다음과 같다.

\[
W_{subway}=D_{j,from}-U\ge0,\qquad
T_{subway,ride}=A_{j,to}-D_{j,from}
\]

실시간 열차 대응이 검증되고 120초 신선도·방향·행선지·유효범위 등을 통과한 경우에는 제공시각 o와 도착까지 남은 e초로 탑승 기준시각을 \(B=o+e\)로 만든다. 이때 현재 코드는 승차역 정차를 포함하기 위해 \(A_{j,to}-A_{j,from}\)을 탑승시간으로 사용한다.

\[
W_{subway}=B-U,\quad
T_{subway,ride}=A_{j,to}-A_{j,from},\quad
ETA_{to}=B+T_{subway,ride}
\]

실시간 도착을 미래의 실제 출발시각으로 확정하는 계산은 아니다. 위치는 이미 승차역을 지난 열차를 제외하는 증거이며 위치 스냅샷만으로 실측 역간 지연을 만들지 않는다. 실시간이 없거나 범위 밖이면 유효한 시간표로 복귀한다. 시간표도 없으면 별도 추정은 부족 상태이고 적용 조건에 따라 카카오 유지 또는 결측 WAIT 처리가 된다.

현재 구현은 일치하며 탑승 가능한 운행 후보 중 하차 도착시각이 가장 이른 결과를 내부 계산 기준으로 선택한다. 사용자에게 새로운 열차 경로를 추천하는 API는 아니다. 사용자와 정리한 핵심은 같은 운행의 두 역 시각 차이이며, 이 내부 최소 도착 선택과 새로운 독립 인덱스의 기준 운행 선택 정책이 완전히 동일하다고 간주하지 않는다.

## 6. 환승 이동

\[
T_{transfer}=T_{Kakao,transfer\ walking}
\]

환승 walking은 다음 차량을 기다리는 시간이 아니라 이전 하차 위치에서 다음 승차 위치로 이동하는 시간이다. 카카오 응답이 포함하는 범위를 확인해 유지한다. 오늘 결정에 따라 별도의 1.2m/s 환산·혼잡 계수를 추가하지 않는다. 접근/이탈 도보와 환승 walking을 중복 집계하지 않는다.

\[
U_{next}=A_{previous}+T_{transfer}
\]

다음 지하철 대기나 버스 배차 시간대는 U_next를 기준으로 조회하는 설계다. 실제 환승 walking이 승강장 간 전체 이동을 포함하는지는 통합 검증 대상이며, 없는 구간을 0초로 간주하지 않는다.

## 7. 버스 대기: 현재 구현과 새 초기 정책

### 7.1 현재 실시간 계산

[BusWaitingService](../../backend/src/main/java/com/ssafy/ddubi/domain/recommendation/evaluation/BusWaitingService.java)는 `transit:latest:bus-arrival:{노선ID}:{정류장ID}`를 읽는다. 정류장 순번·서울 namespace·단위 표시·제공시각·유효기간을 확인한 뒤 첫째·둘째 후보를 평가한다.

\[
B_j=occurredAt+arrivalSeconds_j,\qquad W_j=B_j-U
\]

U 이후 도착하고, 정류장 도착과 차량 도착 모두 `validUntil` 안에 있으며 만차·종점 도착·우회 상태 검사를 통과하는 가장 이른 차량을 사용한다. 자료 발생 후 120초 제한 밖 예측은 사용하지 않는다. 둘 다 사용할 수 없으면 null이며 0초가 아니다. 대기열 때문에 몇 대를 보내는지 계산하거나 배차로 가상 셋째 차량을 만들지 않는다.

### 7.2 2026-09-15 결정한 사전 대기식

\[
\widehat W_{bus}=0.6H,\qquad
\widehat W_{bus,seconds}=36H_{minutes}
\]

배차 5·10·15·20분의 합성 예시는 각각 대기 180·360·540·720초다. 출발 08:00+도보 7분이면 U=08:07이며, 배차 10분을 적용한 예상 탑승 기준시각은 08:13이다. **08:13에 특정 버스가 온다는 ETA나 시간표를 만든 것은 아니다.**

채택 근거는 김경태·이인묵(2025), 「배차간격 정보 기반의 버스 대기시간 추정 방법에 대한 실증적 고찰」, 한국철도학회논문집 28(2), 141–148, DOI `10.7782/JKSR.2025.28.2.141`이다. [KCI 서지·저자 초록](https://www.kci.go.kr/kciportal/ci/sereArticleSearch/ciSereArtiView.kci?sereArticleSearchBean.artiId=ART003172273)

저자 초록은 교통카드의 이용자·차량 시각 분석에서 평균 대기와 평균 간격 사이 약 0.6배 관계를 얻었으며 조건별 동일 계수 적용에는 한계가 있다고 설명한다. 이번에는 초록·서지를 확인했으며 논문 전체 실험·원자료를 재현하지 않았다. 0.6은 우리 서울 데이터로 학습한 계수가 아니고 P60·P90·탑승 성공 확률도 아니다. 공개 계획 배차를 실측 평균의 대용 입력으로 사용하는 것은 추가 근사 가정이다.

일정한 배차와 무작위 승객 도착이면 평균 대기는 H/2다. 변동하는 실측 간격 h_i에서 시간축 균등 도착을 가정하면 다음 관계가 생긴다. 이는 수학적 배경 설명이며 위 논문의 본문 수식을 인용한 것은 아니다.

\[
E[W]=\sum_i\frac{h_i}{\sum_jh_j}\frac{h_i}{2}
=\frac{\sum_i h_i^2}{2\sum_i h_i}
=\frac{\mu_H}{2}(1+CV_H^2)
\]

5분·15분 간격 반복에서는 긴 간격 안에 도착할 확률이 15/20, 짧은 간격은 5/20이므로 평균 대기는 6.25분이다. 이 예의 0.625를 반올림해 0.6을 학습한 것이 아니다. 초기 계수는 위 연구와 사용자 결정에서 왔다.

### 7.3 왜 직접 과거 이력으로 계수를 구하지 않았는가

T-Data 공개 파일을 조사했지만 실측 의미와 운행 완전성이 해결되지 않았다. [정류장별 이력 68](https://t-data.seoul.go.kr/dataprovide/trafficdataviewfile.do?data_id=68)은 2026-09-11~13 73,125행·152노선이었다. 951운행 중 920개는 인접 도착간격이 일정했고, [차량운행별 이력 69](https://t-data.seoul.go.kr/dataprovide/trafficdataviewfile.do?data_id=69)와 키가 연결돼도 마지막 정류장·순번까지 일치한 것은 90개였다. 필드 의미 확인 없이 완전한 실측 정답으로 쓰지 않았다.

[배차정보 72](https://t-data.seoul.go.kr/dataprovide/trafficdataviewfile.do?data_id=72)는 간격 후보를 제공하나 실측 분포를 제공하지 않는다. [차량운행 통계 84](https://t-data.seoul.go.kr/dataprovide/trafficdataviewfile.do?data_id=84)도 중간 정류장 시각 배열을 확보하지 못했다. API 한도·남은 수집 기간까지 고려해 0.6H로 시작하고 실측 고도화를 뒤로 미룬 이유다.

서울 2026-09-02 공식 목록 723개와 대조했을 때 source53 기본 또는 source72 시간대 양수 후보는 695개였다. 이는 일부 필드의 후보 포함률이다. 이후 [서울시 올빼미 안내](https://news.seoul.go.kr/traffic/archives/27974)에서 N노선 14개 배차범위를 확인했고, 8772는 기존 CSV에도 토요일 14·공휴일 13이 있었다. 기본값 0을 전 요일 정보 부재로 설명했던 판단을 정정했다.

새벽 A148·A741·A504 등은 고정 기점 출발 안내가 있어 반복 배차식으로 해결할 수 없다. 공개 CSV 누락이 운행정보 자체의 부재를 뜻하지 않는다. 한편 723개는 관광·특수 항목을 포함하므로 전체 일반버스 운행 전수나 서비스 지원률과 같지 않다. 이번 MR에 조사 CSV나 서비스용 배차 마스터를 추가하지 않는다.

## 8. 전체 합산·fallback·출발시각의 실제 연결

### 8.1 목표 구성식과 중복 방지

\[
T_{route}=T_{access}+T_{egress}
+\sum T_{bus,ride}+\sum T_{subway,ride}
+\sum T_{transfer}+\sum W_{bus}+\sum W_{subway}
\]

이는 구성요소가 분리되고 각각 한 번씩만 포함될 때 성립한다. 기존 총시간을 수정하는 경우에는 같은 의미·범위의 항목을 빼고 새 값을 넣는다.

\[
T_{new}=T_{Kakao,total}-\sum T_{Kakao,replaced}+\sum T_{new,replaced}
\]

현재 RouteEvidenceAssembler는 `unassigned = total − sum(steps)`를 계산한다. 양수이면 그 잔여를 한 번만 보존하고 step 진입시각에 그만큼의 불확실성을 부여한다. 잔여를 전부 접근 도보나 대기로 임의 분배하지 않는다. step 합이 총시간보다 크거나 step이 없으면 전체 제공자 시간으로 돌아간다.

현재 MlRoutePreview가 별도 WAIT를 총시간에 반영하려면 교통수단별 `decomposition-verified=true`와 잔여시간 0 등 조건이 필요하다. 버스는 step 전체 ML도 성공해야 한다. 시간 분해가 확인됐는데 필수 대기가 없으면 결측 WAIT를 남겨 [RouteTimelineEvaluator](../../backend/src/main/java/com/ssafy/ddubi/domain/recommendation/evaluation/RouteTimelineEvaluator.java)가 `INSUFFICIENT_DATA`, ETA=null로 반환한다. 수치가 있다는 것과 `applied=true`는 다르다.

### 8.2 손계산 가능한 전체 예시

다음은 입력 분해·운행 가능·배차 단일값이 확인됐다고 가정한 **정책 설명용 fixture**다. 서비스 실행 응답이 아니다. 도보 숫자는 해당 계획 여유가 이미 반영된 가정값이며 신호 여유를 다시 더하지 않는다.

| 순서 | 항목 | 초 | 종료 예정시각(08:00 출발) |
|---|---|---:|---|
| 1 | 접근 도보 | 420 | 08:07:00 |
| 2 | 버스 대기, H=10분 | 360 | 08:13:00 |
| 3 | 버스 탑승, edge 합 | 900 | 08:28:00 |
| 4 | 환승 walking | 180 | 08:31:00 |
| 5 | 지하철 대기, 기준 출발 08:34 | 180 | 08:34:00 |
| 6 | 지하철 탑승, 기준 하차 08:44 | 600 | 08:44:00 |
| 7 | 이탈 도보 | 300 | 08:49:00 |
| 합계 | 전체 계획 | **2,940초 = 49분** | **08:49:00** |

다른 출발시각이면 버스 입력 시간대와 지하철 기준 운행이 달라질 수 있다. 49분이 나왔다고 모든 출발시각의 소요시간이 49분인 것은 아니다.

### 8.3 현재 두 호출 경로를 구분한다

| 코드 흐름 | 현재 동작 | 이 문서에서의 해석 |
|---|---|---|
| [ScheduleEvaluationWorkflow](../../backend/src/main/java/com/ssafy/ddubi/domain/recommendation/service/ScheduleEvaluationWorkflow.java) → MlRoutePreview → RouteTimelineEvaluator | 같은 출발시각의 후보를 비교하고 유효한 최소 도착 결과를 제공. 내부 `suggestion()`은 이 비교 결과를 포장 | 이 경로가 별도 출발 격자 탐색을 호출하거나 0.6H를 사용한다고 설명하면 안 됨 |
| [DepartureSuggestionService](../../backend/src/main/java/com/ssafy/ddubi/domain/recommendation/evaluation/DepartureSuggestionService.java) | 고정 Journey와 명시한 시간 격자·예산으로 더 이른 출발 후보 탐색 | 별도 구현. 위 workflow에서 `suggest()`를 호출하지 않음 |

TravelTimeEstimator는 API 구간시간으로 먼저 진입시각을 추정해 예측을 배치 요청한다. 모든 edge 예측→모든 edge 기준선→API step 균등 분배 순으로 선택하고 유효한 상태의 지연초를 별도로 더한다. 반면 MlRoutePreview는 예측 edge 결과를 다음 edge 요청 시각에 즉시 반영하며 상태·도로 사건을 위험 근거로 다룬다. 이 둘을 혼합해 하나의 완성된 호출 흐름으로 설명하지 않는다.

DepartureSolver는 초기 \(d_0=D-(T_{API}+buffer)\), 이후 \(d_{next}=D-(T(d)+buffer)\)를 계산한다. 최대 2회 갱신 루프와 60초 종료 허용차가 있으며 초기 estimate 호출은 별도다. 반환 estimate가 최종 출발시각에서 다시 계산된 값과 같다는 보장은 없다. 이 허용차는 첫차·막차·환승 경계의 정확성을 입증하지 않는다. 여기의 기존 buffer를 도보 신호 여유나 버스 0.6 계수와 동일시하지 않는다.

사용자가 원하는 최종 서비스는 출발 후보마다 전체 구성요소를 다시 계산해 도착 희망시각과 비교하는 것이다. 어느 호출 흐름으로 통합할지와 전체 경로 Replay 검증은 후속 구현 범위다. 이번 MR이 추천 수락·알림 게이트를 변경하거나 운영 준비 상태를 승격하지 않는다.

## 9. 보류한 세 가지 해결과제

| 번호 | 과제 | 현재 결정 | 해결 시 필요한 검증 |
|---|---|---|---|
| 1 | 배차범위 대표값 | `20~30분 → 25분`은 예시·제안이며 **채택하지 않음** | 시간대·요일 의미, 평균/최대 등 대표값 정책과 근거 |
| 2 | 배차정보 누락·0·상충 및 고정 출발 노선 | 0초 대기·임의 간격으로 대체하지 않음. fallback 정책 보류 | 자료 우선순위·계산 불가 상태·기점 출발부터 중간 승차지 시각 연결 |
| 3 | 첫차·막차·운행일 경계 | 0.6H로 운행 가능성을 판단하지 않음 | 승차역/정류장별 운행일·공휴일·24/25시·마지막 이용 가능 운행, 결측과 실제 종료 구분 |

이 세 과제를 보류한 상태에서 모든 노선·모든 시각을 계산할 수 있다고 표시하지 않는다. 기존 독립 도보 보정의 복수 신호/중복 문제, 지하철 자료 어댑터·역내 접근, 전체 합산의 포함 범위도 미해결 통합 조건으로 유지한다.

후속 결과는 값·단위와 함께 출처, 입력 기준일, 모델/정책/마스터 버전, fallback 이유, 적용 여부를 추적해야 한다. 실측이 없다고 임의 confidence나 성공 확률을 넣지 않는다. 기존 `waitPredictions.seconds=null`과 `applied=false`, 시간표 source/version·eventId, ML `dataInsufficient` 등의 의미를 보존한다. 새로운 0.6H 출력 enum이나 JSON 필드는 실제 구현 시 기계 계약과 함께 정한다.

## 10. 이번 문서의 검증 범위와 후속 완료 기준

이번 확인은 최신 develop의 호출 코드·기존 계약과 바탕화면 2026-09-14 도보/2026-09-15 지하철·버스 기록을 대조한 것이다. 별도 연구의 숫자를 운영 테스트 결과로 바꾸지 않았다. 기록의 원본은 project_log의 해당 날짜 산출물과 서울 버스·지하철 독립 검증 폴더에 보관돼 있으며, 개인 PC 경로를 실행 의존성으로 문서에 넣지 않는다.

문서 변경 검증은 상대 링크, JSON 예시가 있는 기존 기계 계약과의 상태 설명, 위 합산 fixture·단위 변환, 미반영 정책 표기와 diff 범위 확인이다. Java/Python 실행 코드 변경이 없어 전체 서비스 테스트·재학습·실측 평가를 새로 수행하는 변경은 아니다.

후속 구현에서는 (1) 정상 수식의 손계산 일치, (2) 누락·상충·반대 방향·반복 정류장·stale·심야 경계, (3) 출발 변경 시 모든 후속 입력 시각 재생성, (4) 카카오 시간 중복 없음, (5) 실측 미래 검증집합에서 H/2·0.6H·고도화 방법의 오차/과소추정/지원률 비교를 확인해야 한다. 코드가 값을 반환하는 것과 실제 예측력이 입증되는 것은 별도 완료 기준이다.
