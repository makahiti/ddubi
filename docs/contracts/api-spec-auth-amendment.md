# API 명세서 개정 요청 — AUTH-003 소셜 로그인

작성: 백엔드(서비스) 손정민
대상: Notion「DDUBI_APP_API」v2.1.1 § 3.1.3 소셜 로그인

소셜 로그인 4종(카카오·구글·네이버)을 구현하면서 **명세서와 실제 계약이 어긋나는 지점 2건**을 찾았습니다.
아래 문안으로 고쳐 주시면 됩니다.

---

## 1. `state` 필드 추가 (필수 개정)

**네이버 토큰 교환은 `state` 가 필수입니다.** 현재 Request Body 정의에 없어서,
명세서대로 구현하면 네이버 로그인이 100% 실패합니다.

카카오·구글은 `state` 를 쓰지 않으므로 **선택 필드**로 두고, 네이버일 때만 서버가 필수로 검증합니다.
빠지면 네이버를 호출하지 않고 즉시 `400 INVALID_REQUEST` 를 냅니다 — 외부 호출을 낭비하지 않고
원인이 클라이언트 요청임을 분명히 하기 위해서입니다.

### 붙여넣을 표 (기존 Request 표를 이걸로 교체)

| 필드 | 필수 | 허용값 |
| --- | --- | --- |
| `provider` | O | `KAKAO`, `GOOGLE`, `NAVER` |
| `authorizationCode` | O | 제공자에게 받은 일회용 코드 |
| `redirectUri` | O | 사전 등록 URI |
| `state` | △ | **`NAVER` 일 때 필수.** 인가 요청에 쓴 값과 동일해야 한다. 카카오·구글은 무시된다 |
| `deviceId` | X | 미지정 시 서버가 발급 |

### 요청 예시

```json
{
  "provider": "NAVER",
  "authorizationCode": "제공자에게-받은-코드",
  "redirectUri": "http://localhost:3001/oauth/naver",
  "state": "인가요청에-쓴-난수",
  "deviceId": "device-A"
}
```

> 프론트 참고: `state` 는 CSRF 방지용 난수입니다. 인가 URL 을 만들 때 생성해 두었다가
> 콜백으로 돌아온 값과 대조한 뒤, **같은 값을 그대로** 이 API 에 실어 보내면 됩니다.

---

## 2. `SSAFY` 삭제 (문구 정정)

현재 `provider` 허용값에 `SSAFY` 가 적혀 있습니다. **팀 합의로 제외된 항목**이고
ERD_master 의 `user_auth.provider` ENUM 에도 없습니다(`LOCAL, KAKAO, GOOGLE, NAVER`).

같은 문단이 `user.provider` ENUM 을 근거로 들고 있는데, `provider` 는
「안건 합의」에서 `user` → `user_auth` 로 옮겨졌습니다. 즉 이 문단은 `user_auth` 신설 이전에
쓰인 잔재로 보이며, `SSAFY` 도 거기 딸려온 것으로 판단됩니다.

Apple 제외 각주의 `user.provider` 도 `user_auth.provider` 로 바꾸면 정확해집니다.

---

## 참고 — 구현 현황

| provider | 구현 | 실호출 검증 |
| --- | --- | --- |
| `LOCAL` | 완료 | 완료 |
| `KAKAO` | 완료 | 완료(실계정 로그인·계정 통합 확인) |
| `GOOGLE` | 완료 | **콘솔 등록 대기** |
| `NAVER` | 완료 | **콘솔 등록 대기** |

구글·네이버는 코드와 단위 테스트가 끝났고, GCP·네이버 개발자센터 앱 등록과 키 발급만 남았습니다.
키가 없는 상태에서 호출하면 해당 provider 만 `500 INTERNAL_ERROR` 이고 나머지는 정상 동작합니다.

### 계정 통합 시 이메일 인증 여부를 본다 (구현 결정)

도메인 규칙 3(같은 이메일이면 계정 통합)에 **"인증된 이메일에 한한다"** 는 조건을 더했습니다.

제공자가 이메일을 주더라도 미인증이면(`kakao_account.is_email_verified=false`,
구글 `email_verified=false`) 통합하지 않고 별도 계정을 만듭니다.

이유: 미인증 이메일을 신뢰하면 **남의 이메일을 등록한 소셜 계정으로 그 사람의 기존 계정에
그대로 들어갈 수 있습니다.** 통합 키가 이메일 하나뿐이라 이 검사가 없으면 막을 방법이 없습니다.

# 3. 신규 API 2건 — 회원가입 이메일 인증 (AUTH-006 / AUTH-007)

**로컬 가입 시 이메일 인증을 받기로 했습니다.** 명세서에 없는 엔드포인트라 추가가 필요합니다.

## 왜 넣는가

이메일이 **계정 통합의 유일한 키**입니다(도메인 규칙 3). 그런데 지금 로컬 가입은
이메일 소유를 확인하지 않습니다. 이 조합이 그대로 두면 다음이 성립합니다.

```
1. 공격자가 피해자 이메일로 로컬 가입 (소유 확인 없음)
2. 피해자가 나중에 소셜 로그인
3. 이메일이 같으므로 자동 통합
4. 공격자가 자기 비밀번호로 피해자 계정에 로그인
```

이메일 인증이 들어가면 1번이 막히고, **자동 통합이 안전해집니다.**

## 붙여넣을 문안

### AUTH-006 이메일 인증 코드 발송 🟢

- **Method / URL:** `POST /auth/email/verification`
- **호출 권한:** 인증 불필요
- **처리 주체:** 뚜비 API 서버
- **관련 화면·요구사항:** DDB-001, 계정 생성
- **필요한 이유:** 로컬 회원가입 전 이메일 소유를 확인한다. 계정 통합의 키가 이메일이므로 소유 확인 없이는 계정 탈취 경로가 열린다.
- **Request:** Body: `email`(필수)
- **Response:** `204 No Content`
- **주요 예외:** `400 INVALID_REQUEST` — 형식 오류, 또는 60초 내 재요청
- **비고:** 이미 가입된 이메일이어도 발송한다. 여기서 거절하면 어떤 이메일이 가입돼 있는지 알아내는 통로가 된다.

### AUTH-007 이메일 인증 코드 확인 🟢

- **Method / URL:** `POST /auth/email/verification/confirm`
- **호출 권한:** 인증 불필요
- **처리 주체:** 뚜비 API 서버
- **관련 화면·요구사항:** DDB-001, 계정 생성
- **필요한 이유:** 발송한 코드를 대조해 가입 자격을 준다.
- **Request:** Body: `email`(필수), `code`(필수·숫자 6자리)
- **Response:** `204 No Content`
- **주요 예외:** `400 INVALID_REQUEST` — 코드 불일치·만료·시도 초과
- **비고:** 성공 시 **30분** 유효한 가입 자격이 생긴다. 5회 틀리면 코드를 폐기한다.

### AUTH-001 로컬 회원가입 — 문구 추가

기존 설명에 아래 한 줄을 더합니다.

> **AUTH-007 인증을 마친 이메일만 가입할 수 있다.** 인증 없이 호출하면 `400 INVALID_REQUEST`.
> 가입이 성립하면 인증 자격은 소비되어, 한 번 인증으로 계정을 여러 개 만들 수 없다.

## 프론트 흐름

```
[이메일 입력] → AUTH-006 발송
        ↓  (메일 도착. 스팸함 안내 문구 필요)
[6자리 입력] → AUTH-007 확인
        ↓  (30분 안에)
[비밀번호·닉네임 입력] → AUTH-001 가입
```

**"메일이 안 보이면 스팸함을 확인하세요" 문구를 코드 입력 화면에 넣어 주세요.**
개인 Gmail 계정에서 발송하므로 네이버·다음에서 스팸으로 분류될 수 있습니다.

## 운영 메모

- 발송 계정 자격증명이 없으면 **메일을 보내지 않고 서버 로그에만 코드를 남깁니다.**
  팀원이 앱 비밀번호 없이도 가입 흐름을 개발할 수 있게 한 장치입니다.
- 발송 경로는 환경변수(`MAIL_HOST`/`MAIL_PORT`/`MAIL_USERNAME`/`MAIL_PASSWORD`)로만
  정해집니다. 스팸 분류가 문제되면 코드 변경 없이 다른 발송 서비스로 바꿀 수 있습니다.

# 4. 계정 통합 방식 확정 — 자동 통합 (2026-09-01)

프론트에서 **"기존 계정이 있으면 비밀번호를 확인한 뒤 통합"** 을 제안했으나,
**자동 통합으로 확정**했습니다. 프론트에 비밀번호 확인 화면은 필요 없습니다.

## 이유

비밀번호 확인은 **로컬 계정의 이메일이 검증되지 않았을 때** 필요한 장치였습니다.
AUTH-006/007 로 로컬 가입에도 이메일 인증이 붙으면서 전제가 사라졌습니다.

| | 이메일 검증 주체 |
| --- | --- |
| 로컬 계정 | 뚜비 (AUTH-007 인증 코드) |
| 소셜 계정 | 제공자 (`is_email_verified` / `email_verified` 확인) |

**양쪽 다 소유가 확인된 이메일**이므로, 이메일이 같으면 같은 사람이 맞습니다.
한 단계 더 묻는 것은 안전을 더하지 않고 이탈만 늘립니다.

## 동작 (변경 없음 — 이미 구현·테스트됨)

```
로컬 가입(thswjdals258@naver.com) 후 네이버 로그인
  → user 를 새로 만들지 않는다
  → user_auth 에 NAVER 행만 추가
  → 200 (신규 가입이 아니므로 201 아님)
  → 응답 user.providers = [LOCAL, NAVER]
```

미인증 이메일이거나 제공자가 이메일을 주지 않으면 통합하지 않고 별도 계정이 됩니다.
