# 과거 이력 지연 설계 개선안 (B안) — 설계·평가 계획

- 작성일: 2026-09-18 (Asia/Seoul)
- 상태: **계획만 작성. 재학습·bundle 생성·배포를 수행하지 않았다.**
- 배경: [ml-reference-gaps-20260918.md](ml-reference-gaps-20260918.md)
- **원천·정규화 규칙 정본**: [transit-data-refresh.md](transit-data-refresh.md) (원천별 `0` 의미 포함)
- 기준 결정: [ml-data-decision.md](ml-data-decision.md), [ml-retraining-v12.md](ml-retraining-v12.md)

## 0. 왜 이 문서가 필요한가

현재 v12는 예측일 기준 **77·84·91·98·105·112·119·126일 전 8개 날짜**를 고정으로 참조한다.
그중 하루라도 공급처 원천이 결측이면 그 날짜의 표본이 그대로 사라진다.
2026-09-10~10-10 구간에서는 31일 중 17일이 이 영향을 받는다.

더 큰 문제는 **결측이 아니라 관측 부재**다. 구간 운행시간 원천(OA-21217)의 시간대 칸 33~34%가
`0`이고 이 원천에서 `0`은 관측 없음을 뜻한다.
그 결과 서비스일 2026-09-18 기준 edge-hour의 **30.1%(05~23시 기준 16.7%)가 `history_sample_count = 0`**이다.
고정 8칸 설계는 이 구간에 아무 값도 주지 못한다.

이 문서는 세 후보를 **같은 조건에서 비교할 수 있게** 설계와 평가 기준을 고정한다.
어느 후보가 이긴다고 미리 정하지 않는다.

## 1. 공통 불변 조건

세 후보 모두 아래를 어기면 후보 자격이 없다.

| 항목 | 규칙 |
|---|---|
| 최소 지연 | 모든 참조 날짜는 **예측일 − 77일 이하**여야 한다. 기존 보수적 공개지연 가정을 유지한다 |
| 누수 금지 | `feature_available_at <= prediction_base_at`. 미래 관측·사후 수정본·뒤늦게 공개된 통계 금지 |
| 정답 의미 | 시간대별 인접 정류장 구간 **평균** 소요시간. 개별 차량·전체 경로 실측이 아니다 |
| `0` 처리 | **원천마다 다르다.** OA-21217(구간 운행시간)의 `0`은 관측 없음이므로 결측으로 분리하고, OA-21218·21219·21220(재차인원·승차승객·운행횟수)의 `0`은 **유효 관측이므로 보존**한다. 정본은 [transit-data-refresh.md](transit-data-refresh.md) |
| 결측 생성 금지 | 보간·복사·평균·요일 대체로 없는 날짜를 만들지 않는다 |
| 학습·추론 일치 | 참조 날짜를 고르는 **같은 함수**를 학습과 추론이 공유한다 |
| 기록 | 각 행이 실제로 사용한 참조 날짜 목록과 유효 표본 수를 산출물에 남긴다 |
| 승인 | 결과가 좋아도 `production_ready`를 수동으로 true로 바꾸지 않는다 |

## 2. 후보 설계

### 후보 A — 기존 고정 날짜 간격 + 결측 마스크 (현행 + 최소 변경)

지금과 같은 8개 고정 지연을 쓰되, **왜 비었는지를 모델에 알려준다.**

추가 입력:

- `history_count_8obs`, `history_count_4obs` (이미 있음)
- `history_gap_source_missing_count` — 참조 날짜 중 **파일 자체가 없던** 수
- `history_gap_no_observation_count` — 파일은 있으나 해당 시간대가 `0`이던 수
- 지연 슬롯별 마스크 8개 (`history_slot_77_present` … `history_slot_126_present`)

두 결측 원인을 구분하는 것이 핵심이다. 현재는 둘 다 그냥 NaN이라 모델이 구별하지 못한다.

| 항목 | 값 |
|---|---|
| 최대 탐색 기간 | 126일 (변경 없음) |
| 누수 위험 | 낮음. 참조 집합이 현행과 동일 |
| 학습·추론 일치 | 마스크 생성 로직만 추가. 기존 `attach_features`와 같은 경로 |
| 장점 | 변경 최소, 회귀 위험 낮음, 기존 bundle 구조 유지 |
| 한계 | `history_sample_count = 0`인 30.1% 구간은 **그대로 0**이다. coverage가 늘지 않는다 |

### 후보 B — 같은 요일의 이전 유효 관측 8개를 제한 기간 안에서 탐색

예측일 − 77일부터 **7일씩 거슬러 올라가며** 유효 관측을 모아 최대 8개를 채운다.

```
후보 날짜 = D - 77, D - 84, D - 91, … , D - 77 - 7k   (k = 0 … K)
유효 조건 = 파일 존재 AND (route, from, to, order) 매칭 AND 해당 hour 값이 0이 아님
8개를 채우면 중단. 못 채우면 찾은 만큼만 사용하고 실제 개수를 기록.
```

| 항목 | 값 |
|---|---|
| **최대 탐색 기간** | **D − 245일 (K = 24, 약 8개월)** |
| 최대 탐색 근거 | 계절 변동을 한 계절 이상 넘기지 않으면서 8칸을 채울 여유 확보. 초과 시 미충족으로 남긴다 |
| 요일 고정 | 7의 배수만 사용해 요일을 유지한다. 공휴일은 별도 특성으로 남기고 탐색 조건에 넣지 않는다 |
| 누수 방지 | 모든 후보가 `D − 77` 이하. 탐색 방향이 과거 단방향이라 미래 참조가 구조적으로 불가능 |
| 학습·추론 일치 | 동일 탐색 함수 공유. 학습 시점에도 "그 예측일 기준"으로만 탐색해야 하며, 전체 기간을 미리 스캔해 채우면 안 된다 |
| 추가 기록 특성 | `history_span_days`(가장 오래된 참조까지 일수), `history_search_steps`, `history_count_8obs` |
| 장점 | 결측일·관측부재를 건너뛰어 **coverage가 실제로 올라간다** |
| 한계 | 참조 시점이 행마다 달라져 **관측 신선도가 불균일**해진다. 오래된 관측을 끌어오면 오히려 나빠질 수 있다 |
| 비용 | 참조 파일 수가 늘어 bundle 크기가 커진다. 31일 창 기준 현재 370MB → 추정 2~3배 |

> `history_span_days`를 반드시 모델 입력에 넣는다. 그래야 "8개를 채웠지만 8개월 전 자료"인 행을
> 모델이 신선한 행과 구분할 수 있다.

### 후보 C — 유효 표본 수가 달라져도 처리하는 모델 구조

후보 B의 탐색을 쓰되, **표본 수가 1~8로 들쭉날쭉한 것을 모델이 정상 입력으로 받아들이게** 만든다.

두 가지 방식을 함께 비교한다.

- **C-1 요약통계 + 표본수 가중**: 평균·중앙값·표준편차·추세를 유효 표본만으로 계산하고,
  `history_count`, `history_span_days`, `history_freshness_days`를 명시 입력으로 준다.
  학습 시 표본 수별 가중치를 적용한다. 기존 LightGBM 구조를 유지할 수 있다.
- **C-2 표본 집합 입력**: (관측값, 경과일수) 쌍의 가변 길이 집합을 받아
  순서 무관 집계(평균·최댓값 풀링)로 요약하는 구조. 표본 수 변화를 구조적으로 흡수한다.
  다만 GPU 학습과 CPU 추론 bundle 구조가 모두 바뀐다.

| 항목 | 값 |
|---|---|
| 최대 탐색 기간 | 후보 B와 동일(D − 245일) |
| 누수 방지 | 후보 B와 동일 |
| 학습·추론 일치 | 집합 구성·정렬·패딩 규칙을 bundle에 고정한다. C-2는 `input_spec.json` 스키마 확장 필요 |
| 장점 | 표본 1~2개 구간까지 예측 대상에 포함 가능 |
| 한계 | C-2는 구조 변경 폭이 크고 추론 지연이 늘 수 있다. 검증 부담이 가장 크다 |

## 3. 평가 계획

### 3.1 데이터 분할

- 시간 순서로 **학습 70% / 테스트 30%**. 날짜 경계를 보존하고 실제 행 비율을 `split_dates.json`에 기록한다.
- 모델 선택용 내부 검증은 **학습 70% 안 뒤쪽 20%**에서만 뽑는다.
- 최종 학습에서 내부 검증을 다시 합치되, **재평가나 조기종료에 쓰지 않는다.**
- 테스트 30%는 학습·튜닝·후보 선택에 **일절 사용하지 않는다.**
- 네 후보(현행 v12 포함)는 **완전히 같은 분할·같은 행 집합**에서 비교한다.

### 3.2 필수 기준선 — 같은 테스트 구간에서 함께 측정

| 기준선 | 설명 |
|---|---|
| 전체 평균 | 학습 구간 전체 평균 |
| 노선별 평균 | route 단위 |
| **구간·시간대별 과거 중앙값** | **필수.** 현행 v12가 검증 MAE에서 이 기준선보다 1.57초(약 5.7%)밖에 앞서지 않았다 |
| 현행 v12 LightGBM | 재현 실행 |

**기준선을 테스트 구간에서도 반드시 산출해 같은 표에 넣는다.**
현행 v12는 기준선의 *테스트* 성적이 기록되어 있지 않아 실제 이득 폭을 확인할 수 없다. 이번에는 남긴다.

**어떤 후보도 기준선을 이기지 못하면 ML을 선택하지 않고 그대로 보고한다.**

### 3.3 필수 지표

전체 기준: MAE, RMSE, P95 절대오차, 평균 편향, 20초 이내 비율

분해 기준:

- 노선별 MAE
- 시간대별 MAE
- **유효 표본 수별 MAE** (1~3 / 4~7 / 8)
- **`history_span_days` 구간별 MAE** (후보 B·C의 신선도 저하 효과 측정)
- 미등록 ID 비율, edge 커버리지
- 3·5·10·20개 구간 합산 오차, 전체 경로 합산 오차

### 3.4 정상일 vs 결측일 성능 비교 (핵심 판정)

테스트 집합을 **참조 창에 결측이 있었는지**로 나눠 따로 집계한다.

| 그룹 | 정의 |
|---|---|
| G0 정상 | 8개 고정 지연 날짜가 모두 존재하고 해당 시간대 관측도 모두 있음 |
| G1 파일 결측 | 지연 날짜 중 파일 자체가 없던 행 |
| G2 관측 부재 | 파일은 있으나 OA-21217의 해당 시간대가 `0`이던 행 |
| G3 전무 | `history_sample_count = 0` |

판정 기준:

1. **G0에서 성능이 나빠지면 그 후보는 탈락**한다. 정상 구간을 희생해 결측 구간을 구제하지 않는다.
2. G1·G2에서 MAE 개선과 **coverage 증가량**을 함께 본다. coverage만 늘고 오차가 커지면 이득이 아니다.
3. G3는 후보 B·C만 값을 낼 수 있다. 여기서는 **기준선 대비 개선 여부**만 본다.
4. 후보별로 `history_span_days` 중앙값을 함께 보고한다. 신선도 대가를 숨기지 않는다.

### 3.5 coverage 보고 (성능과 분리)

성능과 별개로 다음을 후보별로 산출한다. 분모와 기간을 명시한다.

- edge-hour 기준 `history >= 1` / `>= 4` / `= 8` 비율
- 노선 단위로 **모든 edge-hour가 기준을 충족하는 노선 비율** (한 edge라도 되면 가능으로 세지 않는다)
- BUS step 단위 적용 가능 비율 (step의 모든 edge가 충족해야 가능)

현행 기준값(서비스일 2026-09-18, edge 87,196, edge-hour 2,092,704, 24시간):

| 지표 | 현행 v12 |
|---|---:|
| `history >= 1` | 69.9% |
| `history >= 4` | 66.8% |
| `history = 8` | 53.2% |
| 모든 edge-hour 충족 노선 (05~23시) | 9.9% (132 / 1,332) |

### 3.6 bundle 비용 검증

후보 B·C는 참조 날짜 범위가 넓어진다. 아래를 함께 보고한다.

- 31일 지원 창 기준 bundle 크기
- 컨테이너 기동 시 SHA 검증 시간
- 단건 추론 지연(p50/p95)
- 참조 캐시 적중률

크기나 지연이 운영 한도를 넘으면 성능이 좋아도 채택하지 않는다.

## 4. 진행 순서 (승인 후)

1. 세 후보의 탐색·특성 생성 함수를 **기존 v12 코드와 분리된 새 실험 경로**에 작성
   (`/home/j-j15e202/ybk/` 아래 날짜·목적이 분명한 신규 작업공간. `j-moo`와 기존 실험 폴더는 읽기 전용)
2. 소규모 표본으로 누수 검사 — 각 행의 참조 날짜가 모두 `D − 77` 이하인지 전수 확인
3. 학습·추론 함수가 같은 참조 날짜를 고르는지 동등성 시험
4. 내부 검증으로 후보 선택
5. 테스트 구간에서 기준선과 함께 최종 측정
6. coverage·bundle 비용 보고
7. 결과 보고 후 채택 여부 결정

**현재 단계에서는 1번도 시작하지 않았다.** 이 문서는 계획이다.

## 5. 이 개선안으로 해결되지 않는 것

- 공급처 원천 결측 11건은 어떤 후보로도 복구되지 않는다. 탐색으로 **우회**할 뿐이다.
- `production_ready=false` 상태는 이 작업으로 바뀌지 않는다. 별도 승인 정책이다.
- 버스 대기·지하철·환승·도보는 이 모델의 대상이 아니다.
- 현행 순차 호출의 `ML_BUDGET_EXHAUSTED` 문제는 별도 과제다. coverage를 올려도 호출이 안 되면 적용되지 않는다.
