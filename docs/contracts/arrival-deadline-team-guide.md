# 조건부 출발 추천 — 세 파트 팀 실행 가이드

- 목적: BE/ML, FE, DATA가 같은 사용자 흐름을 나누어 구현하고 연결하는 순서·인계·완료 기준을 정한다.
- 상태: 작업 계획. 실제 데이터 확보·구현·테스트·배포 완료 보고가 아니다.

새 작업자는 통합 계약→자기 파트 가이드→관련 원천/계산 상세 순서로 읽는다. 공개 필드명은 통합 계약과 공통 구현 계획 2.2절을 따른다. 실행 코드가 문서와 다르면 현재 구현/목표 변경을 이슈에 나란히 적고 호환 작업을 포함한다.

## 2. 담당 경계와 기존 작업 ID 연결

| 파트 | 주 책임 | 기존 작업 ID | 타 파트에 직접 넘길 결과 |
|---|---|---|---|
| BE/ML | 일정 DB, 외부 경로/도보, 후보 매핑 소비, 여정 계산, 버스 모델, 출발 정책, scheduler/outbox, 이동 상태 | C01,B01,B02,B02-W,M01,B03,N01,J01 서버 | FE API/fixture, DATA 수집 demand·소비 계약 |
| FE | 입력/편집/반복, 결과/경로/품질, 수락, 알림 딥링크, 이동 동의/상태 | C01,F01,J01 앱 | 입력/화면 시나리오, API 연동·오류 재현 |
| DATA | 원천 신청·확보, 수집, 정규화, 마스터 artifact, 사건/상태, fact/baseline, 보존/Replay | C01,D01,D02,D03,O01 데이터 | BE/ML source register·schema·artifact·품질 보고 |

공동 작업 C01은 BE가 공개 API 초안, DATA가 원천/서빙 초안, FE가 화면 소비 검증을 제출한다. 별도 인프라 담당에게는 각 파트의 배포 인터페이스/자원 요청을 모아 전달한다. DATA가 `infra/`, Docker, CI 파일을 대신 수정하지 않는다.

## 3. 첫 착수 때 각 파트가 할 일

### BE/ML

1. BM01 DTO/DB 변경과 공통 v2 schema/fixture를 준비한다.
2. DATA에 필요한 노선/역/링크 scope와 시간·ID 필드를 전달한다. ‘실시간 전부 주세요’로 요청하지 않는다.
3. 운영 데이터가 없어도 합성 snapshot으로 P 유지/조건부 탐색을 검증한다.
4. ML 원본·정답·현재 HTTP feature를 대조하고 미확보 입력을 목록화한다.

### FE

1. v2 fixture로 DTO와 상태별 화면을 만든다. 운영 API/실시간 확보 완료를 기다리며 전체 작업을 멈출 필요는 없다.
2. 사용자 P/D·반복 전날 출발·편집·수락 흐름을 BE에 전달한다.
3. null/stale/preview/409/네트워크 실패를 정상 화면처럼 구체적으로 설계한다.

### DATA

1. 원천 가이드 0절을 source별 확보 이슈로 나눈다.
2. 키 승인·샘플·원본 SHA·지원 범위·관측시각·실제 최신성 증거를 기록한다.
3. 미확보 열차 대응/실측/통제 종료는 즉시 의존 작업에 알린다. 내부 요구 필드를 원천 제공 필드로 바꾸어 쓰지 않는다.
4. 확보된 source부터 raw/normalized fixture와 버전 artifact를 BE/ML에 전달한다.

## 4. 통합 구현 순서와 단계별 통과 조건

| 단계 | BE/ML | FE | DATA | 함께 확인할 결과 |
|---|---|---|---|---|
| 1 계약·확보 점검 | v2/정책 fixture | DTO/화면 상태 검토 | source register/필드 검토 | 이름·단위·null·확보 상태 합의 |
| 2 최소 흐름 | 일정 저장→합성 후보→P 비교→결과 조회 | 입력→계산 중→결과 표시 | fixture·기존 artifact 검증 | 08:59 유지/09:00 조정 E2E |
| 3 실제 후보 | 카카오 분해·매핑·도보 fallback | 경로 상세/출처 표시 | node/edge/좌표 artifact | 비용 중복 없는 접근/환승/이탈 |
| 4 실시간 결합 | 버스/지하철 timeline·ML 범위 | 누락/stale/preview 표시 | 수집/latest/시간표/매핑 | 놓친 차량·환승·하차예측 누락 |
| 5 변경 대응 | D tick·사건 wake·revision·outbox | 수락/알림/응답 역전 | incident/impact/poll 상태 | 같은 사건 중복·실패/해제 구별 |
| 6 이동·재현 | 이동 상태/남은 여정 | 출발/동의/도착 | 고정 입력 Replay | 야간·막차·장애·재시작 |
| 7 제한 활성화 | 기능별 gate/기존 호환 | 실제 지원 범위 안내 | 쿼터/coverage/운영 지표 | 통과한 기능·범위만 운영 |

단계 4에서 실제 데이터가 막히면 단계 2의 fixture 결과를 실제 정확도 검증으로 표시하지 않는다. 대체 구현은 PROVIDER_TOTAL/시간표 추정/정보 부족처럼 사용자 결과에 근거가 드러나야 한다.

## 5. 파트 간 인계 패키지

### DATA → BE/ML

- sourceId/officialUrl/서비스명/권한·쿼터/확보 상태
- raw→정규화 컬럼·타입·단위·원천시각·ID namespace
- 정상/빈/오류/부분/stale/순서역전 fixture
- master/crosswalk/timetable version·SHA·적용일·coverage·미매핑 이유
- Redis key/TTL/validUntil, Kafka schema/key/revision, 실제 수집간격/age
- ML 정답 정의·기간·표본·결측·발표시각·학습/예측 가능성

### BE/ML → FE

- v2 schema와 상태별 전체 응답 fixture
- 등록/수정/반복/최신 조회/재평가/수락/출발/이동/도착 API
- P/추천/실제 출발의 소유권, 품질·수락 허용조건, 오류·만료 처리
- 경로 leg/geometry 표시 계약, 원인 설명과 알림 payload

### FE → BE/ML 및 공동 검증

- 실제 요청 예제와 화면 시나리오
- 요청 순서역전·편집/수락 경쟁·네트워크 복구 재현
- null·preview·stale·오래된 알림·자정 표시 결과

인계는 링크만 전달해서 끝내지 않는다. 소비자가 fixture를 읽고 동일 ID/시각/단위와 실패 상태를 재현해야 완료다. 원천 키·개인 위치·사용자 제목이 담긴 실자료를 테스트 저장소에 그대로 넣지 않는다.

## 6. 작업 이슈 작성 양식

각 BM/FE/DA 작업을 다음 형식으로 작성한다. 이번 문서는 실제 Jira 이슈를 생성하지 않는다.

```text
작업 ID / 제목:
사용자가 겪는 문제와 완료 후 동작:
주 담당 파트 / 검토할 소비 파트:
선행 데이터: sourceId, 공식 출처, 확보 상태, 부족 필드
변경 파일/클래스/메서드: 기존 수정 / 추가 / 대체 구별
입력: 필드, 단위, 시간, ID/버전, nullable
처리: 1 → 2 → 3 단계와 판정식
출력/저장: API/DB/Kafka/Redis/artifact
실패: 결측/stale/중복/순서역전/권한/timeout/fallback
인수 시험: 입력 fixture와 기대 결과
인계: 받을 파트와 schema/예제/보고서
활성화 조건 / 미확보 시 제한:
```

예: ‘버스 실시간 연동’ 대신 ‘S03 mkTm+exps를 절대 ETA로 정규화하고 BE 정류장 도착 이후 첫째/둘째 차량 선택에 연결’로 작업을 정의한다. DATA는 정상화·신선도, BE는 차량 선택·환승 결과, FE는 결과/품질 표시를 각각 완료한다.

## 7. 막힌 작업 처리와 계약 변경

데이터 미확보, 실제 필드 부재, 키/쿼터 부족, ID 대응 실패, 운영자 범위 밖을 서로 다른 blocker로 기록한다. 다음에 해야 할 확인·owner·완료 증거·제한 기능을 함께 적는다. 날짜만 적은 ‘추후 처리’로 남기지 않는다.

계약 필드/enum/단위를 바꿀 때는 생산자와 소비자를 찾고 통합 계약→기계 schema/fixture→adapter→양쪽 테스트를 한 변경 계획에 묶는다. 사소한 명칭 변경도 기존 저장 result_json과 구버전 앱 조회를 고려한다. 원천이 안 준 값을 내부에서 계산한다면 산식·입력 범위·근거를 명시한다.

새 feature가 목표 목록에 있다고 ML 입력에 바로 넣지 않는다. 학습/예측 양쪽의 데이터 확보와 같은 전처리가 확인돼야 한다. 공개 API가 있다는 사실만으로 운영 수집 완료에 체크하지 않는다.

## 8. 공동 QA 시나리오와 증거

| 시나리오 | 기대 | 제출 증거 |
|---|---|---|
| P08:30,D09:00,ETA08:59:59 | P 유지·buffer0 | 정책 결과+FE 화면 |
| ETA09:00,08:20 출발→08:50 | T equality 성공·600초 한 번 | timeline+응답+FE 비교 |
| 도보 보강 후 환승 실패 | 다음 차량·전체 ETA 변경 | 후보/도보/차량 fixture |
| 반대 방향/부분 통제 | 임의 차단/지연 가산 없음 | 사건/매핑/통과시간 |
| 수집 실패와 사건 만료 | 정상/해제 오판 없음 | poll 상태→BE→FE |
| 시간표 열차 ID 불일치 | 실시간 결합 거부 | crosswalk 상태+fallback |
| 수정 중 이전 평가 완료 | 저장·수락·화면 역전 없음 | revision/요청 순서 로그 |
| 알림 재시도와 출발 | 중복 억제·옛 출발 권고 취소 | outbox 상태+앱 표시 |
| 같은 manifest Replay | 결과/원인/정책 재현 | 입력/출력 hash와 diff |

실행 시 Backend는 Maven, FE는 Flutter 테스트, DATA/ML은 해당 디렉터리 pytest를 사용한다. 실제 API를 무제한 호출하는 테스트로 대신하지 않는다. 테스트 미실행은 이유와 범위를 PR에 남긴다.

## 9. PR·리뷰·완료 기준

작업 전 Jira Task/브랜치/기존 변경 범위를 확인한다. 데이터 트랙은 저장소의 feature/dt/Jira 관례와 dt/dev 대상 검토를 따르며 다른 파트는 해당 파트 브랜치 정책을 확인한다. 문서 작업의 MR 생성이 구현 코드 배포 승인으로 이어지지 않는다.

PR에는 문제→변경 동작, 수정 파일/계약, 데이터 확보 증거·미확보 항목, 테스트 결과, 소비 파트 인계, fallback/활성화 조건을 적는다. 최소 1명 리뷰와 CI 통과 후 병합하며, 원본·DB 이력·사용자 미커밋 변경을 정리 명목으로 삭제하지 않는다.

완료는 세 단계로 구분한다: **계약/fixture 완료 → 코드 연동 검증 완료 → 실제 데이터 범위의 운영 검증 완료**. 단계가 다른 결과를 모두 ‘구현 완료’로 묶지 않는다. 최종적으로 사용자가 P/D를 입력하고, 근거 있는 추천을 보고, 수락/출발/변경 알림까지 일관되게 이용할 수 있는지 통합 확인한다.
