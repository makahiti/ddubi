## A. `result` 판정 경계 🔴

명세서는 `result` 가 `ON_TIME | TIGHT | LATE_RISK` 라고만 하고 **무엇이 TIGHT 인지 말하지
않습니다.** 목표 4분 전 도착이 성공인지 아슬아슬인지 서버가 정해야 합니다.

### 정한 기준 (2026-09-04)

```
actual_arrival ≤ arrive_by − 10분   → ON_TIME
arrive_by − 10분 < actual ≤ arrive_by → TIGHT
actual_arrival > arrive_by          → LATE_RISK
```

10분인 이유: 대중교통 배차 간격의 통상 하한이 이 근처라, 그보다 여유가 적으면 **한 대만
놓쳐도 지각**입니다. "성공했지만 운이 좋았다"를 성공으로 세면 리포트가 실제보다 낙관적으로
보입니다.

**설정값으로 뺍니다** — `ddubi.report.on-time-margin: 10m`. 데이터가 쌓인 뒤
조정할 값이지 코드에 박을 값이 아닙니다.

### 집계와의 관계

`report` 는 `on_time_est` 와 `delayed_est` 두 칸뿐입니다. **TIGHT 은 어느 쪽에도 넣지
않습니다.**

```
total_schedules = 전체 건수
on_time_est     = ON_TIME 건수
delayed_est     = LATE_RISK 건수
(TIGHT = total − onTime − delayed 로 프론트가 계산 가능)
```

TIGHT 을 정시에 넣으면 위와 같은 낙관 편향이 생기고, 지연에 넣으면 지각한 적 없는 사용자에게
"지연 3건"이 표시됩니다. 둘 다 사실이 아닙니다.

> **명세서에 위 세 줄과 "TIGHT 은 두 집계 어디에도 포함되지 않는다"를 넣어 주세요.**

## B. 추천 의존 필드는 Phase 3 까지 null 🔴

명세서 §9.1 은 ARRIVAL-001 처리를 "최신 추천으로 `planned_depart` 결정" 이라고 씁니다.
추천 엔진(Phase 3, 김종무)이 아직 없으므로 그대로는 구현이 막힙니다.

**그런데 핵심인 `result` 는 추천이 없어도 나옵니다.** 목표 시각과 실제 도착만 있으면 됩니다.
둘 다 이미 있는 값입니다. `report_detail` 의 추천 의존 컬럼이 **전부 NULL 허용**이라
비워둬도 스키마가 성립합니다.

| 필드 | 지금 | Phase 3 이후 | 출처 |
| --- | --- | --- | --- |
| `result` | **계산됨** | 그대로 | `arrive_by` vs `actual_arrival` |
| `actualArrival` | **저장됨**(동의자) | 그대로 | 앱 지오펜스 |
| `plannedDepart` | `null` | 채움 | `recommendation.depart_at` |
| `proxyDurationMin` | `null` | 채움 | 구간 실적 합산 |
| `proxyArrival` | `null` | 채움 | 위와 동일 |
| `mainCause` | `null` | 채움 | `recommendation.reasons` |

> **프론트 요청:** 위 4개는 **당분간 항상 null 로 옵니다.** 화면에서 null 을 빈 값으로
> 처리해 주세요. 나중에 값이 생겨도 계약은 바뀌지 않습니다.

> **명세서 요청:** 각 필드에 "Phase 3 이전 null" 을 표기해 주세요.

## C. `locationConsent` 요청 필드의 효력 🔴

### 지금 문서가 서로 다른 말을 합니다

| 출처 | 내용 |
| --- | --- |
| 명세서 §9.1 | Request 에 `locationConsent` 가 있다 |
| `BACKEND_CONVENTION.md` 6.4-9 | "요청 필드는 **쓰지 않는다** — 서버가 `user.history_consented_at` 으로 판단" |

규칙 9 는 제가 ERD 를 읽고 적어둔 메모인데, **필드를 아예 무시하면 명세서에 있는 입력이
사문화**됩니다.

### 정한 것 — 둘 다 있어야 저장한다 (AND)

```
actual_arrival 저장 조건:
    user.history_consented_at IS NOT NULL     ← 계정 동의 (서버가 가진 사실)
  AND request.locationConsent == true          ← 이번 이동에 대한 의사
```

- **계정 동의가 없으면 요청 필드가 true 여도 저장하지 않습니다.** 규칙 9 가 막으려던 것이
  이것입니다 — 클라이언트가 보낸 값만으로 위치 기록이 남으면 계정 동의가 무의미해집니다.
- **계정 동의가 있어도 요청이 false 면 저장하지 않습니다.** 평소엔 동의했지만 이번엔
  기록을 남기고 싶지 않은 경우, OS 위치 권한을 껐다 켠 경우가 실제로 있습니다.

즉 요청 필드는 **권한을 주는 스위치가 아니라 이번 건에 대한 거부권**입니다.

**저장하지 않아도 요청은 200 입니다.** `actualArrival: null` 로 응답하고 일정은 DONE 이
됩니다. 미동의를 오류로 만들면 앱이 일정을 영영 종료하지 못합니다.

> `actualArrival` 없이는 `result` 도 계산할 수 없으므로 함께 null 입니다.
> 미동의 사용자는 "몇 건 이동했다"까지만 리포트에 남습니다.

> **명세서 요청:** §9.1 Request 설명에 위 AND 조건과 "미동의 시에도 200" 을 넣어 주세요.
> **규칙 9 도 이 내용으로 고치겠습니다**(현재 문구는 필드를 무시한다고 되어 있음).

## D. 같은 일정을 두 번 보고하면 🟡

명세서에 없습니다. 앱이 재시도하거나 사용자가 도착 확인 화면을 두 번 누르면 반드시 생깁니다.

### 정한 것 — 행을 새로 만들지 않고 갱신한다

일정 하나의 이동 결과는 하나여야 합니다. 두 번 보고했다고 리포트가 2건으로 세면 통계가
틀립니다. 기존 `report_detail` 을 찾아 `actual_arrival`·`result` 만 갈아끼우고,
`reportDetailId` 는 **같은 값**을 돌려줍니다.

이미 `DONE` 인 일정에 다시 보고해도 **409 가 아니라 200** 입니다. 실패시키면 클라이언트가
재시도할 방법이 없습니다(알림 읽음 처리와 같은 판단 — NTF-003).

> **명세서 요청:** §9.1 에 "멱등 — 재보고 시 기존 결과를 갱신하고 200" 을 넣어 주세요.

## E. HISTORY-001 응답에 요약을 추가 제안 🟡

현재 명세서는 목록만 줍니다. 그런데 화면(DDB-012)은 목록 위에 **"이번 달 12건 · 평균 42분 ·
정시 75%"** 같은 요약을 보여줍니다.

목록만 주면 프론트가 페이지마다 부분합을 내야 하는데, **페이지네이션 때문에 불가능**합니다
(1페이지 20건으로 낸 평균은 전체 평균이 아닙니다).

### 추가 제안

```json
GET /history?from=2026-09-01&to=2026-09-30&page=0&size=20
{
  "summary": {
    "totalCount": 12,
    "onTimeCount": 9,
    "tightCount": 2,
    "lateCount": 1,
    "onTimeRate": 0.75,
    "avgDurationMin": 42        // proxy_duration_min 평균, Phase 3 이전 null
  },
  "content": [ ... ],
  "page": { "number": 0, "size": 20, "totalElements": 12, "totalPages": 1 }
}
```

`unreadCount` 를 알림 목록에 함께 실은 것과 같은 판단입니다(§8.1). 한 화면을 그리는 데
호출을 두 번 하게 만들 이유가 없습니다.

**`avgDurationMin` 은 Phase 3 이전 null** 입니다(B 참조).

> **명세서 요청:** §9.2 Response 에 `summary` 를 추가해 주세요.

## F. 리포트 기간 단위·경계 🟡

명세서는 `periodStart`/`periodEnd` 만 있고 **주간인지 월간인지, 주의 시작이 월요일인지
일요일인지** 없습니다.

### 정한 것

- **주간 고정.** `UNIQUE(user_id, period_start, period_end)` 가 이미 있어 기간 단위를
  섞으면(주간 행과 월간 행 공존) 집계가 중복됩니다.
- **월요일 시작 ~ 일요일 종료.** `LocalDate` 의 ISO-8601 기본값이고 한국 달력 표기와도 같습니다.
- 어느 주에 속하는지는 **`schedule.arrive_by` 기준**입니다(보고 시각이 아님). 자정 직전
  일정을 새벽에 보고해도 원래 주에 들어갑니다.
- `computed_at` 은 **마지막으로 다시 센 시각**입니다. 도착 보고가 들어올 때마다 갱신됩니다.

### HISTORY 와 REPORT 의 기간 기준이 다릅니다 — 의도된 것입니다

| | 기준 |
| --- | --- |
| REPORT-001 목록 | 리포트 **주차**(월~일)와 겹치는 것 |
| HISTORY-001 목록 | 개별 **일정의 `arrive_by`** 가 구간 안에 있는 것 |

사용자는 이동 기록을 "지난주 화요일에 어디 갔더라"로 찾지 집계 주차로 찾지 않습니다.
리포트는 반대로 주 단위가 단위 자체입니다.

> **명세서 요청:** §9.3 에 "주간(월~일), `arrive_by` 기준 귀속" 을 넣어 주세요.

## ERD 변경 제안 — `report_detail` 에 UNIQUE(schedule_id) 🟡

D 의 "일정 하나에 결과 하나"를 **코드에서만 지키고 있습니다.** 동시에 두 번 보고가 들어오면
(앱 재시도 + 사용자 재탭) 둘 다 "기존 행 없음"을 보고 각자 INSERT 해 행이 2개가 됩니다.

```sql
ALTER TABLE report_detail ADD UNIQUE KEY UK_RDETAIL_SCHEDULE (schedule_id);
```

주간 리포트는 서로 겹치지 않고 일정의 `arrive_by` 는 하나뿐이므로, **한 일정은 정확히 한
리포트에만 속합니다.** 제약을 걸어도 막히는 정상 케이스가 없습니다.

`report`·`report_detail` 은 서비스 백엔드 소유 테이블이라 제가 `docs/ddubi_erd_v2.sql` 과
`V1__init.sql` 에 함께 반영하겠습니다. **다른 팀 작업에 영향이 없습니다.**
