# 명세 개정 — 소셜 로그인 계정 연동 (AUTH-003)

> 요청: 프론트, 2026-09-10 · 구현: 백엔드 · 대상 화면: 기존 계정 발견 안내 / 비밀번호 확인 / 연동 완료

## 왜 바꾸나

지금까지는 소셜 이메일이 기존 계정과 같으면 **묻지 않고** 그 계정에 붙였다.
제공자가 이메일 소유를 잘못 확인한 순간, 남의 계정으로 그대로 들어간다.
이제 **기존 계정의 비밀번호로 소유를 증명**해야 붙는다.

---

## 1. 소셜 로그인 응답이 두 갈래가 된다

대상: `POST /auth/oauth`, `POST /auth/oauth/token`, `POST /auth/oauth/id-token` **전부**

```json
{
  "success": true,
  "data": {
    "status": "ACCOUNT_LINK_REQUIRED",
    "linkToken": "3Qk1_9vZ...",
    "provider": "NAVER",
    "email": "us***@naver.com"
  },
  "timestamp": "...", "requestId": "..."
}
```

| `data.status` | 언제 | HTTP |
| --- | --- | --- |
| `AUTHENTICATED` | 이미 연결된 소셜이거나 완전 신규 | 200 (신규 201) |
| `ACCOUNT_LINK_REQUIRED` | 같은 **검증된** 이메일의 기존 계정이 있다 | 200 |

`AUTHENTICATED` 일 때는 `data.tokens` 에 기존과 같은 토큰 묶음이 들어간다.

### 요청하신 형태와 다른 점

요청은 `{"code": "ACCOUNT_LINK_REQUIRED", "data": {...}}` 였다.
우리 공통 래퍼가 `{success, data, error, timestamp, requestId}` 라(명세서 v2.1.1 §2)
최상위에 `code` 를 둘 자리가 없다. 그리고 **이건 오류가 아니라 흐름의 다음 단계**다 —
`error` 로 주면 프론트 공통 오류 처리기가 "로그인 실패" 로 삼키고, 오류 본문에는
`linkToken` 을 실을 자리도 없다.

**분기 지점만 `data.status` 로 옮겨졌다.**

---

## 2. 연동 확정 API (신규)

```
POST /api/v1/auth/oauth/link
```

```json
{ "linkToken": "3Qk1_9vZ...", "password": "기존 이메일 계정 비밀번호", "deviceId": "dev-1" }
```

성공하면 `AuthTokenResponse` — 로컬 로그인과 같은 모양이다.

### 소셜 액세스 토큰을 다시 보내지 않는다

요청하신 대로다. 누구를 어디에 붙일지는 서버가 `linkToken` 으로 Redis 에 들고 있다.
프론트는 **불투명한 티켓** 하나만 화면 사이로 넘기면 된다.

| | |
| --- | --- |
| 수명 | **5분** |
| 사용 | **한 번**. 성공·실패와 무관하게 소비된다 |
| 담긴 것 | 기존 userId, provider, 소셜 회원번호. **소셜 토큰은 없다** |

실패해도 소비하는 이유: 살려 두면 이 화면이 **비밀번호 대입 창구**가 된다.
다시 하려면 소셜 로그인부터 거쳐야 한다.

## 3. 예외

| 상황 | HTTP | code |
| --- | --- | --- |
| 비밀번호 불일치 | 401 | `LINK_PASSWORD_MISMATCH` |
| 티켓 만료·재사용·위조 | 401 | `LINK_TOKEN_INVALID` |
| 그 소셜이 다른 사용자에게 연결됨 | 409 | `SOCIAL_ALREADY_LINKED` |
| 기존 계정에 비밀번호가 없음 | 409 | `ACCOUNT_LINK_UNAVAILABLE` |

### ⚠️ 네 경우 모두 "소셜 로그인부터 다시" 입니다

**비밀번호가 틀려도 티켓은 이미 소비됐습니다.** 입력창만 비우고 재시도시키면 안 됩니다 —
그 티켓으로는 무엇을 넣어도 `LINK_TOKEN_INVALID` 가 돌아옵니다.

코드를 나눈 것은 **원인을 알려 주기 위해서**지 복구 방법이 달라서가 아닙니다.
`LINK_PASSWORD_MISMATCH` 는 "비밀번호가 틀렸다" 를 사용자에게 알려 주되,
버튼은 **소셜 로그인 화면으로** 보내야 합니다.

> 초기 명세에 "불일치면 비밀번호만 다시 입력" 이라고 적었던 것은 잘못입니다.
> 구현(실패 시에도 티켓 폐기)과 어긋났고, 리뷰에서 지적받아 바로잡았습니다.

### ⚠️ "비밀번호가 없는 기존 계정" 처리가 요청과 다릅니다

요청: *"기존 소셜 로그인 후 마이페이지에서 연동하도록 안내"*

**새 계정을 만들 수 없습니다.** `user.email` 에 `UNIQUE KEY UK_USER_EMAIL` 이 걸려 있어
같은 이메일로 두 번째 사용자를 만들면 `Duplicate entry` 로 500 이 납니다.
이메일을 비워 만들 수는 있지만, 그러면 사용자는 **자기 일정이 사라진 빈 계정**을 봅니다.

그래서 **로그인 자체를 거절하고 안내**합니다.

```
409 ACCOUNT_LINK_UNAVAILABLE
"이 이메일은 GOOGLE 로 가입되어 있습니다. 해당 방식으로 로그인한 뒤
 마이페이지에서 NAVER 을(를) 연결해 주세요."
```

메시지에 **실제로 그 계정에 붙어 있는 제공자 이름**이 들어갑니다.
그 화면은 "새 계정으로 진행" 이 아니라 **"다른 소셜로 로그인"** 안내여야 합니다.

> 마이페이지 연결·해제는 아래 3-2·3-3 참고.

## 3-2. 마이페이지 소셜 연결 (신규)

```
POST /api/v1/auth/social-links      ← 로그인 필요
```

```json
{ "provider": "NAVER", "accessToken": "..." }     // GOOGLE 은 idToken
```

`ACCOUNT_LINK_UNAVAILABLE` 안내를 받은 사용자가 오는 곳입니다.

**비밀번호를 묻지 않습니다.** 이미 그 계정으로 인증된 상태이고, 되물으면 **비밀번호가
없는 사용자**는 영영 연결하지 못합니다 — 그들이 바로 이 화면의 대상입니다.

응답은 연결 후 그 계정의 **전체** 로그인 수단입니다.

```json
{ "success": true, "data": { "providers": ["GOOGLE", "NAVER"] } }
```

방금 붙인 것만 주면 화면을 다시 그리려고 또 조회해야 합니다. 그리고 이 목록은 "이 계정으로
들어올 수 있는 문이 몇 개인가" 이기도 해서, 나중에 해제 버튼을 보여줄지 판단하는 근거가 됩니다.

| 상황 | HTTP | code |
| --- | --- | --- |
| `accessToken`·`idToken` 둘 다 없음 | 400 | `INVALID_REQUEST` |
| 그 소셜이 다른 사용자에게 연결됨 | 409 | `SOCIAL_ALREADY_LINKED` |
| 같은 제공자의 **다른** 계정이 이미 연결됨 | 409 | `SOCIAL_PROVIDER_ALREADY_BOUND` |

이미 내게 연결된 소셜을 다시 보내면 **오류가 아니라 200** 입니다(멱등).

`UK_UAUTH_USER_PROVIDER (user_id, provider)` 때문에 한 사용자에게 제공자당 한 계정만
붙습니다. 다른 카카오 계정이 이미 있으면 조용히 갈아치우지 않고 409 를 줍니다 —
갈아치우면 원래 그 계정으로 로그인하던 사람이 어느 날 못 들어옵니다.

## 3-3. 마이페이지 소셜 해제

```
DELETE /api/v1/auth/social-links/{provider}      ← 로그인 필요
```

응답은 해제 후 **남은** 로그인 수단입니다.

```json
{ "success": true, "data": { "providers": ["LOCAL"] } }
```

### ⚠️ 마지막 하나는 뗄 수 없습니다

떼는 순간 **사용자가 자기 계정에서 잠깁니다.** 되돌릴 방법도 없습니다 — 들어갈 수가 없으니
다시 연결할 화면에도 못 갑니다. 계정을 없애려는 것이면 `DELETE /users/me`(탈퇴)가 맞는 길입니다.

**프론트: 남은 수단이 하나면 해제 버튼을 비활성화**해 주세요. 연결·해제 응답이 매번 전체
목록을 주므로 그 값으로 판단하시면 됩니다. 서버도 막지만, 누를 수 있는 버튼을 누르고 오류를
받는 것보다 처음부터 못 누르는 편이 낫습니다.

| 상황 | HTTP | code |
| --- | --- | --- |
| 연결돼 있지 않음 | 404 | `SOCIAL_LINK_NOT_FOUND` |
| `LOCAL` 을 지정 | 400 | `INVALID_REQUEST` |
| 마지막 남은 수단 | 409 | `LAST_LOGIN_METHOD` |

`LOCAL` 은 이 API 로 해제할 수 없습니다. 비밀번호 로그인을 없애는 것은 성격이 다른 일이라
(다시 만들려면 이메일 인증부터 해야 합니다) 같은 문으로 처리하지 않습니다.

**세션은 건드리지 않습니다.** 토큰은 사용자에게 발급된 것이지 제공자에게 발급된 것이
아니라, 카카오 연결을 뗐다고 쓰던 앱에서 튕겨 나갈 이유가 없습니다.

### 동시 요청 (2026-09-14 보강)

두 요청이 동시에 오면 **행 잠금으로 직렬화**합니다. 서로 다른 소셜을 동시에 해제해도
**하나는 반드시 남습니다** — 뒤에 온 요청은 다시 읽고 409 를 받습니다.

> 처음 구현은 "읽고 → 세고 → 지운다" 라서 수단이 둘뿐인 사용자가 서로 다른 제공자를
> 동시에 해제하면 **둘 다 통과해 로그인 수단이 0개**가 됐습니다. 리뷰에서 잡혔고,
> 지금은 동시 요청 테스트로 고정돼 있습니다.

⚠️ **프론트: 화면에 수단이 둘로 보이는데 `LAST_LOGIN_METHOD` 가 올 수 있습니다.**
다른 기기·탭에서 방금 하나가 빠진 경우입니다. 오류를 그대로 띄우지 말고 **목록을 다시 받아
화면을 갱신**해 주세요. 응답이 항상 전체 목록을 주는 이유이기도 합니다.

`SOCIAL_LINK_NOT_FOUND` 는 `USER_NOT_FOUND` 와 **반드시 구분**해 주세요. 같은 404 라도
뜻이 정반대입니다 — 사용자는 멀쩡하고 연결만 없는 것이라, 로그아웃시키면 안 됩니다.

## 4. 이메일 검증 기준

연동 후보로 삼는 것은 **제공자가 소유를 확인해 준 이메일**뿐이다.

| | 판단 |
| --- | --- |
| 카카오 | `kakao_account.is_email_verified` |
| 구글 | `email_verified` (boolean·문자열 둘 다 처리) |
| **네이버** | **검증된 것으로 본다** — 프로필 API 에 플래그가 없다 |

네이버에 플래그가 없어서 `false` 로 두면 네이버 사용자는 연동을 영영 못 한다.
위험하지 않은 이유는 **연동에 기존 계정 비밀번호가 필요**하기 때문이다.
남는 위험은 "그 이메일로 계정이 있다"는 사실이 마스킹된 형태로 노출되는 것뿐이다.

**미검증 이메일은 새 계정에도 저장하지 않는다.** 저장하면 `UK_USER_EMAIL` 을 차지해
진짜 주인이 그 이메일로 가입하지 못한다.

## 5. 이메일 마스킹

```
user@naver.com  →  us***@naver.com
ab@naver.com    →  a***@naver.com
a@naver.com     →  ***@naver.com
```

도메인은 가리지 않는다. 사용자가 "아 그 네이버 계정" 하고 알아볼 단서가 없으면
연동할지 판단할 수 없다.
