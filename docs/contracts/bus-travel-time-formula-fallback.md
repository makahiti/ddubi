# 버스 구간 소요시간 수식과 적용 계약

## 1. 목적과 적용 우선순위

버스 ML은 현재 서울 공식 ID와 서울 학습 bundle만 지원한다. ML 호출 실패, 시간 초과,
이력 표본 부족, 운영 계약 미충족 또는 SHADOW 모드에서는 카카오가 제공한 BUS step 시간만
사용했기 때문에, 확보한 서울 실측 기준값을 사용할 기회가 없었다. 경기·인천·부산은 서울
학습 범위 밖이므로 서울 모델 숫자를 그대로 적용하면 지역 일반화가 검증되지 않은 값을
실측처럼 사용하게 된다.

서비스는 한 번 탑승하는 BUS step마다 다음 순서로 시간을 선택한다.

| 적용 구간 | 1순위 | 2순위 | 최종 fallback |
|---|---|---|---|
| 서울 `SEOUL_BUS` | 검증된 서울 ML | 서울 실측 기반 구간·요일·시간대 기준값 | 카카오 BUS step 시간 |
| 경기 `GBIS` | GTFS 구간·시간대 계산 완료값 | 없음 | 카카오 BUS step 시간 |
| 인천 `INCHEON_PUBLIC_CSV` | GTFS 구간·시간대 계산 완료값 | 없음 | 카카오 BUS step 시간 |
| 부산 `BUSAN_GTFS` | 부산 GTFS 전용 계산 완료값 | 없음 | 카카오 BUS step 시간 |

지역은 현재 차량 위치나 정류장 좌표로 판단하지 않는다. 활성 마스터가 발급한 namespace와
canonical route/stop component로 판단한다. 서울 버스가 경기도 정류장을 지나더라도
`SEOUL_BUS` 노선이면 서울 흐름을 사용한다.

한 BUS step을 구성하는 모든 인접 edge가 같은 방식으로 계산될 때만 step 전체 시간을
교체한다. 한 edge라도 미매핑·결측·모호·시간대 불확실·버전 불일치이면 일부 수식값과
카카오 시간을 섞지 않고 BUS step 전체를 카카오 원본시간으로 되돌린다.

## 2. 왜 수식을 사용하는가

서울 ML은 학습 ID·지원 날짜·이력 표본·모델 버전·응답 시간 등 여러 조건을 모두 만족해야
적용할 수 있다. 이 조건을 만족하지 못해도 서울에는 실제 운행 집계로 만든 설명 가능한
기준값이 있다. 이를 건너뛰고 바로 카카오 step으로 돌아가면 확보한 구간별 시간대 패턴을
사용하지 못한다.

경기·인천·부산은 실제 날짜별 구간 운행시간을 아직 확보하지 못했다. 이런 상태에서 GTFS를
정답으로 ML을 학습하면 실제 지연을 배우는 것이 아니라 시간표 패턴을 복잡한 모델로 다시
재현하게 된다. 따라서 실제 정답이 확보되기 전에는 GTFS의 인접 정류장 시간차를 직접
집계한 단순 수식이 재현성·설명 가능성·운영 비용 측면에서 적절하다.

GTFS 수식은 실제 운행 정확도가 검증된 값이 아니다. 응답과 진단에서
`BUS_GTFS_FORMULA`를 사용하고 서울 실측 기반 `BUS_HISTORICAL_REFERENCE`와 구분한다.

## 3. 사용 데이터와 출처

### 3.1 서울 실측 기반 자료

- 원천: [서울시 노선별 정류장 구간별 평균 운행시간 정보](https://data.seoul.go.kr/dataList/OA-21217/S/1/datasetView.do)
- 원천 의미: 노선·출발 정류장·도착 정류장·양쪽 순번·날짜·시간대별 평균 운행시간
- 연구에 사용한 범위: 실제 날짜 기준 2022-01-03~2026-09-06, 자료가 존재한 1,504일,
  현재 서울 마스터와 정확히 연결된 872,316,649개 시간대 평균 행
- 제한: 모든 날짜가 연속적으로 존재하지 않으며 현재 마스터와 정확히 연결된 구간만 사용해
  폐선·변경 구간이 제외되는 선택 편향이 있다.

서울 후보 12개는 학습기간 180/365/730일/전체와 반감기 없음/180일/365일 조합이다.
2026-06-13~08-23 개발기간의 MAE로 설정을 선택하고, 선택 후 2026-08-24~09-06의
10,052,189개 행을 한 번 평가했다. 선택식은 최근 180일·반감기 180일이며 마지막 기간
MAE는 15.986초였다. 이 오차는 개별 차량이 아니라 날짜별 시간대 평균에 대한 오차다.

### 3.2 경기·인천·부산 GTFS

- 원천: KTDB 2025년 3월 GTFS 로컬 배포본
  `202503_GTFS_DataSet`과 `202503_GTFS_route세부정보.xlsx`
- 공식 안내: [KTDB 대중교통 GTFS 기반정보 제공 안내](https://ktdb.go.kr/www/selectBbsNttView.do?bbsNo=2&key=45&nttNo=3764)
- 공식 목록: [KTDB 대중교통 GTFS 자료목록](https://www.ktdb.go.kr/www/selectPbldataChargerWebList.do?key=12&searchClStepCode=106)
- 사용 파일: `routes.txt`, `trips.txt`, `stop_times.txt`, `stops.txt`, `calendar.txt`, 지역 분류 XLSX
- 사용 규모:

| 지역 | 노선 레코드 | 인접 구간 occurrence | 구간·시간대 행 | 운행편 구간 행 |
|---|---:|---:|---:|---:|
| 경기 | 3,098 | 176,229 | 2,074,668 | 5,481,074 |
| 인천 | 360 | 24,902 | 369,316 | 1,218,691 |
| 부산 | 301 | 23,184 | 378,863 | 1,334,686 |

KTDB는 이 GTFS가 접근성 지표 분석을 위해 구축된 파일럿 자료이며 ID 체계가 표준화되지
않았다고 안내한다. 따라서 GTFS ID를 프로젝트 ID로 간주하지 않고 공식 마스터와 매핑한
행만 배포한다. `calendar.txt`의 긴 기간과 전 요일 표시는 실제 날짜별 관측 이력이 아니다.
날짜별 행을 인위적으로 반복 생성하지 않고 `observedDates=0`으로 보존한다.

### 3.3 분석에서 제외한 값

이번 fallback 수식에는 날씨, 거리, 제한속도, 실시간 위치, 실시간 도착, 승하차 인원,
도로 소통속도를 사용하지 않는다. 서울 연구에서 과거 구간 평균이 있을 때 이 변수들을
추가한 식의 MAE 개선이 독립 기간에서 안정적으로 재현되지 않았고, 경기·인천·부산에는
동일 시점의 실제 운행 정답이 없기 때문이다.

## 4. 수식 도출 방법과 선택 이유

### 4.1 서울

같은 `구간 occurrence × 일유형 × 시간대`의 최근 180일 실제 평균을 사용한다.

```text
w_i = 2 ^ (-age_days_i / 180)
T_seoul = max(1, sum(w_i * y_i) / sum(w_i))
```

- `y_i`: 한 날짜의 해당 구간·시간대 평균 초
- `age_days_i`: 학습 종료일에서 관측일까지의 일수, 0~179
- 일유형: 평일·토요일·일요일·공휴일

최근 180일 동일가중 MAE 16.199초, 2026-01-07 이후 동일가중 MAE 16.555초보다
선택식의 15.986초가 작았다. 오래된 노선·운영 조건의 영향을 제한하면서 최근 자료의
일시적 노이즈 한 건에 전부 의존하지 않도록 180일 반감기를 선택했다.

연구 데이터는 평일·토요일·일요일·공휴일을 구분했지만 현재 Backend 정확키 계약은
`dow=1~7`만 지원한다. 첫 배포에서는 공휴일 독립 bucket을 적용하지 않고 달력상의 요일
기준값을 사용한다. 공휴일 효과를 적용하려면 공식 공휴일 artifact와 `dayType` 조회 계약을
별도 버전으로 추가한 뒤 같은 기간에서 다시 검증해야 한다.

런타임에는 원본 180일 자료를 넣지 않는다. 위 식으로 미리 계산한 구간·요일·시간대의
최종 `meanSeconds`와 표본·관측기간만 조회한다.

### 4.2 경기·인천

GTFS의 같은 운행편 안에서 다음 정류장 도착시각에서 현재 정류장 출발시각을 뺀다.

```text
travelSeconds = next.arrivalSeconds - current.departureSeconds
L(s,h) = 같은 구간 s와 출발시간대 h의 travelSeconds 평균
```

해당 구간·시간대가 존재하면 `T=max(1,L(s,h))`를 사용한다. 없는 시간대는 구간 평균
`B(s)`와 수도권 공통 시간대 계수 `k(h)`를 사용해 `T=max(1,B(s)*k(h))`로 내려간다.
배포 전 분석에서 모든 시간대별 최종 T를 계산하므로 서버는 수식을 다시 적합하지 않는다.

운행편 ID를 SHA-256으로 train 60%/validation 20%/test 20%로 고정해 같은 운행편의
모든 구간이 한 분할에 속하게 했다. 공통식의 GTFS 내부 MAE는 경기 0.689초, 인천
0.921초였다. 지역별 계수를 따로 두면 각각 0.658초, 0.886초였으나 개선 폭이
0.032초, 0.035초에 불과하고 실제 운행 정답에서 검증되지 않았다. 그래서 경기·인천은
관리 가능한 한 공통 구조를 사용한다.

### 4.3 부산

부산은 validation MAE로 완화계수 후보를 비교해 `alpha=0.25`를 선택했다.

```text
T_busan(s,h) = max(1,
  (n(s,h)*L(s,h) + 0.25*B(s)*k_busan(h)) / (n(s,h)+0.25)
)
```

- `L(s,h)`: 부산 구간·시간대 GTFS 평균 초
- `n(s,h)`: GTFS 시간표에 포함된 운행편 수. 실제 차량 관측 수가 아님
- `B(s)`: 해당 구간의 시간대별 평균을 동일 가중 평균한 기준 초
- `k_busan(h)`: 부산 데이터에서 구한 시간대별 계수

부산 전용식의 GTFS 내부 MAE는 1.192초, 수도권 공통식은 1.201초였다. RMSE는
부산식 9.295초, 공통식 9.246초로 부산식이 더 컸다. 모든 지표에서 우월한 것은 아니지만
사용자가 요청한 부산 전용 시간대 패턴을 작은 완화계수로 제한해 사용한다.

### 4.4 GTFS 내부 MAE의 해석

GTFS 내부 MAE는 따로 뺀 GTFS 운행편의 시간표 값을 얼마나 재현하는지 나타낸다.
실제 버스 운행 오차가 아니다. 서울의 동일한 실제 시간대 통계 7,826,104행에 2025 GTFS
기준값을 적용했을 때 MAE는 56.249초였고, 같은 행에서 서울 실측 기반 수식은 14.532초였다.
이 비교에는 2025/2026 시점과 노선 개편 차이도 포함되므로 GTFS 수식의 실제 정확도를
확정하지 않는다.

## 5. 프로젝트에 넣는 데이터와 넣지 않는 데이터

프로젝트 서버에는 분석용 원본 전체를 넣지 않는다. 다음 계산 완료값만 gzip 청크로 적재한다.

| 필드 | 의미 |
|---|---|
| `masterVersion` | 계산값을 연결한 프로젝트 마스터 버전 |
| `namespace` | `SEOUL_BUS`, `GBIS`, `INCHEON_PUBLIC_CSV`, `BUSAN_GTFS` |
| `routeId`, `fromStopId`, `toStopId` | canonical component. 비서울은 namespace 접두사 포함 |
| `fromOrder`, `toOrder` | 실제 인접 occurrence의 양쪽 순번 |
| `dow`, `hourSlot` | 서울은 달력 요일 조회키, GTFS는 `dow=1` 템플릿과 출발시간대 |
| `sampleKind` | 서울 `HOURLY_SOURCE_MEAN`/`ACTUAL_TRAVERSAL_MEAN`, GTFS `GTFS_SCHEDULE_FORMULA` |
| `meanSeconds` | 오프라인 수식 계산이 끝난 최종 구간 초 |
| `sampleCount` | 서울은 계약에 따른 날짜/운행 표본, GTFS는 시간표 운행편 수 |
| `observedDates` | 서울 관측 날짜 수, GTFS는 반드시 0 |
| `observationStart/End` | 서울 관측기간, GTFS 피드·승인 artifact 적용기간 |
| `sourceSha256` | 최종 행을 만든 원본/매핑 artifact 추적 SHA |

별도 분석 공간에 남기고 서버에는 적재하지 않는 자료는 GTFS 전체 `stop_times.txt`, 날짜별
서울 원본 수억 행, train/validation/test 분할, 후보별 오차 파일, 그래프와 중간 Parquet이다.
재계산·감사를 위해 별도 보관하되 사용자 요청 처리 중 읽지 않는다.

## 6. 배포와 조회 과정

1. 원본을 별도 분석 공간에서 정규화하고 계산식을 선택한다.
2. 제공기관 원본 ID를 현재 프로젝트 마스터의 namespace·노선·정류장·순번에 매핑한다.
3. 매핑 결과가 유일하고 인접 순번이며 같은 출처인 행만 최종 JSONL로 만든다.
4. 서울 자료는 기존 `export-bus-reference.py`, GTFS 계산값은
   `export-gtfs-bus-formula.py`로 1,000행 단위 `.json.gz`를 만든다.
5. `transfer-bus-reference.py`가 모든 청크 SHA·행 수·sampleKind·masterVersion을 검증한다.
6. `--upload`와 내부 API 키를 사용해 `/internal/bus-references/.../chunks/...`로 올린다.
7. 서버의 전체 행·청크 수가 manifest와 같아야 gate를 통과한다. 중간 적재 버전은 사용하지 않는다.
8. 새 버전을 설정한 서버를 재시작하고 SHADOW/시험 환경에서 출처·fallback 사유를 확인한다.

gzip은 전송 형식이다. 요청 시 gzip이나 Parquet를 직접 읽지 않고 MySQL
`bus_reference_row`의 정확키를 조회한다. 동일한 `dataVersion/chunkId` 재전송은 payload SHA가
같을 때만 멱등하게 허용한다. 데이터 변경은 새 버전으로 배포한다.

## 7. 런타임 계산 흐름

1. 카카오 BUS step을 활성 마스터의 인접 edge 목록으로 전개한다.
2. 모든 edge의 canonical segment ID, namespace, 순번 연속성, 마스터 버전을 확인한다.
3. 서울 edge만 ML 배치에 포함한다. 경기·인천·부산은 ML HTTP 요청을 만들지 않는다.
4. 서울 ML이 전체 edge에서 적용 가능하면 ML 합계를 사용한다.
5. 그 외에는 각 edge 진입 예상시각으로 기준값을 조회한다. 앞 edge의 초를 다음 edge
   진입시각에 누적하므로 운행 중 시간대가 바뀌면 다음 시간대 값을 사용한다.
6. 서울은 요청 날짜의 Spark dayofweek와 시간대, GTFS는 `dow=1` 템플릿과 시간대로 조회한다.
7. 한 edge라도 실패하면 BUS step 전체를 카카오 원본시간으로 복귀시킨다.
8. 별도 버스 대기시간은 분해 검증과 유효한 도착정보가 있을 때만 한 번 더한다.

출처는 `ML_PRODUCTION|ML_PREVIEW`, `BUS_HISTORICAL_REFERENCE`,
`BUS_GTFS_FORMULA`, `FALLBACK`으로 구분한다. 사용 버전·sampleKind와 실패 원인을 reason에
남긴다.

## 8. 현재 제한과 운영 전 조건

- 서울 기준값은 실제 운행 통계 기반이지만 개별 차량 예측이 아니라 날짜별 시간대 평균이다.
- 경기·인천·부산 수식은 실제 운행 정확도가 검증되지 않은 GTFS 초기값이다.
- 현재 프로젝트 수도권 마스터에는 서울·GBIS·인천이 포함된다. `BUSAN_GTFS` ID 발급과 조회
  코드는 지원하지만, 부산 공식 마스터와 카카오 경로 매핑 artifact가 프로젝트에 추가되기
  전까지 부산 경로는 검증된 edge를 만들 수 없어 카카오 fallback을 유지한다.
- 연구 공간의 GTFS ID와 프로젝트 마스터 ID가 같아 보인다는 이유로 직접 적재하지 않는다.
  인천 CSV와 실시간 API ID도 별도 crosswalk 검증 전에는 자동 치환하지 않는다.
- 운영 설정의 `expectedRows`, `expectedChunks`, `dataVersion`, master SHA가 배포 manifest와
  일치해야 한다. 자료가 없거나 stale인 상황을 정상으로 표시하지 않는다.
- 경기·인천·부산의 실제 구간 운행 기록이 확보되면 같은 미래 기간에서 GTFS 수식,
  서울식 가중평균, 통합 ML을 비교한 뒤 수식 교체 여부를 다시 결정한다.
