# 서울시 도로 돌발정보를 버스 정류장 간 이동시간에 적용하기

작성: 2026-09-21 · 조사 보강: 2026-09-22 · 대상: 뚜비의 버스 정류장 간 이동시간 예측

## 먼저 결론

서울시 [실시간 돌발 정보(OA-13315)](https://data.seoul.go.kr/dataList/OA-13315/A/1/datasetView.do)는 **사건이 발생한 도로의 `LINK_ID`**를 준다. 버스가 어느 정류장 사이에서 **어떤 도로 링크들을 실제로 지나는지**는 이 API가 알려주지 않는다. 이를 확인하려면 별도의 버스 경로 자료와 [소통 돌발 링크 정보(OA-13310)](https://data.seoul.go.kr/dataList/OA-13310/A/1/datasetView.do)를 연결해야 한다.

따라서 모델에 넣을 데이터를 만드는 과정은 두 단계다.

1. **경로상 관련성:** 버스가 지나는 도로 링크 목록에 사건의 `LINK_ID`가 있고, 진행 방향과 통과 예정 시간도 맞는가?
2. **예측 입력값 생성:** 겹치는 사건의 개수·유형·관측 시각 등을 버스 구간별 feature로 만든다. 그 값이 이동시간 예측에 얼마나 도움이 되는지는 학습과 검증에서 모델이 확인한다.

## 정류장 사이의 길을 어떻게 알아내나?

정류장 A와 B의 ID만으로는 그 사이의 도로 경로를 알 수 없다. **버스 노선, 운행 방향, 정류장 순서**를 지정한 다음 공식 버스 경로 자료로 그 사이의 통과 도로를 찾아야 한다. 같은 정류장 쌍이라도 노선·방향·순환 순서에 따라 경로가 다를 수 있다.

| 순서 | 입력 자료 | 하는 일 |
| --- | --- | --- |
| 1 | [BIS 노선별 경유노드](https://t-data.seoul.go.kr/dataprovide/trafficdataviewfile.do?data_id=58) | 노선 ID와 정류장 순서로 A→B에 해당하는 경유노드·구간을 찾는다. |
| 2 | [BIS 구간링크](https://t-data.seoul.go.kr/dataprovide/trafficdataviewfile.do?data_id=62), [BIS 공간 링크](https://t-data.seoul.go.kr/dataprovide/trafficdataviewfile.do?data_id=63) | 그 구간의 도로 링크를 순서대로 풀고, 시작·끝 노드가 이어져 진행 방향이 맞는지 검사한다. |
| 3 | [TOPIS 표준링크](https://t-data.seoul.go.kr/dataprovide/trafficdataviewfile.do?data_id=7), OA-13310 링크 정보 | BIS 쪽 링크를 돌발정보에서 사용하는 TOPIS `LINK_ID`와 대조한다. 숫자가 같다는 이유만으로 같은 링크라고 확정하지 않는다. |
| 4 | 검증된 결과 | `버스 구간 → [TOPIS LINK_ID 1, LINK_ID 2, …]` 대응표를 만든다. 한 정류장 간 구간이 여러 도로 링크를 지날 수 있다. |

**가상의 예:** 100번 버스의 A→B 구간이 도로 링크 `[11, 12, 13]`을 지난다고 검증됐고, 사건의 `LINK_ID`가 `12`이면 그 사건은 예측 대상 구간에 관련된다. `50`이면 이 구간과 직접 연결되지 않는다. 이 숫자들은 실제 서울시 링크 ID가 아니다.

### 세 BIS 자료가 이어지는 예시

아래 ID는 **연결 원리를 설명하기 위해 만든 가상 값**이다. 실제 API 응답이나 실제 버스 노선을 재현한 값이 아니다.

| 자료 | 가상 행 | 역할 |
| --- | --- | --- |
| 노선별 경유노드 | `노선ID=100번, 노드ID=A정류장, 정류장순번=5, 노드일련번호=20` | 버스가 어느 노드에서 출발하는지 확인 |
| 노선별 경유노드 | `노선ID=100번, 노드ID=B정류장, 정류장순번=6, 노드일련번호=21, 구간ID=S_AB` | B에 도착하기 직전의 구간 `S_AB` 확인 |
| BIS 구간링크 | `구간ID=S_AB, 구간순번=1, 링크ID=B501` | A→B 구간의 첫 번째 BIS 도로 링크 |
| BIS 구간링크 | `구간ID=S_AB, 구간순번=2, 링크ID=B502` | A→B 구간의 두 번째 BIS 도로 링크 |
| BIS 공간 링크 | `링크ID=B501, 시작노드=N1, 종료노드=N2` | B501의 위치와 진행 방향 확인 |
| BIS 공간 링크 | `링크ID=B502, 시작노드=N2, 종료노드=N3` | B501의 끝 `N2`에서 B502가 이어지는지 확인 |

세 자료를 읽은 결과는 `100번 버스 A→B → [B501, B502]`다. **여기까지는 BIS 링크 ID**다. 이후 TOPIS 표준링크 자료에서 `표준링크ID=B501, 시작/종료=N1/N2 → 서비스 LINK_ID=T801`과 `표준링크ID=B502, 시작/종료=N2/N3 → 서비스 LINK_ID=T802`를 검증해 `[T801, T802]`로 바꾼다. 마지막으로 OA-13310 링크 자료 및 실제 AccInfo 표본에서 `T801/T802`가 같은 번호 체계임을 확인해야 한다. 사고의 `LINK_ID=T802`라면 이때 비로소 A→B 구간의 영향 후보가 된다.

## 어떤 조건을 만족해야 영향 후보인가?

| 확인 항목 | 이유 |
| --- | --- |
| 링크 ID 체계가 같고 공식 자료로 검증됨 | BIS·TOPIS·AccInfo의 숫자를 잘못 연결하지 않기 위해서 |
| 버스의 운행 방향과 사건 링크 방향이 맞음 | 같은 도로의 반대 방향 사고를 섞지 않기 위해서 |
| 버스가 그 링크를 지날 예상 시간과 사건 관측 기간이 겹침 | 이미 지난 사건이나 버스 통과 뒤 발생한 사건을 제외하기 위해서 |
| 노선·정류장 순번·구간 전체 경로가 확정됨 | 순환 노선과 부분적으로만 확인된 구간을 잘못 판정하지 않기 위해서 |
| 응답과 대응표가 최신이며 유효기간 안에 있음 | 오래된 사건과 변경된 버스 경로를 사용하지 않기 위해서 |

조건을 통과하면 현재 설계의 결과는 **`POTENTIAL_IMPACT`(영향 가능성)**이다. 이것은 실제 지연이나 운행 불가의 확정값이 아니다. 사고의 `EXP_CLR_DATE/TIME`은 해제 *예정*이며 실제 해제 확인도 아니다. 버스의 임시 우회가 확인되면 평소 경로 대응표를 그대로 적용해서는 안 된다.

## 정류장 간 예측시간에는 어떻게 넣나?

예측할 버스 구간의 도로 목록과 사고 API의 `LINK_ID`를 연결한 다음, **그 결과를 ML 모델의 입력값(feature)**으로 만든다. 여기서 사고 데이터는 정류장 간 이동시간을 직접 결정하지 않는다. 모델은 과거의 실제 정류장 간 소요시간을 정답값으로 학습해 사고 feature가 시간 예측에 주는 관계를 익힌다.

| feature 예시 | 만드는 방법 | 해석 |
| --- | --- | --- |
| `incident_on_path` | 예측 시점에 경로·방향·시간이 맞는 사건이 하나 이상이면 1, 없으면 0 | 해당 구간에 관련 사건이 관측됐는가 |
| `incident_count_on_path` | 일치하는 사건 수 | 관련 사건이 몇 건인가 |
| `incident_type_*` | 일치하는 사건의 `ACC_TYPE`/`ACC_DTYPE`별 존재 여부 또는 건수 | 어떤 종류의 사건인가 |
| `incident_age_minutes` | 예측 시점 − 사건 발생 시각. 유효한 시각이 있을 때만 계산 | 사건이 언제 시작됐는가 |
| `incident_data_available` | API 수집과 구간 대응표가 모두 유효하면 1 | 사건이 0건인 상태와 데이터를 모르는 상태를 구분 |

예를 들어 버스가 지나는 링크가 `[11, 12, 13]`이고 현재 사건의 링크가 `12`라면 `incident_on_path=1`, 사건 1건이면 `incident_count_on_path=1`이다. 이 값을 노선·정류장 구간·시간대 등 기존 입력값과 함께 모델에 전달한다. **“1이면 10분 추가” 같은 규칙을 미리 정하지 않는다.** 도로 소통 속도 자료를 추가할 때도 링크 ID·시각·방향을 같은 기준으로 맞춘다.

학습 자료를 만들 때는 각 과거 예측 시점까지 실제로 수집된 사건만 붙인다. 현재 API의 목록을 과거 전체 구간에 소급해서 붙이면 미래 정보를 사용하게 된다. 대응표가 미확정이거나 API 수집이 실패한 구간은 사건 0건으로 채우지 않고 별도 결측 상태로 표시한다. 사건 feature를 추가한 모델과 기존 모델의 예측 오차를 시간순으로 비교해 사용 여부를 결정한다.

사용자에게는 모델이 예측한 정류장 간 소요시간을 제공한다. 사건 자체를 안내할 때는 검증된 구간에 한해 “경로상 돌발 상황이 관측됐어요”처럼 관측 사실을 표현한다. 실제 우회·운행 중단은 별도의 공식 공지 또는 버스 운행 관측으로 확인한다.

## 집에서 이어서 할 작업

1. [`docs/contracts/bus-road-mapping.md`](contracts/bus-road-mapping.md)와 [`docs/contracts/road-impact.md`](contracts/road-impact.md)를 읽고, 기존 후보의 생성 과정과 제외 사유를 확인한다.
2. [`mapping-audit.json`](../backend/tools/road-impact/validation/mapping-audit.json)의 `operationalMappings: 0`을 확인한다. `TOPIS_PATH_COMPLETE` 같은 후보 수를 서비스 적용 가능 건수로 해석하지 않는다.
3. 공식 OA-13310 링크 마스터와 AccInfo `LINK_ID`가 같은 ID 체계인지 표본으로 대조한다. OA-13311 Vertex, 시작·끝 노드, 방향, 원본 버전·유효기간도 확인한다.
4. 노선 하나와 연속된 정류장 한 쌍을 골라 **버스 경유노드 → BIS 구간링크 → TOPIS 링크 → AccInfo 사건**을 끝까지 추적한다. 같은 도로의 반대 방향과 순환 노선도 반례로 검사한다.
5. 연결이 검증된 구간에만 사건 feature를 생성한다. 과거 실제 버스 구간 소요시간을 정답으로 모델을 학습하고, feature 추가 전후의 예측 오차를 비교해 적용 범위를 결정한다.

## 2026-09-22 조사 결과: 구현 가능한 연결 알고리즘

### 1. 먼저 버스 구간의 도로 목록을 만든다 (정적 배치)

버스 구간의 식별자는 단순히 `A정류장-B정류장`이 아니다. 노선 ID, 출발·도착 정류장 ID와 순번, 방향, 버스 마스터 버전을 묶는다. 순환 노선이 같은 정류장을 다시 지나도 다른 구간으로 다루기 위해서다.

```text
버스 구간(routeId, fromStopId, toStopId, fromOrder, toOrder, direction)
  → BIS 노선별 경유노드: 두 정류장 사이의 연속된 노드 선택
  → BIS 구간링크: 각 노드 사이의 도로 링크를 순서대로 펼침
  → BIS 공간 링크: 앞 링크의 종료노드 = 다음 링크의 시작노드인지 확인
  → TOPIS 표준링크: 표준 ID와 시작·종료 노드가 함께 일치하는 서비스 링크 후보 선택
  → OA-13310 / OA-13311: AccInfo LINK_ID와 동일한 체계인지, 링크 위치·방향·버전을 검증
  → 승인된 구간별 [LINK_ID, LINK_ID, ...] 저장
```

이 과정의 앞부분은 [`audit.py`](../backend/tools/road-impact/audit.py)에 구현돼 있다. 링크마다 후보가 0개이거나 여러 개이면 그 버스 구간을 `UNMAPPED` 또는 `AMBIGUOUS`로 남긴다. 이어진 도로가 일부만 확인되면 `PARTIAL`이다. 완전한 단일 방향 경로만 승인 후보가 된다. [`verify_link_api.py`](../backend/tools/road-impact/verify_link_api.py)는 OA-13311 Vertex를 확인하는 도구이고, [`promote.py`](../backend/tools/road-impact/promote.py)는 검토자가 명시한 근거·유효기간을 검증한 뒤 운영 대응표를 만든다. 후보를 자동 승인하지 않는다.

**주의:** 공식 표준링크 API의 예시에도 `stdLinkId`와 `linkId`가 별도로 나온다. 숫자가 비슷하다고 같은 ID로 취급하지 않는다. [`TOPIS 표준링크 API`](https://t-data.seoul.go.kr/dataprovide/trafficdataviewopenapi.do?data_id=1007)

### 2. 실시간 사건을 해당 구간에 붙인다 (동적 판정)

```text
입력: 구간의 승인된 LINK_ID 목록, 버스의 예상 구간 통과 시간,
      사건의 LINK_ID·발생시각·수집시각·해제 예정시각

if 대응표가 미승인/만료/부분 매핑: UNKNOWN
elif 사건 LINK_ID가 구간 링크 목록에 없거나 방향이 다름: 해당 사건은 이 구간과 매칭 안 됨
elif 사건 수집값이 오래됐거나 예상 통과 시간과 겹치지 않음: UNKNOWN 또는 매칭 안 됨
else: POTENTIAL_IMPACT (영향 가능성)
```

`UNKNOWN`은 “사고가 없다”가 아니다. 해제 *예정*시각이 지났다는 이유만으로 실제 해제됐다고 처리하지 않는다. 정적 경로에서 버스가 임시 우회 중이면 공식 우회 공지 또는 현재 운행 자료로 별도 확인해야 한다. 기존 [`RoadImpactIndex.assess()`](../sparkjobs/common/road_impact.py)는 최신 사건·시간·버전·충돌을 검사하고, 지연초와 통행 불가 여부는 채우지 않는다.

### 3. feature의 예측 가치를 실측으로 검증한다

`POTENTIAL_IMPACT`는 “버스 경로 위에 사건이 있다”는 **위치·시간 매칭 결과**이며, 모델에 전달할 feature의 근거다. 실제 시간 증가를 뜻하지 않는다. 정류장 간 실제 운행 관측을 정답값으로 붙이고 시간순 분리 검증에서 기존 모델보다 예측 오차가 줄어드는지 확인한다. 학습에는 **예측 시점까지 수집된 사건만** 사용한다. 새 마스터를 과거 날짜에 소급 적용하려면 당시 경로와 유효기간이 확인돼야 한다.

추가 실측 후보는 [T-Data 정류장 운행 통계](https://t-data.seoul.go.kr/dataprovide/trafficdataviewopenapi.do?data_id=1083)다. 공식 설명에 `routeId`, `nodeSn`, `sctnId`, 평균속도와 여행시간 관련 필드가 있다. 실제 응답의 집계 단위·시간 해상도와 값의 의미는 인증 후 표본으로 확인해야 한다. [BIS 돌발 이력](https://t-data.seoul.go.kr/dataprovide/trafficdataviewopenapi.do?data_id=1067)은 버스 노선·구간·링크 ID가 있는 **월 1회 갱신 이력**으로, 매핑 표본 검증의 보조 자료가 될 수 있다. 실시간 사건 판정용으로 간주하지 않는다.

### 완료 기준과 지금 남은 일

1. 실제 OA-13315 사건의 `LINK_ID`를 OA-13310 `LinkInfo`에서 조회해 ID 일치를 확인한다. 2026-09-22 현재 사건의 ID 일치는 아래처럼 확인했다. 이어 OA-13311 위치·방향과 원천 버전을 대조한다.
2. 선택한 버스 노선의 연속 정류장 구간에서 공식 BIS 링크 경로가 빠짐없이 이어지고, TOPIS 링크로 유일하게 연결되는지 확인한다.
3. 반대 방향, 순환 노선, 중복 정류장, 단절 링크, 과거 버전, 버스 우회 사례에서 잘못 매칭되지 않는지 검증한다.
4. 출처·SHA·마스터 버전·유효기간을 기록한 승인 대응표를 만든다. 현재 감사의 `operationalMappings`는 **0**이고 후보는 서비스 적용 가능 수가 아니다.
5. 그 후 사건 feature를 넣은 모델의 예측 오차를 실제 정류장 간 소요시간으로 평가한다. 사건의 존재만으로 지연 여부를 결정하지 않는다.

2026-09-22에 공식 원본 CSV 4종(자료 58·62·63·7)을 다시 받아 SHA-256을 확인하고, 현재 버스 마스터(`METRO-BUS-20260917-SEOUL-0902`)로 후보 연결 감사를 재실행했다. 실제 행을 끝까지 추적한 결과는 아래에 기록했다.

### 2026-09-22 실제 API 확인: AccInfo ↔ LinkInfo

저장소에 설정된 인증키로 `AccInfo/1/100/`을 읽고, 응답의 각 고유 `LINK_ID`에 대해 `LinkInfo/1/5/{LINK_ID}/`를 조회했다. 키와 원본 응답은 문서·로그에 기록하지 않았다.

| 확인 항목 | 결과 |
| --- | ---: |
| AccInfo가 보고한 현재 사건 / 실제 읽은 사건 | 15건 / 15건 |
| `LINK_ID`가 비어 있는 사건 | 0건 |
| 서로 다른 사건 `LINK_ID` | 14개 |
| 같은 ID로 LinkInfo 행을 찾은 경우 | **14/14개** |
| 미일치 / 조회 실패 | 0개 / 0개 |

따라서 **현재 관측된 AccInfo의 링크 ID를 OA-13310 LinkInfo에서 조회할 수 있음**을 확인했다. 이 결과는 조회 시점의 사건 표본에 대한 검증이다.

### 2026-09-22 BIS 도로 번호 실제 행 검증

공식 CSV의 원본 행을 따라 아래의 한 사례를 확인했다. 숫자는 설명용 가상 값이 아니라 실제 데이터에 있는 ID다.

| 연결 순서 | 앞 자료에서 가져올 열 | 다음 자료에서 찾을 열 | 연결해서 얻는 값 |
| --- | --- | --- | --- |
| 버스 구간 선택 | 노선 ID, 출발·도착 정류장 ID와 순번 | BIS 노선별 경유노드(58)의 `노선ID`, `노드ID`, `정류장순번` | 도착 정류장 행의 `구간ID` |
| 구간 → BIS 링크 | (58)의 `구간ID` | BIS 구간링크(62)의 `구간ID` | `구간순번` 순서로 정렬한 `링크ID` 목록 |
| BIS 링크의 방향 확인 | (62)의 `링크ID` | BIS 공간 링크(63)의 `링크ID` | 각 링크의 `시작노드ID`·`종료노드ID`; 여러 링크가 순서대로 이어지는지 검사 |
| BIS → TOPIS 링크 | (63)의 BIS `링크ID`와 시작·종료 노드 | TOPIS 표준링크(7)의 `표준링크ID`와 시작·종료 노드 | 같은 행의 서비스 `링크ID` |
| TOPIS 링크 → 사건 | (7)의 서비스 `링크ID` | AccInfo의 `LINK_ID` | 예측 구간의 경로와 겹치는 사건 후보 |

여기서 말하는 **BIS 도로 번호는 `링크ID`**다. CSV에는 `도로번호`라는 별도 열도 있는데, 이는 이 연결에 사용하는 링크 식별자가 아니다. (58)에도 `링크ID` 열이 있지만, 한 정류장 사이의 전체 도로 목록은 (62)의 `구간ID`를 통해 `구간순번`대로 펼쳐서 얻는다. (7)의 `표준링크ID`와 서비스 `링크ID`는 서로 다른 열이므로 실제 행으로 변환값을 확인한다.

| 자료 | 확인한 값 | 뜻 |
| --- | --- | --- |
| BIS 노선별 경유노드(58) | 노선 `100100044`, 정류장 `106000151`(20번째) → `106000149`(21번째), 도착 정류장의 구간 ID `106600206` | 확인할 정류장 사이의 구간 선택 |
| BIS 구간링크(62) | 구간 `106600206`, 첫 번째 BIS 링크 `1060008200` | 그 구간을 구성하는 도로 번호 |
| BIS 공간 링크(63) | BIS 링크 `1060008200`, 시작 노드 `1060008400` → 끝 노드 `1060009000` | 도로의 진행 방향 확인 |
| TOPIS 표준링크(7) | 표준링크 `1060008200`, 같은 시작·끝 노드, 서비스 링크 `1060008200` | 이 사례에서는 BIS 도로 번호와 사건 조회용 도로 번호가 같음 |
| 실시간 돌발정보 AccInfo | 사건 `1101242`의 `LINK_ID=1060008200` | 사건의 도로 번호가 위 버스 구간의 후보 도로와 일치 |

즉 **이 특정 구간에서는 BIS 도로 번호 `1060008200`이 TOPIS 서비스 링크 및 실제 사건의 `LINK_ID`와 연결됨**을 원본 행으로 확인했다. 모든 도로 번호가 항상 같은 숫자라는 뜻은 아니다. 다른 행에서는 변환이 필요하거나 연결이 실패할 수 있다.

현재 조회한 사건의 서로 다른 링크 14개 중 **3개**가 버스 구간 후보에 나타났고, 이에 해당하는 버스 구간 후보 행은 **33개**였다. 현재 마스터의 서울 버스 구간 **40,959개**를 감사해 **13,824개**에서 TOPIS 링크 경로 전체를 구성했다. 이 수치는 연결 *후보*이며, 운영 승인 수는 여전히 **0개**다. 감사 파일은 [`mapping-audit.json`](../data/road-impact-current/mapping-audit.json), 위 사례의 후보 행은 [`mapping-candidates.jsonl`](../data/road-impact-current/mapping-candidates.jsonl)에 있다. 원본 CSV의 SHA-256도 감사 파일에 기록했다.

**서비스 적용 전에 남은 검증:** 버스 마스터와 도로 자료의 적용 시점, 사건의 위치·방향, 노선 우회 여부를 확인해야 한다. 검증된 연결은 ML 입력값을 만드는 데 사용하고, 실제 정류장 간 소요시간은 모델의 학습 정답값으로 사용한다.

### 사고 LINK_ID → 버스 segmentId 역조회 시범 구현

[`preview_reverse_index.py`](../backend/tools/road-impact/preview_reverse_index.py)는 위 감사 결과에서 **모든 occurrence가 동일한 전체 링크 경로를 가진 segmentId만** 역방향 색인에 넣는다. 같은 segmentId에 서로 다른 경로가 있거나 일부 occurrence만 연결되면 제외한다. 출력의 `reverseIndex`는 `LINK_ID → [segmentId, ...]`, `incidents`는 각 사건 링크의 일치 후보, `segmentFeatures`는 구간별 검토용 건수다. 연결되지 않은 구간은 `candidateIncidentCountInSnapshot=null`과 `UNKNOWN_MAPPING`으로 표시한다.

```powershell
python backend/tools/road-impact/preview_reverse_index.py `
  --directory data/road-impact-current `
  --incident-snapshot data/road-impact-current/accinfo-link-snapshot.json `
  --output data/road-impact-current/reverse-preview.json
```

현재 버스 마스터에서 **고유 segmentId 40,587개 중 13,751개**가 전체 경로 후보로 역조회 가능했다. 현재 사건 스냅샷에서는 사고 링크 **3개**가 구간 후보 **33개**에 걸렸다. 이 결과는 **ID 겹침 시범 분석**이다. 사고 스냅샷에 수집·해제 시각과 방향 검증이 없고 운영 승인 매핑도 0건이므로, 출력의 건수를 지금 ML 학습·서빙 feature로 사용하지 않는다. 시간별 수집 이력을 보존하고 매핑 유효기간을 승인한 뒤, 예측 시점 이전에 관측된 사건으로 실제 feature를 생성해야 한다.
