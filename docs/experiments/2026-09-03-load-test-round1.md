# 부하 실험 1차 결과 — worker 수에 따른 처리 지연 (2026-09-03)

절차서: [load-test-runbook.md](load-test-runbook.md). 이 문서는 1차 실행의 원자료·결론·교훈 기록이다.

## 1. 목적과 질문

- 질문: **Spark worker 수(1대 → 2대)를 늘리면 같은 부하를 더 빨리 소화하는가?**
- 발표에서 "계산의 분산"을 숫자로 보이기 위한 사전 실험. 오늘은 리허설 겸 1차 측정

## 2. 구성

| 구성 요소 | 내용 |
|---|---|
| 부하 발생 | `replay-producer`(archiver/src/replay.py). HDFS 아카이브 city.raw(8/31~9/3, 1회 통과 5,765건)를 **전용 토픽 city.replay** 로 재생 |
| 측정 대상 | `spark-streaming-replay`(experiment 프로필). 운영 잡과 같은 코드(weather_latest.py), 환경변수만 다름: 토픽 city.replay, Redis 접두사 `weather:replay`, 체크포인트 `weather_replay`, maxOffsetsPerTrigger 200,000 |
| 자원 | worker 1대 = 코어 2·메모리 1536m 광고. 실험 잡 executor = 1g·코어 1 (submit.sh 기본) → **worker 1대당 executor 1개, 코어 1개** |
| 격리 | 실험 중 운영 스트리밍(spark-streaming-weather) 정지. 아카이버는 city.replay 를 구독하지 않으므로 HDFS 재적재 없음. Redis 운영 키 `weather:latest:*` 무영향 확인 |
| 서버 | 서버1(4코어/16GB)에서 Kafka·Spark·HDFS·replay 전부 실행 |

## 3. 측정 방법 (확정)

Spark Structured Streaming 은 Kafka 컨슈머 그룹에 오프셋을 커밋하지 않으므로 kafka-exporter 랙 지표는 쓸 수 없다.
대신 **실험 잡 체크포인트의 배치별 종료 오프셋**으로 건수를 검산하고, 드라이버 로그의 배치 완료 시각으로 시간을 잰다.

```
# 배치 N 의 파티션별 종료 오프셋 (합계 차이 = 그 배치의 처리 건수)
docker exec hdfs-namenode hdfs dfs -cat /ddubi/checkpoints/weather_replay/offsets/N | tail -1
# 배치 완료 시각
docker logs spark-streaming-replay 2>&1 | grep -E "batch=|falling behind"
# 검산: Kafka 끝 오프셋 합계 = 마지막 배치 종료 오프셋 합계
docker exec kafka /opt/kafka/bin/kafka-get-offsets.sh --bootstrap-server kafka:9092 --topic city.replay
```

- **소진 시간** = 마지막 replay 완료 시각 → 마지막 배치 완료 시각
- **처리 속도** = 배치 건수 ÷ 배치 소요("spent N ms" 경고 또는 직전 배치 완료 시각과의 차)
- Spark UI(4041) Structured Streaming 탭은 보조 확인용(Input Rows·Batch Duration 그래프)

| 조건 (66,000건, 약 4,000/s 투입) | 소진 시간 | 큰 배치 처리 속도 |
|---|---|---|

## 6. 해석

1. **잡이 너무 가볍다.** weather_latest 는 레코드당 JSON 파싱 + 격자 14개 최신값 선택이 전부다. worker 1대가 큰 배치에서 초당 9천 건을 처리하는데 실제 유입은 10분에 14건이다.
2. **배치 시간의 대부분이 건수와 무관한 고정비**(태스크 배분·셔플·Redis 연결·체크포인트 쓰기)다. 같은 조건에서 배치 속도가 150/s ~ 10,250/s 로 널뛰고, 건수가 클수록 속도가 오른다. 고정비는 코어를 늘려도 그대로라 worker 수 차이가 소진 시간에 나타나지 않는다.
3. 따라서 **"분산의 효과"는 이 잡에서는 측정 불가**하고, 레코드당 계산이 무거운 잡(기준선 조인·5분 창 집계를 하는 segment.status)에서 재측정해야 한다.
4. 발표용 메시지 후보: "현재 유입량 대비 수십만 배의 처리 여유. 분산의 가치는 처리량이 아니라 무거운 계산과 장애 내성(worker 유실 시 잡 지속)에 있다."

## 7. 교훈 (다음 실험에 반영)

- **예열은 executor 구성이 바뀔 때마다 필수.** 새 worker 를 붙인 직후 측정은 2배 느리게 나온다(4-6). 예열용 1,000건 1회 후 20초 뒤 본 측정
- **부하 발생기를 측정 대상과 분리.** replay 12개가 서버1 CPU 4개를 점유하는 동안 Spark 배치가 3~10배 느려졌다(4-5 배치 12, 4-7 배치 16). 본 실험에서는 replay 를 **서버2에서** 실행한다(Kafka 9092 는 방화벽에서 서버2 허용)
- **투입 속도는 처리 능력 위로.** 2,400/s 에서는 랙이 안 쌓여 측정할 것이 없었다(4-4). 처리 능력을 먼저 재고 그 1.5~2배로 투입
- **replay 다중 컨테이너는 우회일 뿐.** 아카이브 1회 통과가 5,765건이라 컨테이너 12개를 백그라운드(`&`)로 동시 실행했다. 반복 옵션(`--repeat`)을 replay 에 추가해 프로세스 하나로 대량 재생하게 한다
- **측정은 체크포인트 오프셋 + 로그 시각이 정확하다.** UI 는 보조. kafka-exporter 랙은 Spark 에 해당 없음
- 트리거 10초가 소진 시간의 분해능을 제한한다. 실험 잡의 트리거 간격을 환경변수로 짧게(예: 2초) 조절할 수 있게 하면 정밀해진다
- 운영 잡을 끄고 2시간이 지나면 `weather:latest` 가 TTL 만료로 사라진다. 복귀 시 첫 배치에서 최신값으로 복원됨을 확인(14:09)
