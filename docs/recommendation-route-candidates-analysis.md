# 추천 경로 후보 수 분석과 임시 정책 제안 (2026-09-18, 적용 전)

이 문서는 현재 상태를 숫자로 보고하고 정책 선택지를 제시한다. **아직 코드에 적용하지 않았다.** 적용은 사용자 승인 후 별도 커밋으로 한다.

## 1. 현재 구조 (코드 기준)

```
원본 후보 수집 → (중복 제거 없음) → 계산 가능 후보 선별 → 전체 후보 평가 → 정렬 → (표시 상한 없음)
```

| 단계 | 현재 구현 | 비고 |
|---|---|---|
| 원본 후보 수집 | 카카오 대중교통 경로 응답의 path 전부 | 일정 6 실측: **15개 path** |
| 대안 전개 | `BusAlternativeExpansion` 이 path 마다 최대 32개 변형(같은 정류장 쌍을 지나는 다른 노선, 심야 N13/N31 포함) | 일정 6: 15 path → **33개 후보**, path 6 하나가 10개 변형 |
| 중복 제거 | 없음. `pathIdentity`·`signature()` 두 동일성 개념이 있지만 후보 목록을 줄이는 데 쓰지 않는다 | 저장 시 모든 후보를 그대로 저장(`RecommendationIntegrationTest:167` 이 "전부 저장"을 단언) |
| 계산 가능 후보 선별 | 매핑 실패 segment 가 있어도 후보는 남고, 그 step 은 API 원본 시간을 쓴다 | 일정 6: BUS segment 48개 중 43 mapped / 5 unmapped, SUBWAY 21개 전부 mapped |
| 전체 후보 평가 | 33개 후보를 한 세션 예산으로 순차 평가(2026-09-18 수정 전: 5초 공유, ML 개별 호출 ~0.3초) | 수정 후: 배치 선조회 + 트리거별 예산 30/15/10초 + ML 비율 0.6 |
| 정렬 | 도착 가능 여부 → 예상 도착시각 순. 동률 규칙(`arrival-deadline-calculation.md` §2.3 의 환승 수·도보·출처 품질 우선)은 **미구현** | 일정 6: 33개 중 **ON_TIME 29 / LATE 4**, 서로 다른 예상 도착시각은 **15개**(나머지는 동률) |
| 표시 | 상한 없음 — 저장된 후보 전부가 응답에 실린다 | 앱은 선택 1순위와 후보 목록을 그대로 보여준다 |

## 2. 관찰된 문제

1. **동률·중복이 많다.** 33개 후보 중 예상 도착시각이 서로 다른 것은 15개다. 같은 정류장 쌍의 노선만 다른 변형은 사용자에게 같은 경로로 보인다.
2. **뒤 후보가 예산을 잃었다.** 순차 평가 때 30개 후보가 `ML_BUDGET_EXHAUSTED`, 146 후보의 유효한 과거 평균이 `HISTORICAL_REFERENCE_BUDGET_EXHAUSTED` 로 밀렸다(자료 없음이 아니라 시간 부족). 배치 선조회와 예산 분리로 완화했지만, 후보 수 자체는 그대로다.
3. **정렬 동률 규칙이 없다.** 같은 도착시각이면 저장 순서(카카오 path 순 → 변형 순)로 결정되어 심야 노선 변형이 앞에 올 수 있다.

## 3. 정책 선택지

| 선택지 | 내용 | 장점 | 위험 |
|---|---|---|---|
| A. 완전 동일 후보만 제거 + 최대 5개 표시 (임시 제안) | `signature()`(모드·정류장/역 열·노선 열)가 완전히 같은 후보만 하나로 합치고, 정렬은 지금 그대로, 표시만 5개로 자른다. 저장은 전부 유지 | 계산·정렬 정책을 바꾸지 않아 회귀 위험이 가장 낮다. 화면이 즉시 정리된다 | "다른 노선, 같은 정류장" 변형은 그대로 남아 5개가 비슷할 수 있다 |
| B. 정류장 쌍 기준 묶기 | 같은 승하차 정류장 쌍이면 노선을 하나의 후보로 묶고 "N13·146 중 먼저 오는 차" 처럼 표시 | 사용자가 보는 경로 수가 실제 선택지 수와 같아진다 | 노선별 소요시간 차이(급행·심야)를 숨길 수 있다. 저장 스키마·FE 표시 변경 필요 |
| C. §2.3 동률 규칙 구현 | 도착시각 동률이면 환승 수 → 도보 시간 → 출처 품질(실시간>시간표>과거평균>API) 순 | 계약 문서와 일치한다 | 정렬 결과가 바뀌므로 저장된 평가와 비교 테스트를 다시 잡아야 한다 |
| D. 평가 전 후보 상한(예: 상위 10개만 평가) | 카카오 응답 순서·환승 수로 미리 잘라 평가 비용을 줄인다 | 예산 문제가 근본적으로 줄어든다 | 잘린 후보에 더 빠른 경로가 있을 수 있다. "전체 후보 평가" 원칙과 충돌 |

## 4. 임시 제안 (승인 전)

- **A를 먼저 적용**: 완전 동일 후보만 제거, 기존 정렬 유지, 표시 최대 5개. 저장·평가·정렬 로직은 건드리지 않는다.
- 필요한 변경: 응답 조립 단계(`ScheduleEvaluationStore.response` 또는 FE 표시)에서 상위 5개만 노출 + 동일 signature 제거. `RecommendationIntegrationTest:167` 의 "전부 저장" 단언은 유지(저장은 그대로).
- 확인 방법: 일정 6 저장 평가로 후보 33 → 표시 N(≤5) 을 기록하고, 선택 1순위가 바뀌지 않음을 단언하는 테스트 추가.
- C(동률 규칙)와 B(정류장 쌍 묶기)는 별도 결정으로 남긴다.

## 5. 사용자가 결정할 것

- 선택지 A로 진행할지(권장), 아니면 B/C/D 중 무엇을 먼저 할지.
- 표시 상한 5개를 앱에서만 자를지, 서버 응답에서 자를지(서버에서 자르면 웹·앱이 같아진다).
