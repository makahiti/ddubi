# 기준선 적재 방식 결정 (회의 안건)

- 안건: `baseline_serving` 테이블에 데이터를 넣는 방법
- 작성: 인프라 (이봉민)
- 날짜: 2026-08-31
- **결정: 방법 2 채택 (2026-08-31 회의). 계약은 docs/contracts/internal-api.yaml**

## 1. 배경 — 무엇을 정해야 하나

백엔드 ERD의 `baseline_serving`은 구간별·요일별·시간대별·날씨별 평시 소요시간(p50/p80/p95)을 담는 서빙 전용 테이블이다.
원본 계산은 서버1의 Spark 배치가 HDFS 아카이브를 읽어 수행하는데, Backend(Spring)는 HDFS를 직접 읽기 어렵다.
따라서 계산 결과를 서버2의 MySQL로 옮기는 다리가 필요하다.

```
HDFS 아카이브(교통 4주치) → Spark 배치(서버1, 매일 1회) → [?? 오늘의 안건 ??] → MySQL baseline_serving(서버2, Backend가 조회)
```

데이터 규모: 하루 1회, 약 25만 행(구간 500개 기준) = 수십 MB 수준.

## 2. 두 가지 방법

### 방법 1 — Spark가 MySQL에 직접 적재

경로: `Spark(서버1) → JDBC :3306 → MySQL(서버2)`

장점
- 구현 최소: 배치에 쓰기 코드 몇 줄 + 커넥터 jar. Backend 작업 없음
- 효율 최고: 익스큐터가 병렬로 직접 적재 (수 초)
- 배치 시점에 MySQL만 살아 있으면 됨
- 계산부터 버전 전환까지 잡 하나로 끝나 실패 추적이 한 곳

단점
- 서버 간 3306 포트 개방 + 서버1에 DB 접속 정보 필요 → "외부 공개는 nginx뿐" 원칙에 예외 발생
- Backend 소유 테이블을 Spark가 직접 씀 → 스키마 변경마다 두 팀 동시 수정 (결합)
- 틀린 값이 검증 없이 그대로 서빙됨
- 적재 성공 여부가 Spark 로그에만 남음

### 방법 2 — Spark가 HTTPS로 Spring 업로드 API 호출, 적재는 Spring이

경로: `Spark(서버1) → HTTPS :443 → nginx → Spring → MySQL(서버2)`

장점
- 포트 추가 개방 없음: 이미 열린 443 재활용, 서버1에 DB 정보 없음
- 테이블 주인(Backend)이 스키마·적재·버전 전환을 전부 소유
- 적재 전 검증 가능: 틀린 값을 입구에서 거부
- HTTP라 nginx 로그·Spring 메트릭으로 Prometheus/Grafana에서 성공 여부가 바로 보임
- "서버1→서버2는 인증된 내부 API" 통로가 생겨 이후 데이터(detection_log 등)는 엔드포인트만 추가

단점
- 총 구현량이 더 많음: 업로드 API·인증·분할 전송·활성화 로직을 Backend가 구현
- 효율 열세: 드라이버로 모아 JSON 변환 후 전송 (수십 초). 단, 하루 1회 수십 MB 규모에서는 체감 차이 0
- 배치 시점에 nginx·Spring까지 살아 있어야 함 → 재시도 필요
- 업로드 API가 공개 포트 뒤에 있어 인증이 허술하면 오히려 위험

## 3. 항목별 비교

| 관점 | 방법 1 (JDBC 직접) | 방법 2 (HTTPS API) |
|---|---|---|
| 구현 비용 | **우세** — 코드 몇 줄 | 열세 — API 일체를 Backend가 구현 |
| 처리 효율 | **우세** — 병렬·바이너리, 수 초 | 열세 — 직렬·JSON, 수십 초 (현재 규모에선 무의미) |
| 보안 | 열세 — 3306 개방, 서버1에 DB 정보 | **우세** — 단, 인증(API 키 + IP 제한) 전제 |
| 틀린 값 방어 | 무방비 — 그대로 서빙 | **검증 게이트** — 거부하고 이전 버전 유지 |
| 갱신 중단 감지 | Spark 로그뿐 | **활성화 시각 기록** — 오래되면 confidence 강등 + DATA_STALE 알림 |
| 통제의 통일 | Spring 관문을 우회하는 옆문 | **모든 DB 접근이 단일 관문 통과** |
| 가용성 의존 | **MySQL만** | nginx·Spring까지 (재시도로 완화) |
| 관측성 | 별도 연동 필요 | **HTTP 메트릭 공짜** |
| 재사용성 | 데이터마다 결합 증가 | **내부 API 통로를 선례로 확보** |

## 4. 결정적 논거 — 통제의 통일

서비스 DB를 만지는 모든 행위는 Spring이라는 단일 관문을 지나야 같은 규칙(검증·트랜잭션·로깅·차단)으로 통제된다.
방법 1의 직접 쓰기는 이 관문을 우회하는 옆문이고, 옆문을 다른 경로와 통일할 깔끔한 방법이 없다.
검증 로직을 Spark에 복사하면 두 벌 유지가 되고, DB 권한으로 묶으면 들어오는 물건의 종류만 제한될 뿐 내용은 검사하지 못한다.

> 원칙: DB의 쓰기 주인은 하나, 다른 시스템은 API나 이벤트로만 접근한다.
> 두 시스템이 같은 DB를 직접 만지는 공유 DB 통합(shared database integration)은 대표적인 안티패턴이다.

### 장애 시 동작 차이 — "틀린 값을 조용히 계속 쓰는" 사고

기준선은 추천의 보조 데이터라 서비스가 같이 죽는 건 정답이 아니다. 목표는 **이상함을 알아채고, 표시하면서, 낮은 신뢰도로 동작하기**다.

- 방법 2는 방어선이 두 겹: 입구 검증이 틀린 새 값을 막고, 활성화 시각 기록이 오래된 값을 감지해 confidence를 낮추고 DATA_STALE 알림을 보낸다 (둘 다 ERD에 이미 있는 장치).
- 방법 1에서 같은 방어를 하려면 결국 Backend에 검증·신선도 코드를 넣어야 해서 방법 2를 절반 구현하는 셈이 된다.

## 5. 버전 운영 규칙 (방법 2 채택 시)

- **분할 업로드 + 활성화 분리**: 새 data_version으로 수천 행씩 나눠 POST, 전부 성공하면 활성화 요청을 별도 호출. 중간 실패 시 포인터가 안 넘어가 이전 버전이 계속 서빙됨 (pipeline_config 설계와 일치)
- **삭제는 활성화 성공 뒤 Spring만 수행**: 활성 버전과 직전 버전은 항상 보호 (조회-전환 찰나 충돌 방지 + 롤백용)
- **고아 버전 정리**: 활성화되지 못한 채 이틀 지난 버전은 다음 활성화 때 함께 삭제
- **운영 경보**: "배치 실패 / 기준선 나이 초과"를 Prometheus에 등록해 사용자보다 먼저 알기

## 6. 결론과 역할

### 제안: 방법 2 채택, 조건 4개

1. API 키 헤더 인증 + nginx에서 업로드 경로를 서버1 IP만 허용 (이중 잠금)
2. 분할 업로드와 버전 활성화 분리 (5번 운영 규칙)
3. 업로드 요청 JSON 형식을 docs/contracts/에 계약으로 먼저 확정 → Backend API 완성을 기다리지 않고 양 팀 독립 개발
4. 데이터가 커지거나 갱신 주기가 짧아지면 방법 1 재검토 (전환 비용 낮음)

### 일정 참고

이 API는 Backend의 첫 번째 목표가 아니다. transport 수집기와 segment_id 설계가 끝나야 쓸모가 생기므로,
지금 필요한 건 계약 검토·확정(반나절)뿐이고 엔드포인트 구현은 Backend 일정에 맞춰 진행하면 된다.

### 역할 분담

- 인프라: 업로드 API 계약 초안 작성. 확정 후 nginx 요청 크기 제한·IP 제한 설정 (서버 이식 때)
- Backend: 계약 검토·확정, 이후 자기 일정에 맞춰 엔드포인트 구현
- 공통: redis-keys.yaml의 schedule_segment 표기를 ERD의 route_segment로 동기화
