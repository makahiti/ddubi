# 실시간 외부 API 9종 호출·갱신 주기 조사

> 기준일: 2026-09-21 (KST)<br>
> 대상: `collector`의 운영 Compose에 등록된 9개 수집기<br>
> 목적: 팀 전체가 현재 수집 범위, 호출량, 원천 데이터의 갱신 속도, 호출 주기 단축 조건을 같은 기준으로 이해하도록 정리한다.

## 1. 먼저 보는 결론

1. 현재의 긴 호출 주기는 제공기관 제한만의 결과가 아니다. 프로젝트가 모든 비기상 API에 자체적으로 적용한 **인증키당 900회/최근 24시간 제한**, 소스별 **최소 주기**, 다건 조회의 **초당 1회 직렬 호출**이 함께 작용한다.
2. `COLLECTOR_INTERVAL_SECONDS`를 작게 바꾸는 것만으로는 주기가 줄지 않는다. 날씨를 제외하면 코드가 `max(설정값, 기본 주기)`를 사용한다.
3. 공공데이터포털의 버스 도착 API는 개발계정 1,000회이며, 활용사례를 등록해 운영계정으로 전환하면 증설 신청이 가능하다. 버스 위치는 해당 활용신청에 승인된 트래픽을 포털 콘솔에서 확인해야 한다. 서울 실시간 지하철 API도 기본 1,000회/일이며, 서울 열린데이터광장은 활용사례 심사 후 제한 해제를 안내한다.
4. 그러나 현재 `RequestBudget`은 `API_DAILY_LIMIT > 1,000`을 거부한다. 외부 승인만 받아서는 빨라지지 않으며, 내부 예산 모델과 최소 주기 정책도 수정해야 한다.
5. 여러 번 호출해야 하는 수집은 현재 모두 초당 1회로 순차 처리된다. 100개 버스 노선은 한 스냅샷에 약 100초 이상, 121개 도시 장소는 약 121초 이상 걸린다. 소스 파일의 직접 실행 기본값·검증 상한은 버스 25회/초, 지하철 위치·도시데이터 5회/초이지만, 이는 **제공기관이 보장한 TPS가 아니라 프로젝트 내부 값**이다.
6. 제공기관의 초당 호출 한도는 공식 공개 페이지에서 9종 모두에 대해 일관되게 확인되지 않았다. 운영에서 속도를 올릴 때는 일일 쿼터 승인과 별도로 담당기관에 TPS를 확인하고 부하 시험을 해야 한다.

## 4. 한 번에 전 범위를 받을 수 없는 API

### 4.1 현재 구현의 전체 스캔 방식

| 수집기 | 분할 기준 | 전체 호출 수 | 현재 서버(1회/초) | 소스 파일의 내부 상한으로 실행할 경우 | 비고 |
|---|---|---:|---:|---:|---|
| 버스 도착 | 노선 | 100회 | 약 100초+ | 직접 실행 기본값 25회/초 기준 약 4초+ | 이 함수는 25 TPS 초과를 별도로 차단하지 않는다. 723개 전체면 723회이나 운영 어댑터는 최대 100개로 제한 |
| 버스 위치 | 노선 | 100회 | 약 100초+ | 25회/초 기준 약 4초+ | 723개 전체면 723회. 운영 코드가 최대 100개로 제한 |
| 지하철 위치 | 호선 | 16회 | 약 16초+ | 5회/초 기준 약 3.2초+ | 한 호선당 한 요청 |
| 실시간 도시 | 장소 | 121회 | 약 121초+ | 5회/초 기준 약 24.2초+ | 공식 API가 한 번에 한 장소만 허용 |
| 날씨 | 격자 | 14회 | 응답시간에 따라 변동 | 코드에 명시적 TPS 제한 없음 | 25개 구가 공유하는 격자를 합쳐 14회로 절감 |
| 교통 돌발 | 1,000행 페이지 | 보통 1회 | 1회 응답시간 | 동일 | 1,000건 초과 시 `ceil(건수/1000)`회 |

`약 N초+`는 마지막 요청의 시작 시각에 마지막 응답시간을 더한 값이다. 현재 구현은 동기식 직렬 호출이므로 서버 응답이 1초보다 느리면 표보다 더 오래 걸린다.

### 4.2 “24개 범위, 초당 10회” 예시

제공기관이 10 TPS를 허용하고 24개 범위를 각각 호출해야 한다면 다음과 같이 계산한다.

| 시각 | 시작하는 요청 | 누적 요청 |
|---:|---:|---:|
| 0초 구간 | 10회 | 10회 |
| 1초 구간 | 10회 | 20회 |
| 2초 구간 | 4회 | 24회 |

- 고정 간격 방식이면 100ms마다 한 요청을 시작해 마지막 요청이 약 2.3초에 시작한다.
- 1초 단위 묶음 방식이면 0초에 10개, 1초에 10개, 2초에 4개를 시작한다.
- 전체 완료 시각은 마지막 요청의 응답시간을 더한 약 2~3초 이상이다.
- 현재 코드는 요청을 병렬로 보내지 않는다. 응답시간이 100ms보다 길면 동기식 코드만으로 실제 10 TPS를 채울 수 없으므로, 동시성 제한이 있는 비동기 요청 풀과 토큰 버킷(rate limiter)이 필요하다.
- 전체 범위가 한 스냅샷이어야 한다면 24개가 모두 성공한 뒤에만 새 버전을 공개해야 한다. 일부 실패 시에는 실패 범위만 재시도하고, 구버전 스냅샷을 계속 서비스하는 방식이 안전하다.

## 5. 현재 900회 보호장치가 주기에 미치는 영향

현재 코드는 날씨를 제외한 8종을 실제 인증키 문자열의 SHA-256 지문으로 묶어 최근 24시간 호출량을 센다. 같은 실제 키를 여러 환경변수에 넣으면 서로 다른 API라도 예산을 공유한다.

| 일반적인 키 공유 그룹 | 현재 하루 계획 | 900회 대비 여유 | 의미 |
|---|---:|---:|---|
| 버스 도착 300 + 버스 위치 300 | 600회 | 300회 | 두 수집기를 6시간마다 같이 실행하면 800회/일. 5번째 전체 스캔은 1,000회라 현재 내부 한도를 넘음 |
| 지하철 도착 480 + 위치 384 | 864회 | 36회 | 현재 6분/1시간 조합이 이미 900회에 매우 가까움. 도착을 5분으로 줄이면 합계 960회로 차단됨 |
| 알림 96 + 도시 484 + 돌발 96 + 공지 96 | 772회 | 128회 | 다른 세 API를 15분으로 유지하면 도시데이터는 최대 5회/일(약 4시간 48분 간격, 총 893회)까지가 내부 900회 범위 |

중요한 구현상 제약은 다음과 같다.

- `RequestBudget` 생성자는 `API_DAILY_LIMIT`을 1~1,000으로 제한한다.
- 예산 단위가 제공기관의 실제 과금·쿼터 단위가 아니라 **키 값 하나**다. 공공데이터포털이 상세기능별로 쿼터를 주더라도 같은 키면 내부에서는 합산될 수 있다.
- 날씨에는 이 예산 보호가 적용되지 않는다.
- 실패한 요청과 HTTP 리다이렉트도 사용량으로 기록한다.
- 한 사이클에 필요한 예산이 부족하면 사이클 전체를 시작하지 않는다.
- 버스 위치만 일시 오류 시 5분 뒤 전체 사이클을 한 번 재시도할 수 있다.

### 6.3 코드 측 필수 변경

운영계정 승인을 받은 뒤 다음 변경을 함께 해야 실제 호출 주기가 줄어든다.

1. `API_DAILY_LIMIT <= 1,000` 하드코딩을 제거하고, 제공기관·API·계정별 승인 쿼터를 설정한다.
2. 인증키 지문 하나로 합산하는 현재 모델을 `quota pool`로 명시한다. 예: `data.go.kr/bus-arrival`, `data.go.kr/bus-location`, `seoul/subway-realtime`, `seoul/general`처럼 실제 승인 단위에 맞춘다.
3. 전역 `COLLECTOR_INTERVAL_SECONDS` 대신 `BUS_ARRIVAL_INTERVAL_SECONDS` 같은 소스별 값을 둔다.
4. 비기상 소스의 `max(설정값, 기본 주기)` 정책을 운영 승인값 기반 최소 주기로 바꾼다.
5. 다건 API는 비동기 요청 풀+토큰 버킷으로 바꾸고, 제공기관별 TPS·동시 연결 수를 설정한다. 공개 문서에 TPS가 없으면 먼저 1→2→5 TPS 순으로 올리며 429/5xx/지연을 관찰한다.
6. 범위 전체가 성공한 경우에만 스냅샷 버전을 교체하고, 실패 범위 재시도·지수 백오프·지터를 적용한다.
7. `provider timestamp`, 수집 완료시간, 한 사이클 요청 수, 429/5xx, 쿼터 잔량 추정치를 지표화한다. 호출 주기는 원천 데이터가 실제로 바뀌는 속도보다 짧게 잡지 않는다.

아래 값은 리다이렉트·실패·재시도를 제외한 최소치다. 운영계정 신청 때는 최소 20% 여유를 더해 요청하는 것이 안전하다.

| 지하철 도착(리다이렉트 포함 보수적 2회) | 288회/일 | 576회/일 | 2,880회/일 |

## 8. 권장 운영안

### 당장 적용 가능한 안

- 날씨는 현재 API의 정시 자료가 목적이면 매시 10~15분 이후 14격자를 한 번 수집하고, 미공개 시 짧게 재시도한다. 현재 10분 폴링의 중복을 줄이면 2,016회/일에서 기본 336회/일로 감소한다.
- 지하철 알림은 원천이 1분 갱신이므로 15분 폴링은 새 알림 전달이 최대 약 15분 늦다. 일반키의 승인 쿼터를 확인한 후 이 소스를 우선 1~2분으로 줄이는 것이 효과가 크다.
- 도시데이터는 121장소를 초당 5회 이내로 수집하면 시작 시각 편차를 약 2분에서 약 24초로 줄일 수 있다. 먼저 제공기관 TPS 확인이 필요하다.
- 버스와 지하철 위치의 다건 조회도 승인된 TPS까지 올려 **사이클 완료 시간**을 먼저 줄인다. 이것은 일 호출량을 늘리지 않고 스냅샷의 시간 편차만 줄이는 개선이다.

### 운영계정 승인 후 권장 순서

1. 제공기관 콘솔·답변으로 `일 쿼터`, `TPS`, `쿼터 단위`, `리다이렉트 과금 여부`를 확정한다.
2. 내부 예산 모델과 소스별 최소 주기를 승인값에 맞게 변경한다.
3. 호출량을 늘리지 않는 범위에서 다건 스캔 속도부터 높인다.
4. 원천 갱신 주기가 명확한 알림·인구·상권부터 폴링 주기를 줄인다.
5. 429, 5xx, P95 응답시간, 스냅샷 완성률을 보고 단계적으로 목표 주기까지 내린다.

## 10. 조사 범위와 확인이 남은 사항

이번 조사는 저장소 코드·설정·테스트와 5개 검색 관점에서 Exa 검색 후보 207건을 검토한 뒤, 서울시·공공데이터포털·기상청 등 공식 1차 출처를 우선해 정리했다.

저장소만으로는 다음 운영 상태를 확정할 수 없다.

- 배포 서버에서 실제 사용하는 각 키가 개발계정인지 운영계정인지
- 각 활용신청에 승인된 정확한 일일 트래픽과 TPS
- 서로 다른 API가 제공기관에서 실제로 같은 쿼터 풀을 공유하는지
- 서버의 최근 24시간 실사용량, 429 응답, 평균·P95 응답시간

따라서 다음 운영 점검 때 제공기관 콘솔 화면과 Collector 메트릭을 이 문서에 증빙으로 추가해야 한다. 인증키 원문은 문서나 로그에 남기지 않는다.
