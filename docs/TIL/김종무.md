### 예측 요청부터 결과까지

```text
Spring 백엔드
  → 경로 후보를 인접 버스 정류장 구간으로 매핑
  → 해당 구간 식별자와 진입 예상 날짜·시간 전달
Python 예측 서비스
  → app.py: 필수 값·타입·범위 검증
  → features.py: 달력·좌표·과거 이력을 결합하고 학습과 동일하게 변환
  → predictor.py: 로딩된 모델로 구간 소요시간 예측
Spring 백엔드
  → 예측 시간과 다른 이동·대기 구성요소를 결합해 최종 결과 구성
```

현재 예측 함수의 최소 입력은 다음 6개다. 외부 HTTP 요청·응답 계약은 구현 전에 별도로 확정해야 한다.

| 입력 필드 | 의미 |
|---|---|
| `provider_route_id` | 학습에 사용한 제공자 체계의 버스 노선 ID |
| `provider_from_stop_id` | 출발 정류장 제공자 ID |
| `provider_to_stop_id` | 도착 정류장 제공자 ID |
| `from_stop_sequence` | 해당 노선의 출발 정류장 순번 |
| `service_date` | 구간 진입 예상 날짜, Asia/Seoul 기준 |
| `hour_slot` | 구간 진입 예상 시간대, 0~23 |

- 카카오 ID·정류장 이름·버스 번호를 위 ID로 그대로 대입하지 않는다. 내부 구간 ID와 제공자 ID도 구분하고 검증된 매핑을 사용한다.
- 날짜로 요일·주말·공휴일을 생성하고, 정류장과 구간 식별자로 좌표·과거 운행·수요 통계를 조회한다.
- 과거 통계는 예측 시점에 이용 가능한 정보만 사용하며, 학습 때와 동일한 기간·집계·인코딩·결측 처리 규칙을 유지한다.
- 목표 수집 목록에 날씨·사고·실시간 정보가 있다고 해서 현재 v12 모델에 모두 연결된 것은 아니다. 새 피처를 반영하려면 학습·예측 양쪽을 변경하고 재검증해야 한다.
- 결과는 소요시간(초)과 함께 모델 버전, 결측·미등록 ID 등 품질 정보를 추적할 수 있어야 한다. 매핑 실패나 오래된 데이터는 정상으로 숨기지 않는다.
- 앞 구간의 도보·대기·이동시간을 반영해 다음 구간의 진입 시각을 계산하고, 환승 이동과 다음 차량 대기를 중복 합산하지 않는다.

### 컨테이너 운영 방안

- 별도 물리 서버가 반드시 필요한 것은 아니다. 자원이 충분하면 같은 서버에서 Spring과 Python 예측 서비스를 각각의 컨테이너로 실행할 수 있다.
- 백엔드는 내부 HTTP로 예측을 요청하도록 제안한다. 이는 기존 Redis 최신 상태·기준선 흐름을 교체하는 확정 계약이 아니며, Backend 담당자와 연동·fallback 정책을 합의해야 한다.
- 예측 프로세스가 시작할 때 모델을 한 번 불러두고 요청마다 재사용한다. 프로세스를 여러 개 실행하면 모델 메모리도 중복되므로 worker 수는 부하 시험 후 결정한다.
- 모델과 참조 데이터는 이미지에 포함하지 않고 읽기 전용 볼륨으로 연결하는 방안을 사용한다. 모델·입력 규격·참조 데이터 버전의 호환성을 검증하고 변경 시 재로딩 또는 재시작 정책을 둔다.
- 현재 선정된 CPU 모델의 예측에는 GPU가 필요하지 않다. GPU 서버에서 수행한 학습과 운영 서버에서 수행하는 예측은 별도 과정이다.
- 개발 단계에서는 컨테이너 없이 먼저 예측 결과를 검증할 수 있다. 컨테이너·네트워크·자원 제한·배포 설정은 인프라 담당자에게 요구사항을 전달한다.
- 이번 작업에서는 Docker, `infra/`, CI 설정 및 운영 서버를 변경하지 않는다.

### 배운 점

- 모델 덤프는 예측 규칙이고 참조 데이터는 이번 요청의 피처를 만드는 재료이므로, 모델 파일만 복사한다고 같은 결과가 재현되는 것은 아니다.
- 기존 예측 코드가 학습 모듈을 import하는 구조라면 학습 실행이나 고정 서버 경로에 의존하지 않도록 추론 전용 로직으로 분리해야 한다.
- 결측값을 임의의 0으로 채우거나 입력 필드를 예측 때만 제거하면 학습과 다른 입력이 된다. 전처리와 입력 규격을 모델과 함께 버전 관리해야 한다.
- `.joblib`은 신뢰할 수 있는 자체 산출물만 로드하고, 학습 당시와 호환되는 라이브러리 버전 및 파일 무결성을 확인해야 한다.
- 버스 구간 모델의 오차를 전체 경로 정확도로 바로 해석할 수 없다. 경로별 실측 정답으로 대기·환승 등을 포함한 최종 결과를 별도로 검증해야 한다.

### 다음 작업

1. 최종 모델·입력 규격·설정과 필요한 참조 데이터를 버전별로 묶는다.
2. 학습 코드에서 피처 생성·예측 부분을 분리하고 경로를 설정으로 주입한다. DuckDB는 사용하지 않는다.
3. 같은 입력에서 GPU 서버의 기존 CPU 모델 예측과 분리한 코드의 결과가 허용 오차 안에서 일치하는지 검증한다.
4. 미매핑 ID, 결측, 참조 데이터 누락·stale, 잘못된 날짜·시간 및 모델 로딩 실패를 테스트한다.
5. Backend와 요청·응답, 시간 단위, timeout, fallback 정책을 합의한 후 예측 API를 구현한다.
6. 응답시간·처리량·최대 메모리를 측정하고 인프라 담당자에게 컨테이너 운영 요건을 전달한다.

관련 로컬 기준 문서: `docs/contracts/ml-data-decision.md`. 해당 문서는 목표 데이터 범위이며, 현재 모델의 전체 입력 연결 완료를 의미하지 않는다.
