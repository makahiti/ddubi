# ML 예측 응답이 4초 걸리는 이유 (2026-09-18 측정, 코드 변경 없음)

관측만 추가한 상태에서 서버2 실물로 측정했다. **모델·예측값·묶음은 바꾸지 않았다.**

## 1. 결론

한 번의 예측 요청에서 시간의 거의 전부는 **과거 참고자료를 읽어 표로 바꾸는 단계**에서 쓰인다.
모델이 계산하는 시간은 1000분의 몇 초 수준이다.

| 단계 | 뜻 | 걸린 시간 |
|---|---|---|
| 대기(queue) | 앞 요청이 끝나길 기다린 시간 | 0~1ms |
| 특성 준비(feature) | 과거 자료를 읽어 입력표를 만드는 시간 | 3,150~3,850ms |
| 추론(inference) | 모델이 값을 계산하는 시간 | 6~21ms |

## 2. 구간 수와 거의 무관하다

같은 요청을 구간 수만 바꿔 보냈다.

| 구간 수 | 전체 시간 |
|---|---|
| 1개 | 3.19초 |
| 10개 | 3.25초 |
| 22개 | 3.53초 |

구간이 22배가 돼도 0.34초만 늘었다. 즉 **요청 한 번마다 붙는 고정 비용**이다.
배치로 묶는 지금 방식은 맞는 선택이고, 더 잘게 쪼개면 오히려 손해다.

## 3. 고정 비용의 출처

참고자료 폴더는 340MB이고, 그중 한 파일(월별 수요)이 84MB로 가장 크다.
특성 준비 함수는 요청마다 이 파일을 포함해 여러 참고 파일을 **판다스 표로 다시 변환**한다.
파일 읽기 자체는 캐시에 남지만, 표로 바꾸는 작업은 매번 새로 한다.
지연 시간이 요청 크기와 무관하게 일정한 것이 이 설명과 일치한다.

## 4. 후속 개선 후보 (아직 적용하지 않음)

- 월별 수요 파일을 **필요한 열·행만** 읽도록 좁힌다.
- 변환된 표 자체를 캐시에 올린다(지금은 파일만 캐시).
- 참고자료를 미리 준비해 두고 요청 때는 조회만 하도록 바꾼다.

셋 다 예측값은 바뀌지 않는 범위다. 다만 묶음 검증 규칙을 건드리므로 별도 승인과 회귀 시험이 필요하다.

## 5. 지금 설정이 안전한 이유

고정 비용이 3~4초이므로 backend 대기 상한 7초는 두 배 가까운 여유가 있다.
동시 2건이 들어오면 두 번째는 2초 만에 `MODEL_BUSY`로 빠르게 실패하고 과거 평균 계산으로 넘어간다(실측 2.04초).
