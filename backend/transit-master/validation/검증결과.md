## 재현·오탐·회귀 검증

- 두 날짜 모두 별도 Matcher로 전체 입력을 재계산한 결과 동일.
- 두 날짜 각각 역방향·좌표 이동·미등록 노선·전체 이름 변경·0 길이 1,405건: 잘못된 VERIFIED 0건.
- 전체 검증 전후 1~20.json SHA-256 동일.
- 단위/기존 서울·지하철/카카오 응답/계약 테스트: 73건 중 71건 통과, 실패·오류 0건, 2건 skip.
- skip 1: 신규 실제 MySQL 테스트. 이 PC에서 유효한 Docker 환경을 찾지 못함. DB 적재·롤백·캐시 FK의 실제 MySQL 동작은 미검증이다.
- skip 1: 기존 `MappingCorpusReplayTest`는 별도 corpus 속성 미지정. 이 작업의 실제 1~20.json 검증은 `MetropolitanBusReplay` 실행으로 수행했다.
- 새 V4 테이블 정의와 ERD 일치, artifact SHA와 manifest 일치, `git diff --check` 확인.

Mock JDBC 테스트는 해시/데이터 오류가 DB 접근 전에 거부되는지, 카탈로그 테스트는 새 버전 읽기 실패 때 마지막 정상 스냅샷을 유지하는지 확인한다. 이를 실제 DB 트랜잭션 검증으로 표현하지 않는다.

## 적용 범위와 후속 작업

BUS는 항상 수도권 매핑기를 사용한다. 활성 마스터가 없으면 미구성 상태를 반환한다. 운영 사용 전에는 V4 적용·관리 적재가 필요하다. 운영 DB, 인프라/알림 설정, 원본 카카오 JSON, 기존 stash는 변경하지 않았다. 커밋/푸시는 하지 않았다.

ML 학습 ID 대응, 경기·인천의 공용 canonical topology 계약, 차량 대안 선택/시간 집계는 후속 작업이다. 공식 출처 ID만 확인된 경기·인천 결과는 별도 대안으로 반환하며 임의 segment_id를 발급하지 않는다. 기존 계약이 있는 SEOUL_BUS 단일 검증 대안만 상위 EXACT/segments를 유지한다.

기계 판독 요약과 파일별 수치·입력 해시는 같은 폴더의 `summary.json`에 있다. 상세 후보는 `backend/target/metropolitan-replay-reviewed.json`, `backend/target/metropolitan-replay-current.json`에서 확인한다. 실행 방법은 `backend/transit-master/README.md`에 있다.

## 기존 버스 코드 제거 후 검증 (2026-09-10)

- 서울 전용 버스 Matcher·읽기 모델·JDBC 조회·XLSX 적재·POI·150m 설정·서비스 전환 플래그를 제거했다.
- 지하철 적재가 버스 파일 없이 성공하고 BUS 별칭은 거절되는지 검증했다. 기존 지하철·공용 ID·수동 캐시 거절 경계를 유지한다.
- 기존 회귀 사례는 수도권 테스트로 옮겼다. 과거 corpus JSON 입력용 Legacy fixture만 테스트 소스에 남겼다.
- 실제 DTO → KakaoRouteMapper → MasterDataTransitMappingResolver를 통과한 281개 BUS step의 대안 목록이 두 기준일 모두 순수 Matcher와 완전히 일치했다.
- 9월 9일 기준 757/768 공간 검증 통과 및 기존 공식 ID·전체 순번 유지. 변경 0건.
- 9월 10일 기준 730/768 공간 검증 통과. 만료된 검토 규칙 때문에 감소한 27건은 기존 결과와 동일하며 이번 코드 제거로 악화된 것이 아니다.
- 두 날짜 각각 손상 입력 1,405건에서 잘못된 VERIFIED 0건. 원본 20개 파일의 SHA-256 유지.
- 깨끗한 빌드 후 관련 테스트와 최종 회귀 실행: 73건 중 71건 통과, 실패 0·오류 0·건너뜀 2건. 건너뛴 범위는 위의 MySQL 및 선택 corpus 테스트다.
- 운영 DB를 변경하거나 활성화하지 않았고 기존 테이블·V1~V3도 삭제·수정하지 않았다. DB 실제 트랜잭션은 Docker 부재로 미검증이다.
